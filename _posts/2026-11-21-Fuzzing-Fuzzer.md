# <toc>퍼징(Fuzzing)이란</toc>

퍼징은 프로그램에 <mark>예상하지 못한 입력, 형식이 깨진 입력, 무작위에 가까운 입력을 자동으로 대량 주입</mark>하고, 그 과정에서 프로그램이 비정상적으로 동작하는지 관찰하는 테스트 기법이다. 이런 일을 해 주는 도구를 **퍼저(Fuzzer)**라고 부른다.

사람이 테스트 케이스를 직접 작성하는 단위 테스트는 "개발자가 예상한 입력"만 검사하게 된다. 반면 퍼징은 기계가 수백만 개의 입력을 만들어 던지기 때문에, 개발자가 미처 생각하지 못한 경계 조건을 찾는 데 강하다.

예를 들어 이미지 뷰어를 테스트한다고 하자. 사람이 직접 테스트하면 정상적인 PNG, JPG 파일 몇 개를 열어 보는 정도로 끝날 것이다. 퍼저는 정상 PNG 파일의 바이트를 조금씩 바꿔서 초당 수천~수만 개씩 만들어 계속 열어 본다. 그러다 어떤 파일에서 프로그램이 죽으면, 그 파일을 저장해 두고 개발자나 보안 연구자가 원인을 분석한다.

### <toc2>퍼징이 잘 찾는 버그</toc2>

퍼징이 특히 잘 찾는 것은 <mark>메모리 안전성 취약점</mark>이다.

- **버퍼 오버플로우(Buffer Overflow)**: 할당된 메모리 공간보다 더 많은 데이터를 써서 옆 메모리를 덮어쓰는 버그
- **Use-After-Free(UAF)**: 이미 해제한 메모리를 다시 사용하는 버그
- **정수 오버플로우(Integer Overflow)**: 정수가 표현 범위를 넘어가 엉뚱한 값이 되는 버그. 잘못된 크기 계산으로 이어져 버퍼 오버플로우를 일으키기도 한다

이런 버그는 개발자가 "설마 이런 입력이 들어오겠어?"라고 생각한 경계 조건에서 주로 발생한다. 그래서 사람이 작성한 테스트보다 기계가 쉬지 않고 입력을 던져 보는 퍼징이 이런 버그를 더 잘 찾는다.

### <toc2>퍼징의 기본 흐름</toc2>

```text
[시드 입력] → [입력 생성/변형] → [타겟에 전달] → [실행 & 모니터링] → [결과 분류]
                    ↑                                                 │
                    └──────── (피드백: 새 경로를 찾은 입력은 보관) ────────┘
```

1. **입력 생성**: 처음부터 새로 만들거나, 기존의 정상 입력을 조금씩 바꾼다.
2. **전달**: 파일, 표준 입력, 공유 메모리, 네트워크 소켓 등으로 타겟 프로그램에 입력을 넣는다.
3. **모니터링**: 프로그램이 죽었는지, 멈췄는지, 메모리 오류가 났는지 감시한다.
4. **결과 분류**: 문제를 일으킨 입력을 저장해 나중에 재현하고 분석할 수 있게 한다.
5. **피드백(선택)**: 똑똑한 퍼저는 "이 입력이 프로그램의 새로운 부분을 실행시켰는가?"를 확인하고, 새로운 부분을 연 입력을 다음 변형의 재료로 삼는다.

# <toc>퍼징 용어 정리</toc>

뒤에서 퍼저들을 비교할 때 계속 나오는 용어들이다. 이 부분만 이해하면 이후 내용은 어렵지 않으니, 필요할 때 펼쳐서 확인하면 된다.

<details markdown="1">
<summary>기본 용어</summary>

| 용어 | 설명 |
|---|---|
| 타겟(Target, PUT) | 퍼징 대상 프로그램이나 라이브러리. 논문에서는 PUT(Program Under Test)라고도 쓴다 |
| 하네스(Harness) / 퍼즈 타겟(Fuzz Target) | 퍼저가 만든 입력을 받아 타겟의 특정 함수에 넘겨 주는 **연결용 코드**. 예를 들어 "퍼저가 준 바이트 배열을 이미지 파싱 함수에 넣어라"라는 짧은 함수다 |
| 시드(Seed) | 변형의 출발점이 되는 정상 입력. 예: 정상 PNG 파일 몇 개 |
| 코퍼스(Corpus) | 퍼저가 모아 둔 입력들의 집합. 시드에서 시작해 퍼징이 진행될수록 쓸모 있는 입력이 계속 추가된다 |
| 크래시(Crash) | 프로그램이 비정상 종료되는 것. 퍼징에서 가장 중요하게 보는 결과다 |
| 행(Hang) / 타임아웃 | 프로그램이 제한 시간 안에 끝나지 않는 것. 무한 루프 같은 버그의 신호다 |
| 오픈 소스 / 클로즈드 소스 | 소스 코드가 공개된 프로그램 / 실행 파일(바이너리)만 있고 소스 코드는 없는 프로그램 |

</details>

<details markdown="1">
<summary>입력 생성 관련 용어</summary>

| 용어 | 설명 |
|---|---|
| 뮤테이션(Mutation, 변형) | 기존 입력을 조금씩 바꾸는 것. 비트 하나 뒤집기(bit flip), 바이트 바꾸기, 데이터 끼워 넣기·지우기 등이 있다 |
| 스플라이싱(Splicing) | 두 입력을 잘라서 이어 붙여 새 입력을 만드는 변형 방식 |
| 사전(Dictionary) | `<html>`, `PNG`, `SELECT`처럼 타겟이 의미 있게 받아들이는 키워드 목록. 퍼저가 무작위 바이트 대신 이 단어들을 섞어 넣어 효율을 높인다 |
| 문법(Grammar) | 입력이 따라야 하는 규칙(예: JavaScript 문법, HTTP 요청 형식). 문법을 알면 형식이 맞는 입력을 만들어낼 수 있다 |
| 매직 넘버(Magic Number) | 파일 맨 앞의 `\x89PNG`처럼 특정 값과 정확히 일치해야 통과되는 검사 값. 무작위 변형으로 우연히 맞추기가 매우 어렵다 |
| 체크섬(Checksum) | 데이터가 손상되지 않았는지 확인하는 검증 값. 입력을 조금만 바꿔도 체크섬이 틀어져 프로그램이 입력을 바로 버리기 때문에 퍼징의 큰 장애물이 된다 |

</details>

<details markdown="1">
<summary>커버리지와 계측 관련 용어</summary>

| 용어 | 설명 |
|---|---|
| 커버리지(Coverage) | 입력 하나가 프로그램 코드의 **어느 부분을 실행시켰는지**를 나타내는 정보 |
| 기본 블록(Basic Block) | 중간에 분기 없이 위에서 아래로 쭉 실행되는 코드 덩어리 |
| 엣지(Edge) | 기본 블록에서 다른 기본 블록으로 넘어가는 경로. "A 블록 다음에 B 블록이 실행됐다"는 정보다. 대부분의 퍼저는 엣지 커버리지를 기준으로 새 경로를 판단한다 |
| 계측(Instrumentation) | 커버리지를 수집하기 위해 프로그램에 **감시용 코드를 끼워 넣는 것** |
| 컴파일 타임 계측 | 소스 코드를 컴파일할 때 감시 코드를 함께 넣는 방식. 빠르고 정확하지만 소스 코드가 있어야 한다 |
| 동적 바이너리 계측(DBI) | 이미 만들어진 실행 파일이 **실행되는 도중에** 감시 코드를 끼워 넣는 방식. 소스가 없어도 되지만 컴파일 타임 계측보다 느리다. TinyInst, Frida가 이런 도구다 |
| 에뮬레이션 | QEMU, Unicorn처럼 CPU를 소프트웨어로 흉내 내는 도구 위에서 프로그램을 실행하며 커버리지를 수집하는 방식. 소스가 없어도 되고 다른 CPU 구조의 바이너리도 돌릴 수 있지만 느리다 |
| 하드웨어 기반 피드백 | Intel PT, Intel BTS처럼 CPU 자체에 있는 실행 추적 기능으로 커버리지를 얻는 방식. 프로그램을 수정하지 않아도 된다 |

</details>

<details markdown="1">
<summary>실행 방식 관련 용어</summary>

| 용어 | 설명 |
|---|---|
| exec/s | 1초에 타겟을 몇 번 실행하는지. 퍼저 속도를 나타내는 대표 지표다 |
| 포크 서버(Fork Server) | 타겟을 매번 처음부터 실행하지 않고, 초기화가 끝난 상태의 프로세스를 복제(fork)해서 실행 시간을 줄이는 기법 |
| 퍼시스턴트 모드(Persistent Mode) | 프로세스를 새로 만들지 않고 **한 프로세스 안에서 반복문을 돌며** 여러 입력을 처리하는 방식. 매우 빠르다 |
| In-process 퍼징 | 퍼저와 타겟이 **같은 프로세스 안에서** 동작하는 방식. 가장 빠르지만 타겟이 죽으면 퍼저도 함께 죽는다 |
| 공유 메모리(Shared Memory) | 여러 프로세스가 함께 쓰는 메모리 영역. 입력을 파일로 쓰고 읽는 대신 공유 메모리로 넘기면 디스크 작업이 없어 빠르다 |
| 시드 스케줄링 / 파워 스케줄(Power Schedule) | 코퍼스의 여러 입력 중 **어떤 입력을 얼마나 자주 변형할지** 정하는 전략. 덜 탐색된 경로를 가진 입력에 더 많은 기회를 주는 식이다 |
| 분산 퍼징 | 여러 CPU 코어나 여러 컴퓨터에서 퍼저를 동시에 돌리고, 찾은 입력을 서로 공유하는 방식 |

</details>

<details markdown="1">
<summary>버그 탐지 관련 용어</summary>

| 용어 | 설명 |
|---|---|
| 새니타이저(Sanitizer) | 프로그램이 바로 죽지는 않지만 실제로는 잘못된 동작을 감지해서 강제로 알려 주는 컴파일러 기능. 예를 들어 버퍼를 1바이트만 넘어 써도 프로그램이 멀쩡히 돌아갈 수 있는데, 새니타이저를 켜면 그 순간 오류를 보고한다 |
| ASan (AddressSanitizer) | 버퍼 오버플로우, UAF 같은 메모리 접근 오류를 잡는 새니타이저 |
| UBSan / MSan | 정의되지 않은 동작(Undefined Behavior)을 잡는 새니타이저 / 초기화되지 않은 메모리 사용을 잡는 새니타이저 |
| 코퍼스 최소화(Corpus Minimization) | 같은 커버리지를 내는 중복 입력을 제거해 코퍼스를 작게 유지하는 작업 |

</details>

# <toc>퍼징의 종류</toc>

퍼징은 보통 두 가지 기준으로 분류한다. <mark>타겟 내부를 얼마나 알고 있는가</mark>와 <mark>입력을 어떻게 만드는가</mark>이다.

### <toc2>1. 타겟 정보 기준: 블랙박스 / 그레이박스 / 화이트박스</toc2>

**블랙박스 퍼징(Black-box Fuzzing)**은 타겟 내부를 전혀 보지 않고, 입력을 넣은 뒤 프로그램이 죽었는지만 확인한다. 준비가 거의 필요 없다는 것이 장점이지만, 어떤 입력이 "좋은 입력"인지 알 방법이 없어서 프로그램 깊숙한 곳까지 도달하기 어렵다.

**그레이박스 퍼징(Grey-box Fuzzing)**은 계측으로 커버리지 정보를 가볍게 수집한다. 새로운 코드 경로를 실행시킨 입력을 보관하고, 그 입력을 다시 변형하는 과정을 반복하면서 점점 더 깊은 코드까지 들어간다. 이 방식을 **커버리지 기반 퍼징(Coverage-guided Fuzzing)**이라고도 부른다. 성능과 비용의 균형이 좋아서 <mark>현재 실무에서 쓰이는 퍼저 대부분이 이 방식</mark>이다. 이 글에서 다루는 퍼저도 모두 그레이박스 퍼저다.

**화이트박스 퍼징(White-box Fuzzing)**은 프로그램 내부 로직을 정밀하게 분석한다. 대표 기법이 **심볼릭 실행(Symbolic Execution)**이다. 입력값을 구체적인 숫자 대신 `x` 같은 기호로 두고 프로그램을 따라가며, "이 분기를 통과하려면 x가 어떤 조건을 만족해야 하는가"를 수식으로 모으는 기법이다. 모은 수식을 **SMT 솔버(수식을 만족하는 값을 자동으로 찾아 주는 도구)**로 풀면 특정 경로를 통과하는 입력을 정확히 계산할 수 있다. 매직 넘버 같은 조건도 쉽게 통과하지만, 연산 비용이 커서 큰 프로그램 전체에 적용하기는 어렵다.

| 구분 | 타겟 내부 정보 | 장점 | 단점 |
|---|---|---|---|
| 블랙박스 | 없음 | 준비가 간단하고 어떤 타겟에도 적용 가능 | 깊은 코드 경로에 도달하기 어려움 |
| 그레이박스 | 커버리지 | 적은 비용으로 높은 효율, 대규모 코드에도 적용 가능 | 매직 넘버·체크섬 같은 까다로운 조건에서 막히기 쉬움 |
| 화이트박스 | 전체 로직 | 원하는 경로를 정밀하게 탐색 | 연산 비용이 커서 큰 프로그램에는 비현실적 |

### <toc2>2. 입력 생성 방식 기준: 뮤테이션 / 생성 / 구조 인식</toc2>

**뮤테이션 기반 퍼징(Mutation-based Fuzzing)**은 시드를 조금씩 변형해 새 입력을 만든다. 입력 형식을 몰라도 시드만 있으면 시작할 수 있다. 다만 JavaScript 코드처럼 문법이 엄격한 입력은 무작위로 바꾸면 대부분 문법 오류가 나서, 파서(입력을 해석하는 부분) 뒤에 있는 실제 로직까지 도달하지 못한다.

**생성 기반 퍼징(Generation-based Fuzzing)**은 문법이나 파일 포맷 명세를 바탕으로 입력을 처음부터 만든다. 항상 형식이 맞는 입력이 나오므로 프로토콜, 스크립트 엔진, 컴파일러처럼 입력 구조가 엄격한 타겟에 유리하다. 대신 문법을 미리 작성해야 하는 부담이 있다.

**구조 인식 퍼징(Structure-aware Fuzzing)**은 둘을 섞은 방식이다. 뮤테이션 기반으로 동작하지만 입력의 구조를 알고 있어서 <mark>구조는 유지한 채 내용만 바꾸는</mark> 변형을 한다. 예를 들어 libFuzzer는 **커스텀 뮤테이터(사용자가 직접 정의한 변형 함수)**를 붙여 구조 인식 퍼저로 만들 수 있고, **protobuf(구글의 구조화 데이터 직렬화 형식)** 입력을 위해서는 libprotobuf-mutator라는 도구가 있다.

# <toc>대표 퍼저 정리</toc>

퍼저는 <mark>어떤 타겟을 대상으로 하는가</mark>에 따라 크게 네 갈래로 나눠 볼 수 있다.

| 갈래 | 대표 퍼저 | 한 줄 설명 |
|---|---|---|
| 범용 커버리지 기반 퍼저 | AFL++, honggfuzz | 실행 파일 단위로 타겟을 돌리는, 가장 일반적인 형태의 퍼저 |
| 라이브러리(in-process) 퍼저 | libFuzzer | 특정 함수를 같은 프로세스 안에서 반복 호출하는 퍼저 |
| 바이너리 전용 퍼저 | Jackalope | 소스 코드 없는 실행 파일, 특히 Windows·macOS 프로그램을 위한 퍼저 |
| 퍼저 프레임워크 | LibAFL | 완성된 도구가 아니라 퍼저를 직접 조립하는 라이브러리 |

### <toc2>1. AFL++ — 기능이 가장 풍부한 범용 퍼저</toc2>

> 그레이박스 퍼징을 대중화한 AFL을 커뮤니티가 이어받아 발전시킨, 현재 가장 널리 쓰이는 범용 퍼저

**배경**

AFL(American Fuzzy Lop)은 Michal Zalewski(lcamtuf)가 Google에서 만든 퍼저로, 커버리지 기반 퍼징을 널리 알린 도구다. 원본 AFL의 개발이 멈춘 뒤 Marc Heuse, Dominik Maier, Andrea Fioraldi, Heiko Eissfeldt 등이 이를 포크(fork, 기존 프로젝트를 복사해 독자적으로 개발하는 것)해 AFL++를 만들었다. 원본보다 빠른 속도, 더 다양한 뮤테이션과 계측 방식, 커스텀 모듈 지원을 내세운다.

**동작 방식**

타겟을 별도 프로세스로 실행하고, **포크 서버**로 매번 처음부터 실행하는 비용을 줄인다. 하네스를 작성하면 **퍼시스턴트 모드**로 한 프로세스 안에서 반복 실행해 속도를 더 높일 수 있다.

**주요 특징**

- **다양한 커버리지 수집 방법**: 소스가 있으면 AFL++ 전용 컴파일러(`afl-cc`)로 컴파일 타임 계측을 하고, 소스가 없으면 **QEMU 모드**(에뮬레이션), **Unicorn 모드**(CPU 에뮬레이터 라이브러리로 펌웨어 같은 코드 조각 실행), **Frida 모드**(동적 바이너리 계측)를 쓸 수 있다.
- **까다로운 조건 통과**
  - **CmpLog / Redqueen**: 프로그램이 입력값을 어떤 값과 비교하는지 기록해 두었다가, 그 값을 입력에 직접 넣어 본다. `if (magic == 0xDEADBEEF)` 같은 조건을 무작위 변형보다 훨씬 빨리 통과한다.
  - **laf-intel**: 4바이트를 한 번에 비교하는 코드를 1바이트씩 비교하는 여러 단계로 쪼갠다. 한 바이트만 맞아도 "새 경로"로 인식되므로 퍼저가 한 단계씩 정답에 다가갈 수 있다.
- **스케줄링과 변형 전략**: 여러 **파워 스케줄** 중 상황에 맞는 전략을 고를 수 있고, **MOpt**(어떤 변형 방법이 효과적인지 학습해 자주 쓰는 기법)를 지원한다.
- **커스텀 뮤테이터**: 사용자가 직접 만든 변형 방식을 플러그인처럼 붙일 수 있다. 구조 인식 퍼징도 이 기능으로 구현한다.
- **libFuzzer 하네스 호환**: libFuzzer용으로 작성한 하네스를 거의 그대로 AFL++에서 쓸 수 있다.

**장점**

- 소스 있는 타겟과 없는 타겟을 모두 다룰 수 있어 활용 범위가 넓다.
- 퍼징 연구의 최신 기법들이 꾸준히 통합되어 성능이 좋다. 여러 벤치마크에서 상위권 성적을 낸다.
- 사용자와 자료가 많아 문제를 만났을 때 참고할 곳이 많다.

**단점**

- 옵션과 모드가 매우 많아 처음 접하면 무엇을 켜야 할지 헷갈린다.
- 바이너리 전용 모드(QEMU 등)는 컴파일 타임 계측보다 확연히 느리다.
- 주로 Linux 환경을 중심으로 쓰인다. Windows 프로그램 퍼징에는 다른 도구가 더 적합하다.

**이럴 때 쓰면 좋다**

- 소스 코드가 있는 C/C++ 프로그램을 본격적으로, 오래 퍼징하고 싶을 때
- 소스가 없는 Linux 바이너리를 퍼징해야 할 때
- libFuzzer로 시작한 하네스를 더 강력한 퍼저로 옮기고 싶을 때

```bash
# 기본 실행 형태 (@@ 자리에 퍼저가 만든 입력 파일 경로가 들어간다)
afl-fuzz -i seeds/ -o out/ -- ./target @@
```

### <toc2>2. honggfuzz — 하드웨어 피드백을 지원하는 빠르고 간편한 퍼저</toc2>

> 멀티 프로세스·멀티 스레드로 CPU를 최대한 활용하고, CPU 하드웨어 기능으로도 커버리지를 얻을 수 있는 범용 퍼저

**배경**

Google 저장소에 공개된 퍼저로, Robert Swiecki가 주로 개발하고 있다. 스스로를 "보안 지향적이고 피드백 기반으로 진화하는, 사용하기 쉬운 퍼저"로 소개한다.

**주요 특징**

- **멀티 프로세스 + 멀티 스레드**: 퍼저 하나만 실행해도 여러 CPU 코어를 모두 쓴다. 여러 스레드가 코퍼스를 자동으로 공유하기 때문에 AFL++처럼 인스턴스를 여러 개 따로 띄울 필요가 없다.
- **다양한 피드백 방식**: 컴파일 타임 계측(SanitizerCoverage) 같은 소프트웨어 방식뿐 아니라, Linux에서는 **Intel PT·Intel BTS**나 CPU의 분기·명령어 카운터 같은 **하드웨어 기반 피드백**도 지원한다. 즉, 소스 없이도 프로그램을 수정하지 않고 커버리지를 얻을 수 있다.
- **퍼시스턴트 모드**: 한 프로세스 안에서 입력을 반복 처리해 매우 높은 실행 속도를 낼 수 있다.
- **간편한 시작**: 빈 코퍼스나 1바이트짜리 파일 하나로 시작해도 커버리지 피드백을 이용해 스스로 입력을 키워 나간다.
- **넓은 플랫폼**: Linux, FreeBSD, NetBSD, macOS, Windows(CygWin), Android에서 동작한다. 블랙박스 바이너리용 QEMU 모드도 있다.
- **실적**: OpenSSH의 인증 전 원격 크래시, Apache HTTPD, 여러 SSL 라이브러리의 버그를 찾았고, OSS-Fuzz를 통해서도 수십 건의 보안 문제를 발견했다.

**장점**

- 설정이 간단하고, 퍼저 하나로 멀티코어를 바로 활용할 수 있다.
- 하드웨어 기반 피드백이라는 독특한 선택지가 있다.
- 범용 퍼저 비교 연구에서 AFL++와 함께 최상위권 성능을 보인 적이 있다.

**단점**

- 하드웨어 기반 피드백은 **Linux + 이를 지원하는 Intel CPU**에서만 쓸 수 있다(AMD 미지원).
- AFL++에 비하면 커스텀 뮤테이터나 부가 기능 생태계, 참고 자료가 작은 편이다.

**이럴 때 쓰면 좋다**

- 복잡한 설정 없이 멀티코어로 빠르게 퍼징을 돌리고 싶을 때
- 소스가 없는 Linux 바이너리를 Intel PT로 퍼징하고 싶을 때
- AFL++와 함께 돌려 서로 다른 퍼저의 결과를 비교·보완하고 싶을 때

### <toc2>3. libFuzzer — 함수 단위로 가장 쉽게 시작하는 퍼저</toc2>

> LLVM(Clang 컴파일러 프로젝트)에 내장된 in-process 커버리지 기반 퍼저

**배경**

libFuzzer는 LLVM 프로젝트의 일부라서 별도 설치 없이 Clang만 있으면 쓸 수 있다. 커버리지는 LLVM의 **SanitizerCoverage(Clang이 컴파일할 때 커버리지 수집 코드를 넣어 주는 기능)**로 얻는다.

**동작 방식**

다른 퍼저들이 "실행 파일을 반복 실행"한다면, libFuzzer는 <mark>함수 하나를 같은 프로세스 안에서 반복 호출</mark>한다. 사용자는 아래처럼 `LLVMFuzzerTestOneInput`이라는 하네스 함수만 작성하면 된다.

```cpp
extern "C" int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
    ParseImage(data, size);   // 테스트하고 싶은 함수에 퍼저 입력을 넘긴다
    return 0;
}
```

이 코드를 `-fsanitize=fuzzer,address` 옵션으로 컴파일하면 libFuzzer와 ASan이 함께 들어간 퍼저 실행 파일이 만들어진다.

**주요 특징**

- **In-process 실행**: 프로세스를 새로 만들지 않으므로 속도가 매우 빠르다.
- **새니타이저와의 결합**: ASan, UBSan, MSan과 함께 쓰는 것이 기본이다. 메모리 누수나 메모리 과다 사용(OOM)도 잘 잡아낸다.
- **코퍼스 관리 기능 내장**: `-merge=1`로 코퍼스 최소화를 하고, `-fork=N`이나 `-jobs=N`으로 여러 프로세스를 병렬 실행한다.
- **사실상 표준 하네스 형식**: `LLVMFuzzerTestOneInput` 형식은 AFL++, honggfuzz, LibAFL 등 다른 퍼저에서도 대부분 지원한다. 한 번 작성한 하네스를 여러 퍼저에서 재사용할 수 있다.

**장점**

- 진입 장벽이 가장 낮다. Clang과 짧은 하네스만 있으면 바로 시작할 수 있다.
- 라이브러리의 특정 함수(파서, 디코더 등)를 집중적으로 테스트하기 좋다.
- 하네스를 한 번만 작성하면 AFL++, honggfuzz 등 다른 퍼저로 옮겨 가기 쉽다.

**단점**

- **소스 코드가 필수**이고 Clang으로 빌드할 수 있어야 한다.
- 같은 프로세스에서 돌기 때문에 하네스를 신경 써서 작성해야 한다. 하네스가 `exit()`를 호출하거나, 전역 상태를 남겨 다음 실행에 영향을 주면 퍼징이 제대로 되지 않는다.
- 원 개발자들이 후속 엔진(Centipede)으로 옮겨 가면서, 현재는 **중요한 버그만 고치는 유지보수 모드**다. 새 기능 추가는 기대하기 어렵다.

**이럴 때 쓰면 좋다**

- 퍼징을 처음 배우거나, 라이브러리 함수를 빠르게 테스트해 보고 싶을 때
- CI(지속적 통합) 파이프라인에 짧은 퍼징 테스트를 넣고 싶을 때
- 나중에 AFL++나 LibAFL로 옮길 것을 염두에 두고 하네스를 먼저 만들 때

### <toc2>4. Jackalope — Windows·macOS 바이너리를 위한 퍼저</toc2>

> Google Project Zero 저장소에 공개된, 소스 코드 없는 바이너리를 위한 커버리지 기반 퍼저

**배경**

Google Project Zero 저장소에 공개된 퍼저다(README에는 Google 공식 제품은 아니라고 적혀 있다). AFL++나 libFuzzer 같은 범용 퍼저는 주로 Linux와 소스 코드가 있는 환경을 전제로 만들어져서, **소스가 없는 Windows·macOS 프로그램**에는 적용하기 어렵다. Jackalope는 바로 이 빈자리를 채우기 위해 만들어졌고, Linux와 Android도 지원한다.

**동작 방식**

Jackalope와 같은 개발자가 만든 **TinyInst**라는 가벼운 동적 바이너리 계측 도구로 실행 중인 바이너리에서 커버리지를 수집한다. 보통은 리버스 엔지니어링(바이너리를 분석해 내부 구조를 파악하는 것)으로 입력을 처리하는 함수를 찾은 뒤, <mark>그 함수만 반복 실행하는 퍼시스턴트 모드</mark>로 퍼징한다.

**주요 특징**

- **소스 없는 바이너리 퍼징**: 동적 바이너리 계측으로 소스 없이도 커버리지 기반 퍼징이 가능하다. Linux에서는 소스가 있을 때 SanitizerCoverage 모드도 쓸 수 있다.
- **입력 전달 방식 선택**: 입력을 파일로 넘기거나, 더 빠른 **공유 메모리**로 넘길 수 있다.
- **비교 연산 커버리지**: 비교 연산까지 커버리지로 수집하는 옵션(`-cmp_coverage`)이 있어 AFL++의 CmpLog처럼 까다로운 조건을 통과하는 데 도움을 준다.
- **분산 퍼징**: 한 컴퓨터에서 여러 스레드를 돌릴 수 있다. 서버를 하나 띄워 여러 컴퓨터(워커)의 입력, 크래시, 커버리지를 모으고 나눠 줄 수도 있다.
- **문법 기반 뮤테이션 엔진 내장**: 범용 바이너리 변형뿐 아니라 문법 기반 변형도 지원해서 스크립트 엔진 같은 타겟에도 쓸 수 있다.
- **라이브러리처럼 확장 가능**: `Fuzzer` 클래스를 상속해 뮤테이터, 계측 방식, 입력 전달 방식을 원하는 대로 바꿀 수 있다.
- **커버리지 시각화**: 수집한 커버리지를 IDA(바이너리 분석 도구) 플러그인인 Lighthouse로 열어, 어떤 코드가 실행됐는지 눈으로 확인할 수 있다.

**장점**

- 다른 퍼저로 다루기 힘든 **클로즈드 소스 Windows·macOS 프로그램**을 커버리지 기반으로 퍼징할 수 있다.
- 분산 퍼징과 문법 기반 퍼징을 기본으로 지원한다.

**단점**

- 어떤 모듈의 어떤 함수를 반복 실행할지 직접 지정해야 해서 **바이너리 분석 능력이 먼저 필요**하다.
- AFL++에 비해 사용자층과 참고 자료가 적어, 문제를 만나면 스스로 해결해야 하는 경우가 많다.
- 동적 바이너리 계측이라 소스 기반 계측보다는 느리다.

**이럴 때 쓰면 좋다**

- 소스 코드가 없는 Windows·macOS 애플리케이션이나 라이브러리를 퍼징할 때
- 여러 대의 컴퓨터로 대규모 퍼징을 하고 싶을 때

### <toc2>5. LibAFL — 나만의 퍼저를 조립하는 프레임워크</toc2>

> AFL++ 팀이 Rust로 만든, 퍼저를 부품 단위로 조립할 수 있는 라이브러리

**배경**

AFL++는 기능이 많지만 모든 기능이 하나로 뭉쳐 있는 구조라서, 새로운 연구 아이디어를 넣거나 일부만 바꾸기가 어렵다. 이 문제를 풀기 위해 AFL++ 개발진(Andrea Fioraldi, Dominik Maier 등)이 만든 것이 LibAFL이다. LibAFL은 그 자체로 완성된 퍼저가 아니라 <mark>퍼저를 만드는 재료</mark>다.

**동작 방식**

LibAFL은 퍼저를 이루는 구성 요소를 각각 부품으로 나눠 두었다. 입력 형식, 뮤테이터, 스케줄러, 피드백(커버리지 등), 실행기(executor), 결과를 판정하는 기준 등이 각각 부품이다. 사용자는 이 부품을 골라 조합하거나 직접 만든 부품으로 교체해 자신만의 퍼저를 만든다.

**주요 특징**

- **모든 부품 교체 가능**: 기본 입력 형식인 바이트 배열 대신 AST(추상 구문 트리, 코드 구조를 트리로 표현한 것) 같은 구조화된 입력을 쓰는 등 원하는 대로 바꿀 수 있다.
- **뛰어난 확장성**: **LLMP(Low Level Message Passing)**라는 자체 통신 방식 덕분에 코어 수에 거의 비례해 성능이 늘어난다. TCP로 여러 컴퓨터까지 확장할 수도 있다.
- **다양한 계측 백엔드**: SanitizerCoverage(소스 기반), Frida, QEMU(user/system 모드), TinyInst, Nyx(가상 머신 스냅숏 기반) 등 여러 방식을 지원한다.
- **넓은 플랫폼**: Windows, macOS, Linux, Android에서 동작한다. `no_std` 모드(운영체제 기능 없이 동작하는 모드)로 빌드하면 임베디드 장치나 하이퍼바이저 같은 특수한 환경에도 넣을 수 있다.
- **libFuzzer 대체 가능**: libFuzzer와 같은 방식으로 쓸 수 있는 `libafl_libfuzzer`를 제공해, 기존 libFuzzer 하네스를 그대로 쓰면서 엔진만 바꿀 수 있다.

**장점**

- 원하는 기능을 가진 퍼저를 직접 설계할 수 있어 **연구나 특수 타겟**에 가장 유연하다.
- 성능과 멀티코어 확장성이 뛰어나다.

**단점**

- 바로 실행할 수 있는 도구가 아니라서 **Rust로 퍼저를 직접 작성**해야 한다.
- 퍼징 구조와 Rust를 모두 알아야 해서 **학습 난이도가 가장 높다**.

**이럴 때 쓰면 좋다**

- 기존 퍼저로는 다루기 어려운 특수한 타겟(펌웨어, 하이퍼바이저, 독특한 입력 구조 등)을 퍼징할 때
- 새로운 퍼징 기법을 연구하거나 실험할 때

### <toc2>참고: 퍼저를 운영하는 인프라와 학습 자료</toc2>

- **OSS-Fuzz / ClusterFuzz**: 퍼저가 아니라, libFuzzer·AFL++·honggfuzz 같은 퍼징 엔진을 대규모로 돌려 오픈소스 프로젝트를 지속적으로 퍼징하는 Google의 서비스·인프라다.
- **google/fuzzing 저장소**: 퍼징 튜토리얼, 예제, 토론, 연구 제안을 모아 둔 "Fuzzing Forum" 저장소다. 퍼징을 왜 해야 하는지, 좋은 하네스의 조건, 구조 인식 퍼징 작성법, AFL 계열 퍼저 개요, 용어집, libFuzzer 튜토리얼 등을 다룬다. 퍼징을 처음 공부할 때 순서대로 읽기 좋다.

### <toc2>2. 장단점과 사용처 요약</toc2>

| 퍼저 | 장점 | 단점 | 이럴 때 |
|---|---|---|---|
| AFL++ | 기능이 가장 풍부하고 성능이 좋음, 자료가 많음 | 옵션이 많아 복잡함, 바이너리 모드는 느림 | 소스 있는 C/C++ 프로그램을 본격적으로 퍼징할 때 |
| honggfuzz | 설정이 간단, 퍼저 하나로 멀티코어 활용, 하드웨어 피드백 | 하드웨어 피드백은 Linux+Intel 한정, 생태계가 작음 | 간편하게 빠른 퍼징을 하거나 AFL++와 함께 돌릴 때 |
| libFuzzer | 진입 장벽이 가장 낮음, 하네스 재사용성 | 소스 필수, 하네스 상태 관리 필요, 유지보수 모드 | 퍼징 입문, 라이브러리 함수 테스트, CI 연동 |
| Jackalope | 클로즈드 소스 Windows·macOS 퍼징, 분산·문법 퍼징 | 바이너리 분석이 먼저 필요, 자료가 적음 | 소스 없는 Windows·macOS 프로그램을 퍼징할 때 |
| LibAFL | 무엇이든 바꿀 수 있는 유연성, 뛰어난 확장성 | Rust로 직접 작성해야 함, 학습 난이도 높음 | 특수한 타겟, 퍼징 기법 연구 |

```text
소스 코드가 있는가?
├── 있다
│   ├── 함수 단위로 빠르게 시작하고 싶다 ............ libFuzzer
│   ├── 오래, 강력하게 돌리고 싶다 ................... AFL++ (+ honggfuzz 병행)

```

# <toc>마치며</toc>

정리하면 퍼징은 <mark>대량의 이상한 입력으로 프로그램을 두드려 보는 자동화된 테스트</mark>다. 현대 퍼저 대부분은 커버리지를 피드백으로 삼아 점점 깊은 코드로 파고드는 그레이박스 방식을 쓴다. 퍼저마다 차이가 나는 부분은 크게 네 가지다.

1. **커버리지 수집**: 소스 코드가 없을 때 커버리지를 어떻게 얻는가 (컴파일 타임 계측 / 동적 계측 / 에뮬레이션 / 하드웨어)
2. **실행 속도**: 타겟을 어떻게 더 빨리 반복 실행하는가 (포크 서버 / 퍼시스턴트 모드 / in-process)
3. **조건 돌파**: 까다로운 조건을 어떻게 통과하는가 (CmpLog, laf-intel, 문법 기반 변형)
4. **확장성**: 여러 코어와 여러 컴퓨터로 어떻게 확장하는가

"가장 좋은 퍼저"는 없다. FuzzBench(Google의 퍼저 벤치마크 플랫폼)를 이용한 한 비교 연구에서도 범용 성능은 honggfuzz와 AFL++가 좋았지만, 모든 지표에서 다른 퍼저를 앞서는 퍼저는 없었다. 커버리지와 발견한 버그 수의 관계도 퍼저보다 타겟에 따라 달랐다.

결국 <mark>타겟에 소스가 있는지, 어떤 OS에서 도는지, 입력이 얼마나 구조화되어 있는지</mark>를 먼저 따져 보고 퍼저를 고르는 것이 중요하다. 실제로는 하나의 하네스를 여러 퍼저로 함께 돌려 서로의 약점을 보완하는 경우도 많다.
