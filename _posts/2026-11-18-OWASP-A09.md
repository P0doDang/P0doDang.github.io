# <toc>기록은 있었는데, 아무도 몰랐다</toc>

해킹 사고 기사를 읽다 보면 "공격자는 이미 몇 달 전부터 내부에 들어와 있었다"는 문장을 자주 보게 된다. 몇 달 동안 안에 있었는데 왜 아무도 몰랐을까? OWASP Top 10 목록을 보다가 이 질문에 가장 직접적으로 답하는 항목이 <mark>**A09. 보안 로깅 및 경보 실패**</mark>라고 생각해 주제로 골랐다.


---
# <toc>OWASP Top 10이란</toc>

**OWASP**(Open Worldwide Application Security Project)는 웹 애플리케이션 보안을 연구하고 자료를 공개하는 비영리 재단이다. 이곳에서 몇 년마다 발표하는 **OWASP Top 10**은 "지금 웹 애플리케이션에서 가장 중요한 보안 위험 10가지"를 정리한 문서로, 개발자와 보안 담당자가 공통으로 참고하는 기준처럼 쓰인다. 2025년판은 여덟 번째 판이다.

| 순위 | 항목 |
|---|---|
| A01 | 접근 제어 취약점 (Broken Access Control) |
| A02 | 보안 설정 오류 (Security Misconfiguration) |
| A03 | 소프트웨어 공급망 실패 (Software Supply Chain Failures) |
| A04 | 암호화 실패 (Cryptographic Failures) |
| A05 | 인젝션 (Injection) |
| A06 | 안전하지 않은 설계 (Insecure Design) |
| A07 | 인증 실패 (Authentication Failures) |
| A08 | 소프트웨어 또는 데이터 무결성 실패 (Software or Data Integrity Failures) |
| **A09** | **보안 로깅 및 경보 실패 (Security Logging & Alerting Failures)** |
| A10 | 예외 상황 처리 미흡 (Mishandling of Exceptional Conditions) |

다른 항목 대부분이 "공격자가 들어오는 구멍"을 다룬다면, A09은 성격이 조금 다르다. A09은 <mark>**구멍이 뚫렸다는 사실을 알아차리는 능력**</mark>에 관한 항목이다.

# <toc>로그와 경보, CCTV로 이해하기</toc>

### <toc2>로그(Log)란</toc2>

> 시스템에서 일어난 일을 시간 순서대로 적어 둔 기록

예를 들어 어떤 웹 서비스의 로그인 기록은 이렇게 생겼을 수 있다.

```text
2026-11-18 02:10:31 INFO    로그인 성공   user=kim    ip=203.0.113.10
2026-11-18 02:11:02 WARNING 로그인 실패   user=admin  ip=198.51.100.7
2026-11-18 02:11:03 WARNING 로그인 실패   user=admin  ip=198.51.100.7
2026-11-18 02:11:04 WARNING 로그인 실패   user=admin  ip=198.51.100.7
...
```

같은 IP에서 1초 간격으로 `admin` 계정 로그인 실패가 반복된다. 누군가 비밀번호를 무작위로 대입하고 있을 가능성이 높다. 로그가 없었다면 이런 시도가 있었다는 사실조차 알 수 없다.

### <toc2>로그만으로는 부족하다</toc2>

하지만 로그가 쌓이기만 하고 아무도 보지 않는다면 의미가 없다. 이 관계를 건물 보안에 빗대면 이해가 쉽다.

| 건물 보안 | 시스템 보안 | 빠지면 생기는 일 |
|---|---|---|
| CCTV 녹화 | **로깅** — 사건을 기록 | 침입이 있었는지 증거가 없다 |
| 녹화본 보관 | **로그 보관·보호** — 기록을 안전하게 저장 | 나중에 돌려 보려 해도 영상이 없다 |
| 경비원이 화면을 봄 | **모니터링** — 기록을 지켜봄 | 녹화는 됐지만 아무도 모른다 |
| 수상한 움직임에 울리는 알람 | **경보(Alerting)** — 이상 징후를 사람에게 알림 | 경비원이 졸면 놓친다 |
| 알람이 울리면 할 일을 적은 매뉴얼 | **대응 절차(플레이북)** | 알람이 울려도 무엇을 할지 모른다 |

이 중 <mark>어느 한 단계라도 빠지면, 도둑이 들어와도 한참 뒤에야 알게 된다.</mark> A09은 이 사슬의 어딘가가 끊어진 상태를 말한다.

# <toc>A09이 말하는 '실패'의 네 가지 모습</toc>

OWASP 공식 문서는 애플리케이션이 A09에 취약한 조건을 14가지로 나열한다. 하나씩 외우기보다 <mark>네 묶음으로 나누면</mark> 훨씬 이해하기 쉽다.

### <toc2>1. 남겨야 할 것을 남기지 않는다</toc2>

- 로그인 성공·실패, 고액 거래처럼 **나중에 확인해야 하는 이벤트**가 기록되지 않거나, 기록 방식이 제각각이다.
- 경고나 오류가 발생해도 로그가 없거나, 있어도 무슨 뜻인지 알 수 없을 만큼 부실하다.
- 예외 상황 자체를 시스템이 알아채지 못해 기록할 기회조차 없다.

### <toc2>2. 남기면 안 되는 방식으로 남긴다</toc2>

- 비밀번호, 주민등록번호, 인증 토큰 같은 **민감 정보가 로그에 그대로 찍힌다.** 로그는 여러 사람이 보는 경우가 많아서, 로그 자체가 유출 경로가 된다.
- 사용자 입력을 그대로 로그에 쓰다 보니 **로그 인젝션**(가짜 로그를 끼워 넣는 공격)이 가능하다. 이건 아래 로그 인젝션 파트에서 직접 코드로 확인해 본다.

### <toc2>3. 남긴 기록을 지키지 못한다</toc2>

- 로그의 **무결성**이 보호되지 않아 공격자가 흔적을 지우거나 고칠 수 있다.
- 로그가 서버 한 대에만 저장되고 백업이 없다. 그 서버가 털리거나 고장 나면 기록도 함께 사라진다.

### <toc2>4. 기록을 보고도 반응하지 못한다</toc2>

- 애플리케이션과 API 로그를 아무도 모니터링하지 않는다.
- 경보 기준이나 보고 체계가 없거나 제대로 작동하지 않아, 경보가 오래 방치된다.
- 모의해킹이나 자동 취약점 스캐너로 공격을 흉내 내도 **경보가 울리지 않는다.**
- 실시간에 가깝게 공격을 탐지하고 보고할 수 없다.
- **오탐이 너무 많아** 진짜 경보가 묻히고, SOC가 지친다.
- 경보가 울렸을 때 무엇을 해야 하는지 적은 **플레이북**이 없거나 낡았다.

4번 항목에서 "모의해킹을 해도 경보가 안 울린다"는 조건이 특히 흥미롭다. 일부러 공격을 해 봤는데도 아무 반응이 없다면, <mark>실제 공격자가 와도 마찬가지</mark>라는 뜻이다. 우리 시스템이 A09에 취약한지 확인하는 가장 직관적인 방법이기도 하다.

> 오탐과 경보 피로(Alert Fatigue)에 대해서는 [침입 탐지 및 방지 시스템(IDS/IPS)이란?](/posts/IDS-IPS/)에서도 다뤘다.

# <toc>2025년판에서 달라진 점</toc>

### <toc2>1. 이름이 바뀌었다: Monitoring → Alerting</toc2>

이 항목의 이름은 판마다 조금씩 바뀌어 왔다.

| 연도 | 순위 | 이름 |
|---|---|---|
| 2017 | A10 | Insufficient Logging & Monitoring (불충분한 로깅 및 모니터링) |
| 2021 | A09 | Security Logging and Monitoring Failures (보안 로깅 및 모니터링 실패) |
| 2025 | A09 | **Security Logging & Alerting Failures (보안 로깅 및 경보 실패)** |

2025년판에서 순위는 9위를 그대로 유지했지만, 이름의 'Monitoring'이 **'Alerting'**으로 바뀌었다. OWASP는 그 이유를 짧게 설명한다. 아무리 로그를 잘 남겨도 <mark>**경보로 이어지지 않으면 보안 사고를 찾아내는 데 거의 쓸모가 없다**</mark>는 것이다. 로그는 사람을 움직이게 만들 때 비로소 가치가 생긴다는 점을 이름에서부터 강조한 셈이다.

### <toc2>2. 데이터가 아니라 '현장의 목소리'로 뽑혔다</toc2>

OWASP Top 10은 기본적으로 실제 애플리케이션 테스트 데이터를 바탕으로 순위를 정한다. 그런데 A09은 데이터로 잡아내기가 어렵다. 다른 취약점은 "이 코드에 이런 구멍이 있다"를 찾으면 되지만, A09은 **"있어야 할 기록이 없다"**는 것을 찾아야 하기 때문이다. 없는 것을 자동 도구로 찾기는 쉽지 않다.

그래서 A09은 데이터에서는 늘 과소평가되고, 대신 **커뮤니티 설문**을 통해 목록에 들어갔다. 설문으로 선정된 것은 이번이 세 번째다. 2025년판에서 이렇게 설문으로 자리를 얻은 항목은 A03 공급망 실패와 A09 두 개뿐이다. <mark>현장의 보안 실무자들이 "데이터에 잘 안 잡혀도 이건 꼭 들어가야 한다"고 판단</mark>했다는 뜻이다.

### <toc2>3. 주요 수치</toc2>

| 항목 | 값 |
|---|---|
| 매핑된 CWE 수 | 5개 |
| 최대 발생률 | 11.33% |
| 평균 발생률 | 3.91% |
| 총 발생 건수 | 260,288건 |
| 관련 CVE 수 | 723개 |

관련 CVE가 723개로 다른 항목에 비해 적지만, OWASP는 이 항목이 **가시성**, **사고 경보**, **포렌식**에 미치는 영향이 매우 크다고 강조한다.

### <toc2>4. 매핑된 CWE</toc2>

| CWE | 이름 | 쉽게 말하면 |
|---|---|---|
| CWE-117 | Improper Output Neutralization for Logs | 로그에 쓰는 값을 제대로 처리하지 않아 로그 인젝션이 가능함 |
| CWE-221 | Information Loss or Omission | 중요한 정보가 기록 과정에서 빠짐 |
| CWE-223 | Omission of Security-relevant Information | 보안상 중요한 정보를 기록하지 않음 |
| CWE-532 | Insertion of Sensitive Information into Log File | 로그에 민감 정보를 기록함 |
| CWE-778 | Insufficient Logging | 로깅 자체가 부족함 |

# <toc>실제 사고로 보는 A09</toc>

A09은 단독으로 사고를 일으키기보다, <mark>다른 취약점으로 들어온 공격자가 **오래 머물 수 있게 만드는**</mark> 역할을 한다. 두 가지 사고를 보면 앞서 나눈 네 가지 실패가 실제로 어떤 모습인지 잘 드러난다.

### <toc2>1. Target (2013) — 경보는 울렸지만 아무도 움직이지 않았다</toc2>

> 탐지 도구도, 관제 인력도, 경보도 있었지만 대응이 없었던 사례

미국 대형 유통업체 Target은 2013년 중반, 약 160만 달러를 들여 FireEye의 악성코드 탐지 솔루션을 도입했다. 인도 방갈로르에는 24시간 이 시스템을 지켜보는 보안 팀도 두었다.

그해 11월 30일, 공격자가 결제 시스템에 카드 정보를 빼돌리는 악성코드를 설치하자 FireEye가 이를 잡아냈다. 방갈로르 팀은 경보를 미국 미니애폴리스 본사 보안팀에 전달했다. 12월 2일에는 추가 경보도 울렸다. 하지만 본사에서는 아무 조치도 하지 않았다. 게다가 악성코드를 자동으로 지우는 기능은 이미 꺼져 있었다.

결과적으로 약 **4천만 건의 카드 정보**와 **7천만 건의 개인정보**가 유출됐다.

왜 경보를 무시했을까? 당시 전문가들은 보안팀이 **하루에도 수백 건의 비슷한 경보**를 받고 있었을 가능성을 지적했다. 도입한 지 얼마 안 된 도구라 결과를 신뢰하지 못했다는 분석도 있었다.

**A09 관점**

- 4번, **기록을 보고도 반응하지 못한** 사례다.
- 빠진 것은 "경보가 울리면 누가 무엇을 한다"는 **대응 절차**, 그리고 진짜 경보를 가려낼 수 있을 만큼 **오탐을 줄이는 일**이었다.
- <mark>경보가 너무 많으면 경보가 없는 것과 같다.</mark>

### <toc2>2. Equifax (2017) — 감시 장비가 19개월 동안 멈춰 있었다</toc2>

> 감시 시스템은 있었지만, 감시 시스템이 살아 있는지는 아무도 감시하지 않았던 사례

미국 신용평가회사 Equifax는 2017년 웹 프레임워크(웹 서비스를 만들 때 쓰는 뼈대 소프트웨어) Apache Struts의 취약점을 통해 침투당했다. 약 **1억 4,550만 명**의 개인정보가 유출됐고, 공격은 약 **76일** 동안 탐지되지 않았다.

미국 하원 감독위원회 보고서는 탐지가 늦어진 핵심 원인을 짚었다. 해당 시스템의 네트워크 트래픽을 감시하던 장비가 **보안 인증서 만료로 19개월 동안 사실상 꺼져 있었던 것**이다.

이 장비는 인증서(암호화된 통신을 풀어 보기 위한 일종의 신분증)를 이용해 암호화된 트래픽 내용을 검사하고 있었다. 인증서가 만료되자 장비는 암호화된 트래픽을 들여다볼 수 없게 됐고, 공격자는 그 사이로 데이터를 빼냈다. 2017년 7월 29일 인증서를 갱신하자마자 수상한 트래픽이 바로 눈에 들어왔다. 조사 결과 Equifax에서 만료된 인증서는 300개가 넘었고, 그중 79개는 핵심 도메인을 감시하는 데 쓰이던 것이었다.

**A09 관점**

- 3번과 4번이 겹친 사례다. 감시 장비가 멈춘 사실 자체를 아무도 알아채지 못했다.
- OWASP 로깅 치트시트도 **"로깅이 멈췄을 때 이를 탐지하라"**고 권고한다.
- <mark>경보가 하나도 울리지 않는 상태는 '평화롭다'는 뜻이 아니라 '고장 났다'는 신호일 수 있다.</mark>

### <toc2>3. 두 사례의 공통점</toc2>

| 구분 | Target (2013) | Equifax (2017) |
|---|---|---|
| 있었던 것 | 탐지 솔루션, 24시간 관제 팀, 경보 | 트래픽 감시 장비 |
| 끊어진 고리 | 경보 → **사람의 대응** | 감시 장비 → **작동 여부 확인** |
| 결과 | 카드 정보 4천만 건, 개인정보 7천만 건 유출 | 1억 4,550만 명 개인정보 유출, 약 76일간 미탐지 |

두 회사 모두 **보안 도구가 없어서** 당한 것이 아니다. Target은 경보를 받았고, Equifax는 감시 장비가 있었다. 문제는 그 도구가 <mark>제대로 작동하는지, 결과를 보고 사람이 움직이는지</mark>였다. A09이 '도구'가 아니라 '실패'라는 이름을 달고 있는 이유가 여기에 있다고 생각한다.

# <toc>숫자로 보는 '들키지 않는 시간'</toc>

보안 업계에서는 공격자가 침투한 뒤 발견되기까지 걸린 시간을 **체류 시간(Dwell Time)**이라고 부른다. <mark>A09의 성패가 가장 직접적으로 드러나는 지표</mark>다.

구글 클라우드 산하 보안 기업 Mandiant가 매년 내는 M-Trends 보고서에 따르면 다음과 같다.

| 지표 | 값 | 출처 |
|---|---|---|
| 2025년 전 세계 체류 시간 중앙값 | **14일** (전년도 11일에서 증가) | M-Trends 2026 |
| 사이버 스파이 활동·북한 IT 인력 위장 취업 사례의 체류 시간 중앙값 | **122일** (약 4개월) | M-Trends 2026 |
| 조직이 **스스로 발견**한 경우 (2024년) | **10일** | M-Trends 2025 |
| **외부 기관이 알려 준** 경우 (2024년) | **26일** | M-Trends 2025 |

2025년 체류 시간이 늘어난 주된 이유는, 오래 숨어 있는 것 자체가 목적인 사이버 스파이 활동과 북한 IT 인력 위장 취업 사례였다.

마지막 두 수치가 특히 A09과 맞닿아 있다. 자체 로깅·경보 체계가 제대로 작동해 스스로 알아챈 조직은, <mark>남이 알려 줄 때까지 몰랐던 조직보다 공격자를 훨씬 빨리 쫓아냈다.</mark> 앞의 Equifax 사례에서 공격이 탐지되지 않은 기간(약 76일)은 2025년 중앙값인 14일의 5배가 넘는다.

# <toc>직접 확인해 보는 로그 인젝션 (CWE-117)</toc>

"로그에 값을 쓰는 게 왜 위험하지?"라는 의문이 들 수 있다. 간단한 파이썬 예제로 확인해 보자.

### <toc2>1. 취약한 코드</toc2>

로그인에 실패하면 사용자가 입력한 아이디를 그대로 로그에 남기는 코드다.

```python
import logging

logging.basicConfig(
    format="%(asctime)s %(levelname)s %(message)s",
    datefmt="%Y-%m-%d %H:%M:%S",
    level=logging.INFO,
)
log = logging.getLogger()

# 공격자가 아이디 입력창에 넣은 값
username = "guest\n2026-11-18 02:31:07 INFO 로그인 성공: admin"

log.warning(f"로그인 실패: {username}")
```

공격자는 아이디 안에 **줄바꿈 문자(`\n`)**를 넣고, 그 뒤에 진짜 로그처럼 보이는 문장을 덧붙였다. 실행 결과는 다음과 같다.

```text
2026-11-18 02:31:45 WARNING 로그인 실패: guest
2026-11-18 02:31:07 INFO 로그인 성공: admin
```

로그를 보는 사람 입장에서는 `admin` 계정이 정상적으로 로그인한 것처럼 보인다. 공격자가 <mark>**가짜 기록을 끼워 넣은 것**</mark>이다. 이런 식으로 수사를 엉뚱한 방향으로 돌리거나, 자신의 진짜 행동을 다른 기록 속에 묻어 버릴 수 있다.

### <toc2>2. 고친 코드</toc2>

**방법 1. 줄바꿈 문자를 눈에 보이는 문자열로 바꾼다**

```python
def sanitize(s: str) -> str:
    return s.replace("\r", "\\r").replace("\n", "\\n")

log.warning("로그인 실패: %s", sanitize(username))
```

```text
2026-11-18 02:31:45 WARNING 로그인 실패: guest\n2026-11-18 02:31:07 INFO 로그인 성공: admin
```

**방법 2. JSON 같은 구조화된 형식으로 남긴다**

값이 하나의 필드 안에 갇히기 때문에 줄바꿈이 있어도 새 기록으로 해석되지 않는다.

```python
import json
log.warning(json.dumps({"event": "login_fail", "user": username}, ensure_ascii=False))
```

```text
2026-11-18 02:31:45 WARNING {"event": "login_fail", "user": "guest\n2026-11-18 02:31:07 INFO 로그인 성공: admin"}
```

두 경우 모두 공격 시도가 **한 줄 안에 그대로 드러난다.** 가짜 기록이 사라졌을 뿐 아니라, <mark>오히려 누군가 로그를 조작하려 했다는 증거가 남는다.</mark> OWASP 로깅 치트시트는 구조화된 형식 사용, 로그에 쓰는 입력 길이 제한, 출력 형식에 맞는 인코딩을 함께 권고한다.

### <toc2>3. 참고: Log4Shell (CVE-2021-44228)</toc2>

2021년 전 세계를 떠들썩하게 만든 **Log4Shell**도 로그와 관련된 취약점이다. 자바 로깅 라이브러리 Log4j가 로그에 기록되는 문자열을 해석하는 과정에서 원격 코드 실행(공격자가 멀리서 서버에 원하는 명령을 실행시키는 것)이 가능했다. 로그에 무엇을 어떻게 쓰느냐가 단순한 기록 문제가 아니라 <mark>**공격 통로**가 될 수 있다</mark>는 것을 보여 준 사건이다.

# <toc>어떻게 막을까</toc>

OWASP 공식 문서와 로깅 치트시트의 권고를 앞의 네 가지 실패에 맞춰 정리하면 다음과 같다.

### <toc2>1. 무엇을 남길까</toc2>

- 로그인 성공과 실패, 접근 제어 실패(권한 없는 페이지나 데이터에 접근하려다 막힌 경우), 서버 측 입력값 검증 실패
- 세션 이상 (조작된 세션 ID, 검증에 실패한 토큰 등)
- 관리자 기능 사용, 권한 변경, 설정 변경, 민감 데이터 접근, 데이터 내보내기
- 모든 보안 통제의 **성공과 실패 둘 다**

그리고 수상한 계정을 가려낼 수 있도록 <mark>**누가 했는지에 대한 맥락**을 충분히 함께 남겨야 한다.</mark>

### <toc2>2. 어떻게 남길까</toc2>

좋은 로그 한 줄에는 **언제, 어디서, 누가, 무엇을**이 들어가야 한다.

| 요소 | 예시 |
|---|---|
| 언제 (When) | 국제 표준 형식의 시각, 관련 이벤트를 묶는 요청 ID |
| 어디서 (Where) | 애플리케이션 이름·버전, 서버, 접근 경로(URL) |
| 누가 (Who) | 출발지 IP, 사용자 ID |
| 무엇을 (What) | 이벤트 종류, 심각도, 결과(성공/실패), 설명 |

반대로 **남기면 안 되는 것**도 있다.

- 비밀번호, 세션 ID, 액세스 토큰, 암호화 키, DB 접속 정보
- 카드·계좌 번호, 주민등록번호 같은 민감 개인정보

이런 값은 기록하지 않거나 **마스킹·해시** 처리해야 한다. 로그 관리 도구가 쉽게 분석할 수 있는 형식(JSON 등)으로 남기고, 앞의 로그 인젝션 예제처럼 입력값은 인코딩해서 쓴다.

### <toc2>3. 어떻게 지킬까</toc2>

- 로그를 애플리케이션 서버에만 두지 말고 **중앙 로그 시스템(SIEM 등)으로 모은다.**
- 한 번 쓰면 고칠 수 없는 **추가 전용(Append-only) 저장소**나 읽기 전용 매체에 보관해 변조를 막는다.
- 로그에 접근한 기록도 남기고, 읽기 권한은 최소한으로 둔다.
- 여러 서버의 **시간을 동기화**한다. 시각이 어긋나면 사건의 순서를 재구성할 수 없다.
- **포렌식 분석이 가능할 만큼 충분한 기간** 보관한다.

> SIEM(Wazuh)의 탐지 룰을 직접 분석하고 개선해 본 과정은 [SIEM Upgrade, Wazuh 탐지 룰 개선하기](/posts/SIEM-Upgrade-Wazuh/)에 정리해 두었다.

### <toc2>4. 어떻게 반응할까</toc2>

- 수상한 행동에 대한 **경보 기준과 보고 체계(에스컬레이션)**를 정한다.
- 경보마다 "울리면 누가, 무엇을 하는지" 적은 **플레이북**을 만든다.
- **허니토큰**을 심어 둔다. 정상 사용자는 건드릴 일이 없으니 <mark>오탐이 거의 없는 경보</mark>를 만들 수 있다.
- 행위 분석이나 AI를 활용해 **오탐을 줄인다.** Target 사례처럼 경보가 너무 많으면 진짜 경보가 묻힌다.
- **로깅이 멈추거나 경보가 장기간 없을 때도 경보가 울리게** 한다. Equifax 사례를 막을 수 있었던 장치다.
- 모의해킹을 할 때 **경보가 실제로 울리는지**도 함께 점검한다.
- NIST SP 800-61(미국 국립표준기술연구소가 낸 보안 사고 대응 지침) 같은 **사고 대응 계획**을 갖추고, 개발자도 공격 징후를 알아보고 보고할 수 있도록 교육한다.

### <toc2>5. 한눈에 정리</toc2>

| 실패 유형 | 대표 증상 | 핵심 대응 |
|---|---|---|
| 1. 남기지 않는다 | 로그인 실패·권한 변경 기록 없음 | 보안 이벤트의 성공·실패를 모두 기록 |
| 2. 잘못 남긴다 | 민감 정보 노출, 로그 인젝션 | 마스킹·해시, 구조화된 로그, 입력값 인코딩 |
| 3. 지키지 못한다 | 흔적 삭제, 서버와 함께 로그 소실 | 중앙 수집, Append-only 저장, 시간 동기화 |
| 4. 반응하지 못한다 | 경보 방치, 오탐 홍수, 감시 장비 정지 | 플레이북, 오탐 튜닝, 허니토큰, 로깅 중단 경보 |

# <toc>마치며</toc>

<!-- 마무리: 직접 수정 예정 -->

A09을 공부하면서 가장 크게 바뀐 생각은, 보안이 "막는 것"만으로 끝나지 않는다는 점이다. 다른 Top 10 항목이 공격자가 들어오는 문을 다룬다면, A09은 <mark>**문이 열렸을 때 그 사실을 얼마나 빨리 알 수 있는가**</mark>를 다룬다. 공격을 완벽하게 막을 수는 없기 때문에, 피해의 크기를 결정하는 것은 결국 탐지 속도다.

두 사고를 정리하며 공통적으로 느낀 것은, 문제가 **도구의 부재가 아니라 운영의 실패**였다는 점이다. 경보는 울렸지만 무시됐고, 감시 장비는 있었지만 꺼져 있었다. 2025년판에서 이름이 'Monitoring'에서 'Alerting'으로 바뀐 것도 같은 맥락이라고 생각한다. 기록하는 것보다 <mark>**기록을 보고 움직이게 만드는 것**</mark>이 더 어렵고, 더 중요하다.
