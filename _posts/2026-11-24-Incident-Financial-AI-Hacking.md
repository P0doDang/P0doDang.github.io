# <toc>들어가며</toc>

2026년 9월 말부터 신한·KB국민·하나은행을 시작으로 국내 금융회사들이 잇따라 해킹을 당했다. 11월 5일 기준 **37개사, 약 47.3만 건**의 정보가 유출된 것으로 집계됐고, 공격 인프라에서는 AI 기반 자율 침투 테스트 도구 **ARTEX**의 흔적이 발견됐다.

뉴스에서는 주로 "AI 해킹"이라는 이름으로 다뤄졌지만, 자료를 정리해 보니 공격자가 실제로 노린 것은 <mark>**오래전부터 있던 기본적인 약점**</mark>이었다. 이 글에서는 사고의 경과와 공격 방식, 근본 원인과 대응을 순서대로 정리해 본다.

# <toc>용어 정리</toc>

뒤에서 계속 나오는 용어들이다. 필요할 때 펼쳐서 확인하면 된다.

<details markdown="1">
<summary>공격 관련 용어</summary>

| 용어 | 설명 |
|---|---|
| 침투 테스트 (모의해킹) | 허가를 받고 실제 공격자처럼 시스템을 공격해 보며 취약점을 찾는 점검. 원래는 방어를 위한 활동이다 |
| LLM | 대규모 언어 모델(Large Language Model). 대량의 텍스트로 학습해 문장을 이해하고 만들어 내는 AI 모델로, ChatGPT나 Claude가 대표적이다 |
| AI 에이전트 | 목표를 주면 스스로 작업을 쪼개고, 도구를 실행하고, 그 결과를 보고 다음 행동을 정하는 AI 프로그램 |
| 무작위 대입 (Brute Force) | 가능한 값을 계속 바꿔 넣어 보며 맞는 값을 찾아내는 공격 |
| 크리덴셜 스터핑 (Credential Stuffing) | 다른 곳에서 유출된 아이디·비밀번호 조합을 다른 사이트에 그대로 넣어 보는 공격. 여러 사이트에서 같은 비밀번호를 쓰는 습관을 노린다 |
| 인증 우회 | 로그인이나 휴대폰 본인 확인 같은 절차를 거치지 않고 기능을 쓸 수 있게 되는 것 |
| API | 프로그램끼리 데이터를 주고받는 창구. 앱 화면 뒤에서 서버에 "이 고객의 정보를 달라"고 요청하는 통로다 |
| VPS | 가상 사설 서버(Virtual Private Server). 클라우드 업체에서 빌려 쓰는 서버로, 공격자가 위치를 숨기기 위해 여러 나라의 VPS를 거쳐 공격하는 경우가 많다 |

</details>

<details markdown="1">
<summary>방어·관리 관련 용어</summary>

| 용어 | 설명 |
|---|---|
| 공격 표면 (Attack Surface) | 외부에서 공격할 수 있는 지점 전체. 인터넷에 노출된 서버, 웹 페이지, API 등이 모두 포함된다 |
| 공격표면관리 (ASM) | Attack Surface Management. 외부에 노출된 자산을 계속 찾아내 목록으로 관리하고 취약점을 점검하는 활동 |
| 섀도 IT (Shadow IT) | 조직이 존재를 모르거나 보안 관리 대상에서 빠져 있는 시스템·서비스 |
| 인증 / 인가 | 인증(Authentication)은 "이 사람이 누구인지" 확인하는 것, 인가(Authorization)는 "이 사람이 이 데이터를 볼 권한이 있는지" 확인하는 것. 로그인에 성공했더라도 남의 정보를 조회할 수 있다면 인가가 빠진 것이다 |
| 접근통제 | 허용된 사람과 기기만 시스템에 접근할 수 있도록 막는 것 |
| MFA | 다중요소 인증(Multi-Factor Authentication). 비밀번호에 OTP나 휴대폰 인증을 더하는 것처럼 두 가지 이상의 수단으로 본인을 확인하는 방식 |
| 제로 트러스트 (Zero Trust) | 한 번 인증했다고 계속 믿지 않고, 접근할 때마다 신원과 권한을 다시 확인하는 보안 원칙 |
| EOS | End of Support. 제조사의 기술지원이 끝나 더 이상 보안 패치가 나오지 않는 제품 |
| 관제 | 보안 장비의 경보와 로그를 실시간으로 지켜보며 공격을 탐지하고 대응하는 업무 |
| 전자금융기반시설 | 전자금융거래에 쓰이는 정보처리시스템과 통신망. 전자금융거래법에 따라 정기적인 취약점 분석·평가를 받아야 하는 등 더 엄격하게 관리된다 |
| CI (연계정보) | 주민등록번호를 대신해 온라인에서 같은 사람임을 식별하는 값. 본인확인기관이 주민등록번호를 암호화해 만들며, 한 사람당 하나의 값이 나온다 |
| 침해지표 (IoC) | Indicator of Compromise. 공격에 쓰인 IP 주소, 도메인, 파일 해시처럼 공격 흔적을 찾는 단서 |
| FIRST | 금융감독원의 통합 관제 시스템. 금융회사들이 공격 정보를 공유하는 창구로 쓰인다 |

</details>

# <toc>공격은 어떻게 이루어졌나</toc>

### <toc2>1. 전체 구조: 정문이 아니라 옆문</toc2>

> 보안이 강한 핵심 뱅킹 대신, 상대적으로 허술한 주변부 시스템을 노린 공격

```text
[공격자] ── 여러 나라의 VPS 경유 ──> [ARTEX 등 자동화 도구]
                                       │  외부에 노출된 서비스·API를 스캔
                                       ▼
 ┌────────────────────────── 금융회사 ──────────────────────────┐
 │  [인터넷·모바일뱅킹]        ← 보안이 강함, 침해 확인 안 됨       │
 │  [대출모집인용 조회 서비스]  ← 본인 확인 우회 → 고객 정보 조회    │
 │  [직원용 업무지원 시스템]    ← 접근통제 누락 → 고객·직원 정보     │
 │  [홈페이지]                ← 알려진 취약점 → 악성코드 → 로그 탈취 │
 └─────────────────────────────────────────────────────────────┘
```

공격자는 대출모집인·직원·외주 인력이 쓰는 주변부 시스템을 노렸다. SK쉴더스는 이를 <mark>**잠긴 정문 대신 열려 있는 옆문을 찾은 것**</mark>에 비유했다. 금융당국도 인터넷·모바일뱅킹 같은 고객용 서비스에는 영향이나 금전 피해가 없는 것으로 파악했다.

### <toc2>2. 금융당국의 3개 유형 분류 (10월 4일)</toc2>

| 유형 | 확인된 문제 |
|---|---|
| 정보조회 서비스 | 본인 확인 절차가 누락된 사례 |
| 직원 업무지원 서비스 | 모바일 단말기 접근통제 누락, 권한 없이 접근할 수 있는 웹 취약점 |
| 홈페이지 서비스 | 이미 알려진 보안 취약점으로 악성코드를 설치한 뒤, 고객 정보가 담긴 로그 파일을 탈취한 사례 |

아래 신한은행 사례는 정보조회 서비스 유형, KB국민은행 사례는 직원 업무지원 서비스 유형과 가깝다. 다만 당국이 각 은행 사고를 어느 유형으로 분류했는지 공식적으로 밝히지는 않았다.

### <toc2>3. 신한은행: 대출모집인용 간편조회 서비스</toc2>

- **공격 대상**: 대출모집인이 자신이 접수한 대출의 처리 현황을 확인할 때 쓰는 'M신한' 모바일 웹의 간편조회 서비스. 고객용 앱인 신한 슈퍼SOL과는 별개의 서비스다.
- **수법**: 공격자는 고객번호 같은 입력값에 무작위 값을 넣어 보면서 서비스 조회와 휴대폰 본인 확인을 우회하려 했다. 이후 대출 신청 결과 조회 등 6개 서비스에 집중해 개인정보를 빼냈다. 이 서비스는 <mark>인터넷·모바일뱅킹보다 가벼운 인증</mark>을 쓰고 있었다.
- **크리덴셜 스터핑 여부**: 초기 보도에서는 모집인의 아이디·비밀번호가 크리덴셜 스터핑으로 뚫렸다는 설명이 나왔다. 하지만 이후 사고 보고 내용은 무작위 값 입력에 가까워, 전형적인 크리덴셜 스터핑으로 단정하기 어렵다. 구체적인 취약점 내용은 공개되지 않았다.
- **피해**: 고객 25,729명. 고객명, 고객번호, 연락처, 연소득, 대출 한도, 신청 상품, 금리 등 대출 신청 정보가 유출됐고, 이 중 주민등록번호 66건과 CI 97건이 포함됐다.

### <toc2>4. KB국민은행: 직원용 모바일 업무지원시스템</toc2>

- **공격 대상**: 기업금융 담당자(RM)와 프라이빗뱅커(PB)가 쓰는 직원용 모바일 업무지원시스템 'RM 에이전트'와 'PB 에이전트'
- **수법**: 개별 공격 요청이나 취약점의 기술적 내용은 공개되지 않았다. 공격 IP는 계속 바뀌었지만 다른 은행을 공격한 IP와 거의 같았다.
- **피해**: 총 119명(고객 99명, 임직원 20명), 개인정보 153건. 처음에는 고객 119명으로 발표됐다가 이후 정정됐다.

### <toc2>5. ARTEX: AI 자율 침투 테스트 도구</toc2>

> 깃허브에 오픈소스로 공개된 LLM 기반 자율 침투 테스트 시스템

ARTEX는 바이두가 연 AI 에이전트 공방 대회에서 수상한 프로젝트로 알려졌고, 처음부터 악성코드로 만들어진 것은 아니다. 하지만 소스코드가 공개되어 있어 <mark>공격자도 방어자도 내려받아 쓸 수 있다.</mark>

#### 동작 구조

| 구성 | 역할 |
|---|---|
| Planner | 목표를 하위 작업으로 나누고 다음 행동을 결정한다 |
| Worker (여러 개) | 명령 실행, 웹 요청 전송 등 실제 테스트를 수행하고, 찾아낸 자산·취약점·결과를 기록한다 |
| 작업 기록 | 이전 작업 내용을 남겨, 긴 작업에서도 앞서 찾은 정보를 잃거나 실패한 시도를 반복하지 않게 한다 |
| 외부 LLM 연결 | 판단과 실행을 위해 외부 LLM을 호출한다 |

기존 자동화 스캐너가 정해진 대상을 반복 점검하는 것과 달리, ARTEX는 **앞 단계의 결과를 보고 다음 목표를 고르며** 공격 경로를 넓혀 간다. 보안업체 에브스핀이 테스트 환경에서 실험한 결과, ARTEX는 브라우저 없이 API를 직접 호출해 <mark>6번의 작업 주기, 22초 만에</mark> 정보조회 기능의 목표에 도달했다.

#### 이번 사고와 연결된 근거

| 출처 | 시점 | 내용 |
|---|---|---|
| 지니언스 | 10월 2일 | 여러 국내 기관 공격에 쓰인 웹 서버의 HTML 제목에서 중국어로 'ARTEX 자율 침투 테스트 콘솔'이라는 문자열 발견 |
| 금융보안원 | 10월 3~4일 | 신한은행 로그와 공격 IP에서 ARTEX 관련 흔적 확인. 국민·신한·하나·부산은행에서 같은 공격 IP와 같은 문자열 발견 |
| 크라우드스트라이크 | 10월 7일 | 공격자가 관리하는 서버의 외부 노출 폴더에서 ARTEX 설정 파일과 AI 코딩 도구(Claude Code)의 작업 기록 확보. 홍콩 서버를 주 거점으로 두고 별도 서버에서 ARTEX를 실행했으며, 이 서버가 국내 금융권 공격에 쓰였을 가능성이 높다고 평가 |

#### 그래도 확정은 아니다

금융당국과 금융보안원은 수법을 보면 AI를 활용한 것으로 추정되지만 **확정은 아니라는 입장**이다. 당국 관계자도 AI가 사람 개입 없이 스스로 공격한 것이 아니라 <mark>해커가 AI 도구를 이용한 것</mark>이라고 선을 그었다. 엔키화이트햇은 ARTEX가 사람의 개입을 전제로 설계되어 숙련된 해커가 쓸 때 가장 효과적이라고 평가했다. 개별 침해에서 ARTEX가 정확히 어떤 역할을 했는지는 아직 수사 중이다.

# <toc>근본 원인</toc>

### <toc2>1. 주변부 시스템의 인증·인가 누락</toc2>

가장 직접적인 원인은 대출모집인·직원·외주 인력이 쓰는 시스템에서 **본인 확인과 권한 확인이 제대로 이루어지지 않았다**는 점이다. 고객용 뱅킹은 강하게 보호하면서, <mark>같은 고객 정보를 조회할 수 있는 주변 시스템은 상대적으로 가벼운 인증만 쓰고 있었다.</mark>

금융위원회가 10월 14일 발표한 555개 금융회사 점검 결과에서도 대외 시스템의 인증·인가 누락과 중요 서비스의 MFA 미도입이 주요 미흡 사항으로 지적됐다.

### <toc2>2. 공격 표면을 모르고 있었다</toc2>

공격자가 찾아낸 시스템은 회사 입장에서는 관리 우선순위가 낮거나 존재 자체를 잘 파악하지 못한 **섀도 IT**에 가까웠다. 특히 KB국민은행의 직원용 업무지원시스템은 전자금융기반시설로 분류되지 않고 은행 자체 점검 대상으로 관리되어 온 것으로 보도됐다. 법정 취약점 분석·평가의 범위가 명확하지 않으면, 이런 주변부 시스템은 점검에서 빠지기 쉽다.

### <toc2>3. 필요 이상의 개인정보를 보관·조회하고 있었다</toc2>

금융위원회는 10월 4일 사고 원인으로 대출모집인·위탁업체 같은 외부 인력과 임직원이 쓰는 시스템을 지목하면서, 이런 시스템에서 **개인신용정보가 불필요하게 보관·조회**되고 있었다고 밝혔다. 대출모집인이 처리 현황을 확인하는 데 고객의 주민등록번호나 연소득까지 보여 줄 필요가 있었는지 따져 볼 지점이다.

### <toc2>4. 기본 보안 관리의 공백</toc2>

10월 14일 점검 결과 555개사 중 130개사가 일부 항목에서 미흡하다고 보고했다. 주요 미흡 사항은 다음과 같다.

- 최신 보안 패치 미적용
- 기술지원이 끝난(EOS) 시스템 관리 부족
- 24시간 실시간 관제 체계 미구축
- 공격 표면 관리 부족 (대외 시스템 인증·인가 누락, 중요 서비스 MFA 미도입)

미흡 사항은 주로 전자금융업과 온투업에 몰려 있었다.

### <toc2>5. AI는 원인이 아니라 증폭기</toc2>

AI가 새로운 취약점을 만든 것은 아니다. 공격자가 노린 것은 인증 누락, 알려진 취약점, 접근통제 누락처럼 **원래부터 있던 약점**이다. SK쉴더스도 <mark>AI는 새 취약점을 만드는 기술이 아니라 공격을 키우는 도구</mark>라고 정리했다. AI는 취약한 서비스를 찾고 반복 공격을 대량으로 시도하는 속도를 높여, 짧은 기간에 여러 금융회사를 동시에 뚫는 결과를 만들었다.

반대로 다중인증 체계를 갖췄거나 알려진 취약점을 미리 보완한 금융회사는 같은 공격을 받고도 침해를 막아냈다.

# <toc>보완이 미흡했던 부분</toc>

### <toc2>1. 경고가 있었는데도 막지 못했다</toc2>

- 금감원은 사고 직전인 8월 24일, 9월 4일, 9월 15일 세 차례에 걸쳐 외부 노출 시스템의 위험 등을 담은 보안 유의사항을 금융회사에 보냈다.
- 2026년 상반기에도 iM뱅크와 바로저축은행에서 해킹 공격이 포착된 것으로 보도됐다.
- 신한은행은 2024년 금감원 요청으로 본인 확인 서비스의 인증 우회 취약점을 점검하고 조치했지만, 이번 사고를 막지 못했다. 당시 점검이 이번에 뚫린 서비스까지 포함했는지는 알려지지 않았다.

점검과 경고가 있었다는 것은 <mark>"몰라서 못 막은" 사고가 아니라는 뜻</mark>이다. 점검이 특정 시스템에만 한정되고, 비슷한 구조의 다른 서비스로 확대 적용되지 않은 것이 문제로 보인다.

특히 KB국민은행은 공격이 시작됐을 때 이를 일상적인 이상 트래픽으로 보고 해당 IP만 차단한 것으로 국감에서 지적됐다. 공격자는 IP를 계속 바꾸었기 때문에, <mark>IP 단위 차단은 공격을 잠시 늦출 뿐 막지는 못한다.</mark> 신한은행도 IP를 차단하자 공격자가 IP와 수법을 바꿔 2차 공격을 이어 갔다.

### <toc2>3. 연 1회 점검과 모호한 점검 범위</toc2>

기존 제도에서 금융회사는 외부 기관으로부터 연 1회 이상 취약점 점검을 받아 당국에 제출해 왔다. 하지만 다음과 같은 한계가 지적됐다.

1. 위협이 빨라지는 속도에 비해 점검 주기가 길다.
2. 의무 점검 범위가 명시되지 않아 주변부 시스템까지 꼼꼼히 점검하기 어렵다.
3. 점검에서 문제가 나와도 보완하지 않으면 강제할 수단이 마땅치 않다.

AI 도구는 쉬지 않고 외부 노출 자산을 스캔한다. 1년에 한 번 하는 점검으로는 그 사이에 새로 생기거나 바뀐 시스템의 취약점을 따라잡기 어렵다.

### <toc2>4. 피해 규모가 계속 늘어났다</toc2>

피해 기관과 유출 건수는 10월 14일 16개사 약 10만 건에서 11월 5일 37개사 약 47.3만 건으로 늘었다. 이는 공격이 계속됐다기보다, **공유된 공격 IP로 각 회사가 뒤늦게 자체 점검을 하면서 이미 일어난 침해를 발견한 결과**에 가깝다. 사고가 공개된 뒤에야 자신이 공격당했다는 사실을 아는 회사가 많았다는 점에서, 평소의 탐지 체계가 충분하지 않았다고 볼 수 있다.

### <toc2>5. 보안 투자</toc2>

신한은행의 2026년 정보보호 예산은 약 405억 원으로 5대 은행 중 가장 적었고, 전년 대비 약 10.4% 줄었다. IT 예산 대비 비중도 9.1%로 5대 은행 중 가장 낮았다. 다만 예산 감소와 이번 사고 사이의 직접적인 인과관계가 확인된 것은 아니다.
