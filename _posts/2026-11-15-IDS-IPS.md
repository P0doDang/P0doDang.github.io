# <toc>왜 IDS/IPS가 필요한가</toc>

방화벽은 주로 IP 주소, 포트, 프로토콜 같은 **헤더 정보**를 기준으로 트래픽을 허용하거나 차단한다. 예를 들어 "외부에서 80/443 포트로 들어오는 트래픽은 허용"이라는 정책이 있다면, 그 안에 SQL Injection 페이로드가 들어 있더라도 방화벽은 정상 트래픽으로 보고 통과시킨다.

즉, 방화벽은 <mark>**누가, 어디로** 들어오는지는 보지만 **무엇을** 들고 들어오는지는 잘 보지 못한다.</mark> 허용된 경로를 타고 들어오는 공격, 내부에서 발생하는 이상 행위, 이미 침투한 공격자의 활동은 방화벽만으로 확인하기 어렵다. 이 빈틈을 메우기 위해 패킷의 내용(페이로드)과 행위를 분석하는 IDS/IPS가 사용된다.

| 구분 | 방화벽 | IDS | IPS |
|---|---|---|---|
| 주 목적 | 접근 통제 | 침입 탐지 | 침입 탐지 + 차단 |
| 분석 대상 | 주로 헤더(IP, Port, Protocol) | 헤더 + 페이로드 + 행위 | 헤더 + 페이로드 + 행위 |
| 동작 | 정책에 따라 허용/거부 | 탐지 후 경보 | 탐지 후 실시간 차단 |

# <toc>용어 정리</toc>

뒤에서 계속 나오는 용어들이다. 필요할 때 펼쳐서 확인하면 된다.

<details markdown="1">
<summary>배치 관련 용어</summary>

| 용어 | 설명 |
|---|---|
| 인라인(In-line) | 장비가 트래픽이 지나가는 **경로 위에 직접** 놓이는 방식. 모든 트래픽이 장비를 거쳐 가므로 차단이 가능하다 |
| 아웃오브밴드(Out-of-band) | 원본 트래픽 경로에서 벗어나, 트래픽의 **사본**만 받아 분석하는 방식. 차단은 못 하지만 서비스에 영향을 주지 않는다 |
| SPAN (미러링 포트) | 스위치의 특정 포트로 지나가는 트래픽을 복사해 다른 포트로 보내 주는 기능 |
| TAP | 회선 중간에 설치해 트래픽을 물리적으로 복사해 주는 장비. SPAN보다 패킷 손실이 적다 |
| DMZ | 외부에 공개되는 서버(웹, 메일 등)를 내부망과 분리해 두는 중간 구간 |
| 내부 확산(Lateral Movement) | 내부망에 들어온 공격자가 다른 시스템으로 옮겨 가며 권한을 넓혀 가는 행위 |

</details>

<details markdown="1">
<summary>연동 시스템 관련 용어</summary>

| 용어 | 설명 |
|---|---|
| SIEM | 여러 장비의 로그를 한곳에 모아 **상관 분석**하고 경보를 띄우는 보안 관제 시스템 |
| SOAR | 보안 경보에 대한 대응 절차를 **자동화**하는 시스템. 예: 특정 경보가 뜨면 방화벽에 IP 차단 정책 자동 추가 |
| EDR | 엔드포인트(PC, 서버)의 행위를 감시하고 탐지·조사·대응까지 하는 시스템 |
| NDR | 네트워크 트래픽을 기반으로 위협을 탐지하고 대응하는 시스템 |
| NGFW | 차세대 방화벽. 기존 방화벽에 애플리케이션 식별, IPS 등의 기능을 통합한 장비 |

</details>

# <toc>IDS(Intrusion Detection System)</toc>

### <toc2>정의</toc2>

IDS는 네트워크 트래픽이나 시스템 활동을 모니터링하여 악의적인 행위나 정책 위반을 <mark>**탐지하고 알리는** 시스템</mark>이다. 핵심은 "탐지"와 "경보"이며, 직접 트래픽을 막지는 않는다.

### <toc2>구성 요소</toc2>

| 구성 요소 | 역할 |
|---|---|
| 센서(Sensor) | 네트워크 패킷이나 호스트 로그 등 원시 데이터를 수집 |
| 분석 엔진(Analyzer) | 수집된 데이터를 룰·프로파일과 비교하여 침입 여부 판단 |
| 관리 콘솔(Console) | 탐지 결과 확인, 정책 설정, 경보 관리 |
| 저장소(Database/Log) | 이벤트와 로그를 저장하여 사후 분석에 활용 |

### <toc2>동작 과정</toc2>

```text
[데이터 수집] → [필터링·정규화] → [분석/탐지] → [경보·보고]
```

1. **데이터 수집**: 네트워크 패킷(미러링 포트, TAP)이나 호스트의 시스템 로그, 파일 변경 내역 등을 수집한다.
2. **필터링·정규화**: 분석에 불필요한 데이터를 걸러내고, 단편화된 패킷을 재조합하거나 인코딩을 해제하는 등 분석 가능한 형태로 만든다.
3. **분석/탐지**: 시그니처 비교, 이상 행위 분석 등을 통해 침입 여부를 판단한다.
4. **경보·보고**: 침입으로 판단되면 관리자에게 알리고 로그를 남긴다. 이후 대응은 관리자 또는 연동된 시스템(SIEM, SOAR 등)이 맡는다.

# <toc>탐지 방식</toc>

IDS/IPS의 성능은 결국 <mark>"무엇을 공격으로 판단하느냐"</mark>에 달려 있다. 대표적인 탐지 방식은 세 가지다.

### <toc2>1. 시그니처 기반 탐지 (Signature-based / Misuse Detection)</toc2>

> 이미 알려진 공격의 패턴(시그니처)과 트래픽을 비교하는 방식

공격 패턴을 데이터베이스로 만들어 두고, 들어오는 트래픽과 비교한다. 백신의 패턴 매칭과 비슷하다.

- **ex)** 페이로드에 `' OR 1=1 --` 같은 문자열이 포함되어 있으면 SQL Injection으로 판단

**장점**

- 알려진 공격에 대한 탐지 정확도가 높고 오탐이 적다.
- 어떤 룰에 걸렸는지 명확해 분석이 쉽다.

**단점**

- 시그니처가 없는 신종 공격, 제로데이 공격은 탐지하지 못한다.
- 시그니처를 지속적으로 업데이트해야 하며, 패턴을 조금만 변형해도 우회될 수 있다.

### <toc2>2. 이상 탐지 (Anomaly-based / Behavior-based Detection)</toc2>

> 평소의 정상 행위를 기준선으로 삼고, 여기서 크게 벗어나는 행위를 공격으로 판단하는 방식

정상 행위를 학습할 때는 주로 통계적 기법이나 머신러닝을 사용하고, 평소보다 많은 대역폭을 사용하는 프로세스나 일반적으로 닫혀 있는 포트를 여는 디바이스와 같은 비정상적 편차를 표시한다.

- **ex)** 평소 시간당 100건 수준이던 로그인 시도가 갑자기 10,000건으로 증가, 새벽 시간대에 대량의 외부 전송 발생

**장점**

- 시그니처가 없는 신종 공격이나 제로데이 공격도 탐지할 가능성이 있다.

**단점**

- 정상적인 변화(이벤트로 인한 트래픽 급증 등)도 이상으로 판단하므로 <mark>**오탐이 많다**.</mark>
- 기준선을 학습하는 기간이 필요하고, 학습 기간에 이미 공격이 섞여 있으면 그 공격을 정상으로 학습할 가능성이 있다.

### <toc2>3. 상태 기반 프로토콜 분석 (Stateful Protocol Analysis)</toc2>

> 프로토콜 표준이 정의한 정상 동작을 기준으로, 표준에서 벗어나는 행위를 탐지하는 방식

각 프로토콜의 상태 흐름을 추적하며 비정상적인 동작이나 변칙적인 상태 전환을 찾아낸다.

- **ex)** 인증이 끝나지 않은 FTP 세션에서 인증 이후에만 가능한 명령이 실행됨, 비정상적으로 긴 HTTP 헤더

**장점**

- 프로토콜 수준의 비정상 행위를 정밀하게 탐지할 수 있다.

**단점**

- 세션 상태를 추적해야 하므로 자원 소모가 크다.
- 표준을 지키면서 이루어지는 공격은 탐지하기 어렵다.

### <toc2>4. 탐지 방식 비교</toc2>

| 구분 | 시그니처 기반 | 이상 탐지 | 상태 기반 프로토콜 분석 |
|---|---|---|---|
| 기준 | 알려진 공격 패턴 | 정상 행위 기준선 | 프로토콜 표준 |
| 신종 공격 탐지 | 어려움 | 가능 | 일부 가능 |
| 오탐(False Positive) | 낮음 | 높음 | 중간 |
| 관리 부담 | 시그니처 업데이트 | 기준선 학습·튜닝 | 프로토콜별 모델 유지 |

실제 제품은 한 가지 방식만 쓰기보다 <mark>여러 방식을 섞은 형태</mark>가 많다.

### <toc2>5. 오탐과 미탐</toc2>

탐지 시스템을 평가할 때는 다음 네 가지 경우를 함께 봐야 한다.

| | 실제 공격 | 실제 정상 |
|---|---|---|
| **공격으로 탐지** | True Positive (정탐) | False Positive (오탐) |
| **정상으로 판단** | False Negative (미탐) | True Negative(무탐/정상) |

- **오탐(False Positive)**: 정상 트래픽을 공격으로 판단하는 것. IDS에서는 경보 피로(Alert Fatigue)를, IPS에서는 정상 서비스 차단을 유발한다.
- **미탐(False Negative)**: 실제 공격을 놓치는 것. (가장 위험한 경우)

룰을 엄격하게 할수록 미탐은 줄지만 오탐이 늘고, 느슨하게 할수록 그 반대가 된다. 그래서 <mark>IDS/IPS 운영할 때는 이 균형을 맞추는 작업이 필요하다.</mark>

# <toc2>IDS의 유형</toc2>

### <toc3>1. NIDS (Network-based IDS, 네트워크 침입 탐지 시스템)</toc3>

> 네트워크 구간에 설치되어 해당 구간을 지나는 패킷을 분석하는 IDS

스위치의 미러링 포트(SPAN)나 네트워크 TAP을 통해 트래픽 사본을 받아 분석한다.

**장점**

- 하나의 센서로 네트워크 구간 전체를 감시할 수 있다.
- 트래픽 사본을 분석하므로 네트워크 성능에 영향을 주지 않는다.

**단점**

- 암호화된 트래픽(HTTPS 등)의 내용은 볼 수 없다.
- 호스트 내부에서 일어나는 일(로컬 권한 상승, 파일 변조 등)은 탐지할 수 없다.
- 대용량 트래픽 환경에서는 패킷을 놓칠 수 있다.

### <toc3>2. HIDS (Host-based IDS, 호스트 침입 탐지 시스템)</toc3>

> 개별 서버나 PC에 에이전트 형태로 설치되어 해당 호스트를 감시하는 IDS

시스템 로그, 시스템 콜, 파일 무결성, 프로세스, 레지스트리 변경 등을 감시한다.

**장점**

- 호스트 내부 행위를 정밀하게 볼 수 있다.
- 복호화된 이후의 데이터를 분석하므로 암호화 트래픽 문제에서 비교적 자유롭다.
- 공격의 성공 여부를 확인하기 쉽다.

**단점**

- 감시할 호스트마다 설치·관리해야 한다.
- 호스트 자원을 사용하며, 공격자가 호스트를 장악하면 HIDS 자체가 무력화되거나 로그가 조작될 수 있다.

### <toc3>3. NIDS vs HIDS</toc3>

| 구분 | NIDS | HIDS |
|---|---|---|
| 설치 위치 | 네트워크 구간 | 개별 호스트 |
| 분석 대상 | 네트워크 패킷 | 로그, 파일, 프로세스, 시스템 콜 |
| 감시 범위 | 넓음 (구간 전체) | 좁음 (설치된 호스트) |
| 암호화 트래픽 | 내용 분석 어려움 | 복호화 이후 분석 가능 |
| 내부 행위 탐지 | 어려움 | 가능 |
| 관리 부담 | 상대적으로 적음 | 호스트 수에 비례 |

두 방식은 <mark>서로의 약점을 보완하므로</mark>, 실제 환경에서는 함께 사용하는 경우가 많다.

# <toc>IPS(Intrusion Prevention System)</toc>

### <toc2>정의</toc2>

IPS는 IDS의 탐지 기능에 <mark>**실시간 차단 기능**을 더한 시스템</mark>이다. 트래픽이 지나가는 경로 위에 직접 위치(인라인, In-line)하여, 공격으로 판단된 트래픽을 목적지에 도달하기 전에 막는다.

### <toc2>대응 동작</toc2>

IPS는 공격을 탐지했을 때 다음과 같은 동작을 수행할 수 있다.

- **패킷 폐기(Drop)**: 악성 패킷을 버린다.
- **세션 종료(Reset)**: TCP RST 패킷을 보내 연결을 끊는다.
- **출발지 차단(Block)**: 공격 IP를 일정 시간 동안 차단한다.
- **트래픽 정규화/수정**: 악성 부분을 제거하거나 비정상 패킷을 정상 형태로 바꿔 전달한다.
- **경보 및 로깅**: IDS와 마찬가지로 기록을 남기고 관리자에게 알린다.

### <toc2>IPS의 유형</toc2>

| 유형 | 설명 |
|---|---|
| NIPS (Network-based IPS) | 네트워크 경로에 인라인으로 배치되어 구간 트래픽을 검사·차단 |
| HIPS (Host-based IPS) | 호스트에 설치되어 악성 프로세스 실행, 파일·레지스트리 변조 등을 차단 |
| WIPS (Wireless IPS) | 무선 구간을 감시하여 비인가 AP(Rogue AP), 무선 공격 등을 탐지·차단 |
| NBA (Network Behavior Analysis) | 트래픽 흐름(Flow) 통계를 분석하여 DDoS, 웜 확산, 비정상 통신 등을 탐지 |

### <toc2>Fail-Open과 Fail-Closed</toc2>

IPS는 트래픽 경로 위에 있기 때문에 <mark>IPS 장비가 장애를 일으키면 네트워크 전체가 영향을 받는다.</mark> 이때의 동작 방식을 미리 정해 두어야 한다.

- **Fail-Open**: 장애 시 검사 없이 트래픽을 그대로 통과시킨다. 서비스 가용성은 유지되지만 그동안 보안 공백이 생긴다.
- **Fail-Closed**: 장애 시 모든 트래픽을 차단한다. 보안은 유지되지만 서비스가 중단된다.

서비스 특성에 따라 가용성과 보안 중 무엇을 우선할지 선택해야 하며, 일반적으로 바이패스(Bypass) 장치나 이중화 구성으로 이 문제를 완화한다.

# <toc>배치 구조</toc>

```text
[Internet] ── [Router] ── [Firewall] ── [IPS(인라인)] ── [Switch] ── [내부 서버/PC]
                                                            │
                                                       (SPAN/TAP)
                                                            │
                                                        [IDS 센서]
                                                            │
                                                     [관리 콘솔/SIEM]
```

- **IPS**는 트래픽이 반드시 거쳐 가는 경로에 **인라인**으로 배치된다. 보통 방화벽 뒤에 두어, 방화벽이 걸러낸 트래픽을 한 번 더 정밀 검사한다.
- **IDS**는 스위치의 미러링 포트나 TAP을 통해 트래픽 **사본**을 받는 **아웃오브밴드(Out-of-band)** 방식으로 배치된다. 원본 트래픽 흐름에는 관여하지 않는다.
- 외부와 내부 사이뿐 아니라 DMZ 구간, 내부망 주요 구간에도 센서를 두어 내부 확산(Lateral Movement)을 감시하기도 한다.

# <toc>IDS와 IPS 한눈에 비교하기</toc>

### <toc2>1. 특징 비교</toc2>

| 구분 | IDS | IPS |
|---|---|---|
| 주 기능 | 탐지 및 경보 | 탐지 및 실시간 차단 |
| 배치 방식 | Out-of-band (미러링/TAP) | In-line (트래픽 경로 위) |
| 대응 방식 | 수동적(Passive) – 관리자가 사후 대응 | 능동적(Active) – 자동 차단 |
| 네트워크 성능 영향 | 거의 없음 | 지연(Latency) 발생 가능 |
| 장애 시 영향 | 탐지만 중단, 서비스 영향 없음 | 서비스 중단 또는 보안 공백(Fail-Open/Closed) |
| 오탐의 영향 | 불필요한 경보 증가 | 정상 서비스 차단 |
| 적합한 상황 | 가시성 확보, 포렌식·사후 분석, 룰 검증 | 알려진 공격의 즉각적인 차단 |

한 줄로 정리하면, <mark>**IDS는 "CCTV"**, **IPS는 "출입문 앞의 경비원"**</mark>에 가깝다. CCTV는 모든 상황을 기록하고 이상이 있으면 알려 주지만 직접 막지는 않는다. 경비원은 수상한 사람을 그 자리에서 막을 수 있지만, 잘못 판단하면 정상적인 방문자까지 돌려보내게 된다.

실제로는 둘 중 하나만 선택하기보다, 같은 엔진을 IDS 모드와 IPS 모드로 나누어 운영하는 경우가 많다. 새로운 룰은 먼저 탐지 모드로 적용해 오탐 여부를 검증한 뒤, 충분히 안정적이라고 판단되면 차단 모드로 전환하는 방식이다.

### <toc2>2. 장단점 정리</toc2>

**IDS**

| 장점 | 단점 |
|---|---|
| 네트워크 성능과 가용성에 영향을 주지 않음 | 탐지만 할 뿐 직접 차단하지 못함 |
| 오탐이 발생해도 서비스가 중단되지 않음 | 경보가 많으면 분석 인력의 부담이 커짐 |
| 전체 트래픽에 대한 가시성 확보, 사후 분석에 유용 | 대응이 사람에 의존하므로 대응 시점이 늦어질 수 있음 |

**IPS**

| 장점 | 단점 |
|---|---|
| 공격을 실시간으로 자동 차단 | 오탐 시 정상 서비스가 차단됨 |
| 대응 시간 단축, 운영 인력 부담 감소 | 인라인 처리로 인한 지연, 처리 성능 한계 |
| 알려진 취약점 공격에 대한 가상 패치(Virtual Patching) 효과 | 장비 장애가 곧 네트워크 장애가 될 수 있음 |

### <toc2>3. 공통 한계</toc2>

- **암호화 트래픽**: TLS로 암호화된 트래픽은 페이로드를 볼 수 없다. 이를 해결하려면 별도의 복호화 장비(SSL 가시화)나 HIDS/EDR을 함께 사용해야 한다.
- **회피 기법**: 패킷 단편화, 인코딩 변형, 타이밍 조작 등으로 탐지를 우회할 수 있다.
- **운영 부담**: 룰 업데이트와 튜닝을 지속적으로 해야 한다. <mark>도입만 하고 관리하지 않으면 효과가 크게 떨어진다.</mark>

# <toc>활용 방법과 대표 도구</toc>

### <toc2>1. 대표적인 오픈소스 도구</toc2>

| 도구 | 유형 | 특징 |
|---|---|---|
| Snort | NIDS/NIPS | 가장 널리 알려진 시그니처 기반 IDS/IPS. 룰 문법이 사실상 표준처럼 쓰임 |
| Suricata | NIDS/NIPS | 멀티스레드 구조로 고성능 처리에 유리, Snort 룰과 호환성 높음 |
| Zeek (구 Bro) | NIDS(네트워크 분석) | 시그니처보다 트래픽 메타데이터·로그 생성과 스크립트 기반 분석에 강점 |
| OSSEC / Wazuh | HIDS | 로그 분석, 파일 무결성 검사, 루트킷 탐지 등 호스트 기반 감시 |
| Security Onion | 통합 플랫폼 | Suricata, Zeek 등을 묶어 제공하는 보안 모니터링 배포판 |

> Wazuh 탐지 룰을 직접 분석하고 개선해 본 과정은 [SIEM Upgrade, Wazuh 탐지 룰 개선하기](/posts/SIEM-Upgrade-Wazuh/)에 정리해 두었다.

### <toc2>2. Snort 룰 구조</toc2>

Snort/Suricata의 룰은 **헤더**와 **옵션**으로 구성된다.

```text
alert tcp $EXTERNAL_NET any -> $HOME_NET 22 (msg:"Possible SSH Brute Force"; flow:to_server; flags:S; detection_filter:track by_src, count 5, seconds 60; sid:1000001; rev:1;)
```

| 구성 | 값 | 의미 |
|---|---|---|
| Action | `alert` | 탐지 시 경보 발생 (IPS 모드에서는 `drop`, `reject` 등으로 차단) |
| Protocol | `tcp` | 검사할 프로토콜 |
| 출발지 | `$EXTERNAL_NET any` | 외부 네트워크의 모든 포트 |
| 방향 | `->` | 출발지에서 목적지 방향 |
| 목적지 | `$HOME_NET 22` | 내부 네트워크의 22번(SSH) 포트 |
| msg | `"Possible SSH Brute Force"` | 경보 메시지 |
| flow | `to_server` | 서버 방향 트래픽만 검사 |
| flags | `S` | SYN 패킷(연결 시도) |
| detection_filter | `track by_src, count 5, seconds 60` | 같은 출발지에서 60초 안에 5회를 넘으면 탐지 |
| sid / rev | `1000001` / `1` | 룰 고유 ID와 버전 (사용자 정의 룰은 보통 1,000,000 이상 사용) |

같은 룰에서 action만 `alert`에서 `drop`으로 바꾸고 엔진을 인라인 모드로 운영하면 IDS 룰이 IPS 룰이 된다. <mark>IDS와 IPS의 차이가 "탐지 로직"보다는 "배치와 대응 방식"에 있다</mark>는 점을 잘 보여 주는 부분이다.

### <toc2>3. 운영 환경에서의 활용</toc2>

- **SIEM 연동**: IDS/IPS 경보를 SIEM으로 보내 방화벽, 서버, EDR 로그와 함께 상관 분석한다. 단일 경보만으로는 판단하기 어려운 공격도 여러 로그를 엮으면 흐름이 보인다.
- **가상 패치**: 취약점이 공개되었지만 당장 패치를 적용하기 어려운 시스템 앞에 해당 공격을 막는 IPS 룰을 먼저 적용해 시간을 번다.
- **단계적 적용**: 새 룰은 IDS(탐지) 모드로 먼저 운영하며 오탐을 확인하고, 검증된 룰만 IPS(차단) 모드로 전환한다.
- **사고 대응·포렌식**: IDS 로그와 패킷 캡처는 침해사고 발생 시 공격 경로와 시점을 재구성하는 근거 자료가 된다.

# <toc>최근 흐름</toc>

IDS/IPS는 독립 장비로 쓰이기보다 <mark>다른 보안 기술과 결합되는 방향</mark>으로 변하고 있다.

- **NGFW 통합**: 차세대 방화벽(NGFW)에 IPS 기능이 기본 탑재되어, 방화벽과 IPS의 경계가 흐려지고 있다.
- **NDR / EDR**: 네트워크 쪽은 NDR(Network Detection and Response), 호스트 쪽은 EDR(Endpoint Detection and Response)로 발전하며 탐지뿐 아니라 조사·대응까지 포괄하는 형태가 되었다. 각각 NIDS와 HIDS의 확장으로 볼 수 있다.
- **머신러닝 기반 탐지**: 이상 탐지의 고질적인 문제였던 오탐을 줄이기 위해 머신러닝을 활용한 행위 분석이 확대되고 있다.
- **암호화 트래픽 분석**: 페이로드를 복호화하지 않고 TLS 핸드셰이크 정보, 패킷 크기·주기 같은 메타데이터로 악성 통신을 식별하려는 시도가 이어지고 있다.

# <toc>마치며</toc>

정리하면 IDS는 <mark>트래픽을 지켜보고 알려 주는 시스템</mark>이고, IPS는 <mark>트래픽 경로 위에서 직접 막는 시스템</mark>이다.

1. **IDS**: 트래픽 사본을 받아 분석하는 Out-of-band 방식으로, 공격을 탐지하고 경보를 보낸다. 서비스에 영향이 없는 대신 대응은 사람이 맡는다.
2. **IPS**: 트래픽 경로 위에 인라인으로 배치되어, 탐지한 공격을 실시간으로 차단한다. 대응이 빠른 대신 오탐과 장애가 곧 서비스 영향으로 이어진다.
3. **탐지 방식**: **시그니처 기반**(알려진 공격에 정확, 신종 공격에 취약), **이상 탐지**(신종 공격 탐지 가능, 오탐 많음), **상태 기반 프로토콜 분석**(프로토콜 표준 위반 탐지)으로 나뉘며, 실제로는 이를 섞어 사용한다.
4. **설치 위치**: **네트워크 기반**(NIDS/NIPS)과 **호스트 기반**(HIDS/HIPS)으로 나뉘고, 두 방식은 서로의 약점을 보완한다.

결국 IDS와 IPS의 차이는 탐지 로직보다 **배치 방식과 대응 방식**에 있다. 어느 쪽을 쓰든 <mark>오탐과 미탐의 균형을 맞추는 지속적인 튜닝</mark>이 운영의 핵심이다.
