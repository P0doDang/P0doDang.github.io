# 프로젝트 소개

건국대 SecurityFact, 서울여대 SWING, 세종대 S! 세 보안 동아리가 연합해 **3S** 팀으로 2026년 4월부터 10월까지 6개월 동안 오픈소스 vcflib을 퍼징했다. AFL++로 크래시를 만들고, 그 크래시를 분석해 취약점을 찾는 것이 이번 프로젝트의 흐름이었다.

vcflib 빌드부터 크래시 파일 생성까지는 팀이 함께 진행했다. 그중 <mark>최종적으로 성공한 퍼징 과정과 방법은 내가 주도했다</mark>.

- **기간**: 2026년 4월 ~ 10월 (6개월)
- **팀**: 세 동아리 연합, 매주 정기 미팅
- **함께 한 일**: vcflib 빌드부터 크래시 파일 생성까지
- **내가 주도한 일**: AFL++ 빌드 환경 구성과 vcflib 의존성 설치, 빌드 오류 해결, QEMU 모드 퍼징으로 크래시 파일 생성, 크래시 유효성 검사

### 사용 기술과 환경

- **퍼저**: AFL++ (QEMU 모드)
- **빌드**: LLVM 16, CMake, Makefile, Docker
- **분석**: gdb, bash 검증 스크립트, AddressSanitizer
- **대상**: vcflib (VCF 파일을 처리하는 C++ 라이브러리와 유틸리티 모음)

# 왜 이 프로젝트를 했나

목표는 <mark>공부에서 끝내지 않고 실제 오픈소스에서 취약점이라는 결과물을 내는 것</mark>이었다. 처음에는 Windows 대상도 고려했지만, 6개월 안에 결과를 내기는 어렵다고 판단했다. 프로젝트 기간과 난이도를 함께 따져 본 끝에 Linux 환경에서 진행하기로 했다.


---
# 진행 과정

### 1. 사전 학습

퍼징은 처음이라 먼저 Fuzzing 101 실습으로 AFL++ 사용법과 크래시 분석 흐름을 익혔다. 계측 방식 선택, ASAN 리포트 읽기, 병렬 퍼징 같은 기초를 여기서 배웠고, 이후 vcflib 퍼징에 그대로 활용했다.

### 2. 대상 선정과 병행 빌드

C/C++로 작성되었고 알려진 취약점이 적은 오픈소스를 우선해 후보를 조사했다. 퍼징은 빌드에 실패하면 시간이 크게 낭비된다. 그래서 모두가 하나에 매달리지 않고 <mark>두 갈래로 나눠 서로 다른 대상의 빌드를 시도했다</mark>. 그중 vcflib 빌드가 성공해서 이후로는 vcflib으로 진행했다.

### 3. 의존성과 빌드 실패 해결

AFL++는 LLVM 16을 설치한 뒤 소스에서 빌드했다. vcflib은 htslib, tabixpp, WFA2-lib, pybind11을 먼저 직접 빌드해 설치해야 빌드할 수 있었고, 실패한 지점마다 하나씩 직접 고쳐 나갔다.

1. **tabixpp**: Makefile이 htslib 경로를 찾지 못해서 `sed`로 경로를 바꾸고 Makefile을 수정했다.
2. **vcflib**: `CMakeLists.txt`에서 htslib과 WFA2-lib 경로를 환경에 맞게 고쳤다.
3. **ctest**: 10번 테스트가 실패했는데, WFA2-lib의 테스트 스크립트를 수정해 해결했다.

### 4. afl-clang-lto 대신 QEMU 모드

처음에는 afl-clang-lto로 소스를 계측해 빌드하려 했지만 끝내 해결하지 못했다. 그래서 방향을 바꿔, AFL++의 <mark>QEMU 모드로 이미 빌드된 바이너리를 소스 계측 없이 그대로 퍼징</mark>했다.

입력은 헤더와 변이 한 줄만 담은 최소한의 VCF 파일을 직접 만들어 시작했고, 이 방식으로 vcfallelicprimitives에서 크래시 파일이 생성되었다.

```bash
afl-fuzz -Q -i input -o output -- ./vcfallelicprimitives @@
```

### 5. 크래시 유효성 검사

생성된 크래시 파일 57개를 대상 프로그램에 일괄 실행해서 실제로 비정상 종료하는지 확인하는 스크립트를 작성했다. 결과는 <mark>57개 모두 재현되는 유효한 크래시</mark>였다.


---
# 결과

vcfallelicprimitives에서 크래시 파일 57개를 확보했고, 모두 재현을 확인했다. 팀 전체로 크래시를 분석한 결과, 다음 세 가지 문제를 확인했다.

1. **vcfallelicprimitives**: 비어 있는 ref나 alt 값을 처리하지 못하고 예외가 처리되지 않아 비정상 종료됨
2. **vcfecho**: 헤더에 필수 필드가 없을 때 힙 버퍼 오버플로(읽기)가 발생함
3. **vcfflatten**: 두 벡터의 크기가 달라 힙 버퍼 오버플로가 발생함

vcfuniq는 약 2일 20시간 퍼징했지만 크래시가 나오지 않았다. 퍼징 과정과 결과는 프로젝트 막바지에 발표로 공유했다.

다만 이번 프로젝트의 결과는 취약점 발견까지이고, 아직 공식 보고는 하지 않았다. 따라서 <mark>위 문제들은 vcflib 관리자가 확인한 것은 아니다</mark>.

# 아쉬운 점

- 취약점 발견에서 멈췄고, 공식 보고(이슈, PR, CVE 신청)까지 하지 못했다.
- 내가 만든 크래시 57개는 같은 원인일 가능성이 높은데, 중복을 제거해 고유한 크래시를 추리지 못했다.
- 크래시 검증을 스크립트 한 가지 방법으로만 했다.
- afl-clang-lto 계측 빌드를 해결하지 못해, 소스 계측 방식보다 정보가 적은 QEMU 모드에 의존했다.
- 발표 자료를 따로 남기지 않았다.

# 배운 점

퍼징은 <mark>빌드와 환경 구성이 시간의 대부분을 차지했다</mark>. 대상을 정하기 전에 빌드 가능성부터 확인하고, 여러 갈래로 병행해서 시도한 것이 시간 낭비를 줄여 주었다.

또 한 가지 방식이 막혔을 때 QEMU 모드처럼 다른 방식으로 바꾸면 길이 열린다는 것도 경험했다. 그리고 크래시는 개수보다 <mark>중복 제거와 원인 분석이 중요하다</mark>는 점도 배웠다.

## 마치며

이번 프로젝트는 취약점 발견에서 멈췄지만, 다음에는 아래 순서로 이어 가려 한다.

1. **크래시 중복 제거**: afl-tmin과 스택 해시로 고유한 크래시를 추린다.
2. **공식 보고와 패치 제안**: 확인한 취약점을 vcflib에 보고하고 패치를 제안한다.
3. **퍼징 성능 개선**: persistent 모드 하네스를 작성해 속도를 높인다.
4. **Windows 대상 퍼징**: 이번에 미뤘던 Windows 대상에 도전한다.
