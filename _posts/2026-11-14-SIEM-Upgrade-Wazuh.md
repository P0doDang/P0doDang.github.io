# 프로젝트 소개

세종대 보안 동아리 S!에서 4명이 한 팀으로 2025년 5월부터 8월까지 오픈소스 SIEM인 **Wazuh**의 기본 탐지 룰을 분석하고 개선하는 프로젝트를 진행했다. 레벨 10~15 룰을 분류·선별해 분석한 뒤 개선 룰을 적용하고, 개선 전후의 탐지 결과를 비교하는 것이 이번 프로젝트의 흐름이었다.

- **기간**: 2025년 5월 ~ 8월 (약 4개월)
- **팀**: 4명
- **내가 맡은 일**: Wazuh 룰셋의 분류와 선별, 선별한 룰의 분석. 이 분석이 이후 룰 개선과 검증의 기준이 되었다.

### 사용 기술과 환경

- **SIEM**: Wazuh (`wazuh-logtest`, `local_rules.xml`, 디코더)
- **분석**: Python(pandas), MITRE ATT&CK
- **로그 대상**: Apache, Nginx, sshd, F5
- **환경**: 개인 서버에서 Wazuh 운영


---
# 왜 이 프로젝트를 했나

Splunk 같은 상용 SIEM은 구축 비용과 라이선스 부담이 크다. 그래서 <mark>「오픈소스 기반 SIEM 시스템 구축 및 적용 연구」</mark>라는 과제로 비용 효율적인 대안을 만드는 것을 목표로 시작했다.

진행하면서 범위를 좁혀, 기본 룰이 놓치는 공격(미탐)을 잡고 잘못 잡는 경우(오탐)를 줄이는 <mark>탐지 룰 개선</mark>에 집중하기로 했다.


---
# 진행 과정

### 1. 분석할 룰 고르기

Wazuh 룰셋 전체 4,490개를 추출해 Python으로 분류했다. 레벨 0이거나 `noalert`인 룰은 알림을 내지 않고 하위 룰의 부모 역할만 하기 때문에, 이를 기준으로 나눴다.

1. **탐지용 룰**: 3,817개
2. **템플릿용 룰**: 673개 (레벨 0 또는 `noalert`)

그다음 프로젝트 결과를 위해 레벨 10~15 위주로 기준을 세웠다. 그룹별로 50개씩 1차 선별한 뒤, 레벨 10~15 룰 90개를 <mark>공격 유형, 대상 OS, 위험도, 재현 가능성</mark>으로 분석표에 정리했다.

정리해 보니 최고 레벨인 15 룰 32개 중 29개가 Windows·Office 365 대상이었다. 우리 환경에서는 재현하기 어려웠기 때문에, 재현할 수 있는 웹·SSH·F5 룰 31개를 개선 후보로 정했다.

### 2. 룰 개선

룰마다 부모 룰 체인과 조건을 분석해 탐지의 빈틈을 찾았다. 개선은 기본 룰 파일을 직접 고치지 않고 `local_rules.xml`에 모았고, 개선한 룰에는 `Upgrade_` 그룹을 붙여 기본 룰과 구분했다. 최종적으로 <mark>52개 룰(기존 룰 덮어쓰기 7개 포함)</mark>을 작성했다.

주로 사용한 개선 방향은 다음과 같다.

- **탐지 문자열 추가**: 기존 룰이 놓치는 로그 문자열을 추가
- **반복 탐지**: 같은 IP에서 짧은 시간 안에 반복되면 경보
- **실패 후 성공**: 인증 실패가 반복된 뒤 로그인에 성공하면 경보
- **동일 계정·다른 IP**: IP를 바꿔 가며 한 계정을 노리는 분산 공격 탐지
- **취약 계정**: root, admin 같은 계정 대상 시도 탐지
- **해외 접속**: 국외에서 들어온 로그인 시도 탐지
- **SQLi·XSS 대표 룰**: 공격 기법별 대표 룰을 새로 작성

### 3. 개선 룰이 트리거되지 않는 문제

같은 테스트 로그를 개선 전후로 `wazuh-logtest`에 넣어 비교했다. SSH는 같은 룰 ID가 걸렸지만 그룹이 `Upgrade_` 그룹으로 바뀌어 덮어쓴 룰이 적용된 것을 확인했다. 그런데 <mark>새로 만든 SQLi·XSS 대표 룰은 걸리지 않았다</mark>.

프로젝트가 끝난 뒤 `local_rules.xml`을 Wazuh 공식 룰 문법과 하나씩 대조해 원인을 다시 분석했다.

1. **여러 `<match>`가 하나로 이어 붙여짐**: `<match>`를 여러 개 쓰면 OR가 아니라 값이 하나로 이어 붙여진다. 수십 개의 패턴이 하나의 긴 문자열이 되어 실제 로그와 일치할 수 없었다.
2. **`<match>`에 정규식 사용**: `<match>`는 기본이 단순 매칭인데 정규식 문법을 써서 의도대로 해석되지 않았다.
3. **빈도 조건을 문자열로 작성**: `frequency`, `timeframe` 속성 대신 조건을 문자열로 적은 룰이 있었다.
4. **체이닝·조건 누락**: "실패 후 성공" 룰이 엉뚱한 룰 ID를 참조하거나, 해외 접속 룰에 국가 조건이 빠져 있었다.

예를 들어 1번은 아래처럼 패턴을 나눠 쓴 것이 문제였고, 패턴을 `|`로 묶은 `<match>` 하나로 쓰거나 `<regex>`를 써야 했다.

```xml
<!-- 의도: 둘 중 하나라도 있으면 탐지 -->
<match>union select</match>
<match>or 1=1</match>

<!-- 수정: 하나의 <match>에 OR로 묶기 -->
<match>union select|or 1=1</match>
```

환경 때문에 걸리지 않는 경우도 있었다. 92208 룰은 Windows Sysmon 이벤트를 받는 부모 룰이 먼저 걸려야 동작해서, Linux 환경에서는 비슷한 로그를 넣어도 트리거되지 않았다.

# 결과

- **룰셋 분류**: 4,490개를 탐지용 3,817개, 템플릿용 673개로 분류
- **룰 분석표**: 레벨 10~15 룰 90개 정리, 개선 후보 31개 선정
- **룰별 분석 문서**: 11개 룰의 부모 룰 체인, 조건, 개선안 정리
- **개선 룰셋**: `local_rules.xml`에 52개 룰 작성 (기존 룰 덮어쓰기 7개 포함)
- **트리거 실패 원인 분석**: 룰별 원인과 수정 방향 정리

개선 전후 `wazuh-logtest` 비교 결과는 다음과 같다.

| 테스트 | 판정 |
|---|---|
| SSH 익스플로잇 | 개선 룰 적용 확인 |
| SQLi | 부분 개선 |
| XSS | 부분 개선 |
| Apache DoS | 변화 없음 |
| 악성 URI | 수정 필요 |

다만 개선한 룰이 실제로 <mark>오탐을 줄이고 미탐을 정탐으로 바꿨는지 검증하는 테스트는 진행하지 못했다</mark>.

# 아쉬운 점

- 일정이 조금씩 밀려 마지막에 개선 효과를 검증할 시간이 부족했고, 룰 개선까지만 하고 마무리를 잘 짓지 못했다.
- 룰을 한꺼번에 작성한 뒤 테스트해서, 트리거되지 않는 문제를 프로젝트 기간 안에 고치지 못했다.
- 검증이 로그 한 줄짜리 테스트 위주였다.
- 그룹별 침투 시나리오를 구상하지 못했다.


---
# 배운 점

룰은 혼자 동작하지 않았다. 로그가 디코더에서 필드로 제대로 나뉘어야 하고, 부모 룰이 먼저 걸려야 한다. 그래서 <mark>룰은 디코더·로그 형식, 체이닝 구조와 함께 봐야 한다</mark>는 것을 배웠다.

또 비슷해 보이는 문법도 Wazuh에서는 다르게 동작했다. 그럴듯한 예시를 그대로 쓰기 전에 <mark>공식 문서와 `wazuh-logtest`로 먼저 확인해야 한다</mark>는 점을 느꼈다. 그리고 조건과 체이닝을 늘리면 정확도는 오르지만 탐지가 늦어지는, 탐지 정확도와 탐지 시간의 트레이드오프도 배웠다.

## 마치며

이번 프로젝트는 룰 개선에서 멈췄지만, 다음에는 아래 순서로 이어 가려 한다.

1. **룰 단위 테스트**: 룰을 추가할 때마다 `wazuh-logtest`로 확인하며 작성한다.
2. **A/B 테스트**: 개선 전후 룰셋에 같은 트래픽을 보내 오탐률·미탐률을 수치로 비교한다.
3. **공격 시나리오 검증**: 실제 공격 트래픽 기반 시나리오로 빈도·시간 조건 룰을 검증한다.
4. **Windows·Sysmon 환경**: 이번에 빠진 레벨 15 룰을 Windows 환경에서 검증한다.
