# <toc>들어가며</toc>

2026년 5월 말, CJ ENM 계열 국내 OTT 서비스 티빙(TVING)에서 **3,954만 개 계정**의 정보가 유출됐다. 활성 계정뿐 아니라 휴면·탈퇴·테스트 계정까지 전부였다.

이 사고는 정교한 신기술보다 <mark>**기본적인 관리 실패가 사슬처럼 이어진 사례**</mark>에 가깝다. 개발자 한 명의 접속키로 개발환경에 들어간 공격자가, 소스코드 안에 그대로 적혀 있던 운영환경 접속키를 손에 넣으면서 피해가 운영 데이터 전체로 번졌다. 게다가 같은 취약점은 2024년 모의해킹에서 이미 발견된 것이었다. 이 글에서는 키 하나가 어떻게 전체 유출로 이어졌는지 정리한다.

# <toc>용어 정리</toc>

뒤에서 계속 나오는 용어들이다. 필요할 때 펼쳐서 확인하면 된다.

<details markdown="1">
<summary>키와 개발 환경 관련 용어</summary>

| 용어 | 설명 |
|---|---|
| 접속키 (Access Key) | 사람이 아이디·비밀번호로 로그인하는 대신, 프로그램이 클라우드나 서버에 접속할 때 쓰는 일종의 비밀번호. 이 키만 있으면 키에 부여된 권한을 그대로 쓸 수 있다 |
| 개발환경 / 운영환경 | 개발환경은 개발자가 코드를 만들고 테스트하는 공간, 운영환경은 실제 사용자가 쓰는 서비스가 돌아가는 공간이다. 운영환경에는 실제 고객 데이터가 있다 |
| 하드코딩 (Hardcoding) | 값을 설정 파일이나 별도 저장소에서 불러오지 않고 소스코드 안에 직접 적어 넣는 것. 접속키를 하드코딩하면 소스코드를 본 사람은 누구나 키를 얻는다 |
| 환경변수 | 프로그램 실행 환경에 저장해 두고 코드에서 불러 쓰는 설정값. 코드와 분리되지만, 암호화하지 않으면 그대로 노출될 수 있다 |
| 평문 | 암호화하지 않은 원래 그대로의 데이터 |
| 시크릿 관리 (Secret Management) | 접속키, 비밀번호, 인증서 같은 비밀 정보를 코드와 분리해 전용 저장소(예: AWS Secrets Manager, HashiCorp Vault)에 보관하고, 발급·사용·교체·폐기를 체계적으로 관리하는 것 |
| AWS | 아마존의 클라우드 서비스. 서버, 데이터베이스, 저장소 등을 빌려 쓸 수 있다 |
| 가상 서버 (인스턴스) | 클라우드에서 필요할 때 만들었다가 지울 수 있는 서버. 권한만 있으면 몇 분 만에 만들 수 있다 |

</details>

<details markdown="1">
<summary>보안 관리 관련 용어</summary>

| 용어 | 설명 |
|---|---|

| 모의해킹 | 허가를 받고 실제 공격자처럼 시스템을 공격해 취약점을 찾는 점검 |
| ISMS | 정보보호 관리체계 인증. 기업이 정보보호를 위한 관리 체계를 갖추고 운영하는지 국가가 심사해 인증하는 제도 |
| 이상 행위 탐지 | 평소와 다른 접근, 대량 조회, 비정상적인 데이터 이동 등을 찾아내 경보를 울리는 것 |
| 제로 트러스트 | 내부 사용자라도 믿지 않고, 접근할 때마다 신원과 권한을 다시 확인하는 보안 원칙 |
| 민관합동조사단 | 큰 침해사고가 나면 과학기술정보통신부가 정부와 민간 전문가로 꾸리는 조사단. 원인과 피해 규모를 조사해 발표한다 |

</details>

<summary>개인정보 관련 용어</summary>

| 용어 | 설명 |
|---|---|
| CI (연계정보) | 주민등록번호를 대신해 온라인에서 같은 사람임을 식별하는 값. 본인확인기관이 주민등록번호를 암호화해 만들며, 주민등록번호 하나당 하나의 CI가 나온다. 여러 서비스가 같은 CI를 쓰기 때문에, 유출되면 다른 곳에서 유출된 정보와 연결하는 기준이 될 수 있다 |

| 일방향 암호화 (해시) | 원래 값으로 되돌릴 수 없게 변환하는 방식. 비밀번호 저장에 쓴다 |
| 양방향 암호화 / 복호화 | 키가 있으면 원래 값으로 되돌릴 수 있는 암호화 방식. 되돌리는 것을 복호화라고 한다. 키를 데이터와 함께 잃어버리면 암호화한 의미가 없어진다 |

</details>

# <toc>공격은 어떻게 이루어졌나</toc>

### <toc2>1. 공격 경로</toc2>

> 개발환경 키 하나가 운영환경 전체로 이어지는 사슬

```text
[개발자의 개발환경 접속키]  ← 탈취 경로 미확인
          │ ① 개발환경 접속 (5/29)
          ▼
[개발환경] ── 모든 개발자가 전체 프로젝트에 접근 가능
          │ ② 개발 프로젝트 361건 전부 반출 (30.35GB)
          ▼
[소스코드·환경변수 속 운영환경 접속키 43개 + 평문 DB 접속 정보]
          │ ③ 이 중 2개 사용
          ├──────────────────────────────┐
          ▼ (5/30)                        ▼ (5/31)
[운영 DB에서 대량 추출 시도]          [AWS에 가상 서버 생성]
 CPU 100% → 차단, "장애"로 처리          → 이용자 데이터 복사
                                          → 약 24GB 해외 전송
                                          → 가상 서버 삭제
```

개발환경 접속키 자체는 고객 데이터에 바로 접근할 수 있는 키가 아니었다. 그러나 개발환경에 있는 소스코드 안에 운영환경으로 들어갈 수 있는 키가 그대로 적혀 있었고, 모든 개발자가 모든 프로젝트를 볼 수 있었기 때문에 <mark>**키 하나로 전체를 손에 넣을 수 있었다.**</mark>

### <toc2>2. 운영환경 접속키 43개는 어디에 있었나</toc2>

| 저장 위치 | 개수 |
|---|---|
| 소스코드에 하드코딩 | 41개 |
| 환경변수에 암호화 없이 저장 | 3개 |
| (중복) | 1개 |
| **합계 (중복 제외)** | **43개** |

공격자는 43개 중 2개를 실제 공격에 썼다. 하나는 DB에서 데이터를 추출하는 데, 다른 하나는 AWS에 가상 서버를 만들어 데이터를 옮기는 데 쓰였다. DB 접속 정보도 평문으로 저장되어 있었다.

참고로 "하드코딩"이 무엇인지 간단한 예시로 비교하면 다음과 같다. (아래 코드는 이해를 돕기 위한 예시이며, 티빙의 실제 코드가 아니다.)

```python
# 하드코딩: 코드를 본 사람은 누구나 키를 얻는다
client = boto3.client(
    "s3",
    aws_access_key_id="AKIAXXXXXXXXXXXXXXXX",
    aws_secret_access_key="xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx",
)
```

```python
# 시크릿 관리: 코드에는 키가 없고, 실행 시점에 권한(IAM 역할)으로 받아 온다
client = boto3.client("s3")  # 인스턴스/컨테이너에 부여된 역할의 임시 자격 증명 사용

secret = boto3.client("secretsmanager").get_secret_value(SecretId="prod/db")
```

두 번째 방식에서는 소스코드가 통째로 유출되더라도 그 안에서 운영환경 키를 얻을 수 없다.

### <toc2>3. 첫 번째 시도와 두 번째 시도</toc2>

5월 30일 공격자는 DB에서 데이터를 한꺼번에 뽑아내려 했고, 그 부하로 DB 서버 CPU가 100%까지 올라 경보가 울렸다. 티빙은 해당 쿼리를 막았지만 이를 <mark>단순 시스템 장애로 보고 보안 사고로 다루지 않았다.</mark>

다음 날 공격자는 방식을 바꿨다. 가상 서버를 만들 수 있는 다른 키로 AWS에 별도 서버를 만들고, 그곳으로 데이터를 옮긴 뒤 해외로 보냈다. 이때는 CPU 사용률이 10% 미만으로 유지됐다. 조사단은 공격자가 **전날의 경보를 피하려고 의도적으로 부하를 낮춘 것**으로 보았다. 작업이 끝나자 가상 서버는 삭제됐다.

| 구분 | 5월 30일 (1차) | 5월 31일 (2차) |
|---|---|---|
| 사용한 키 | DB 추출용 운영 접속키 | 가상 서버 생성이 가능한 운영 접속키 |
| 방식 | 운영 DB에서 직접 대량 추출 | AWS에 가상 서버를 만들어 복사 후 해외 전송 |
| CPU 사용률 | 100% → 경보 | 10% 미만 → 경보 없음 |
| 결과 | 쿼리 차단, "장애"로 처리 | 약 24GB 유출, 가상 서버 삭제 |

### <toc2>4. 최초 침입 경로는 밝혀지지 않았다</toc2>

개발자의 접속키가 어떻게 탈취됐는지는 아직 모른다. 조사단은 피싱, 악성코드, 공급망 공격, 키 공유·오용, 취약점 악용 가능성을 모두 살폈고 개발자 노트북·PC 9대를 포렌식(디지털 증거를 수집·분석하는 것)했지만 경로를 찾지 못했다. 티빙의 VPN(외부에서 사내망에 안전하게 접속하는 통로) 접속 기록이 **6일치만 보관**되어 있었던 것도 조사를 어렵게 했다.

티빙 대표는 국정감사에서 AI 기반 해킹으로 추정한다고 답했지만, 이는 회사의 추정이며 침입 경로와 원인은 확정되지 않았다.

### <toc2>3. 실제 피해자 수</toc2>

티빙은 같은 사람이 여러 가입 방식으로 계정을 만들 수 있는 구조였고, <mark>한 사람이 최대 13개 계정</mark>을 가진 경우도 있었다. CI가 있는 계정 1,903만 6,223개는 중복을 빼면 1,323만 5,452개였다. CI가 없는 약 2,040만 개 계정은 같은 사람인지 확인할 수 없어, 실제 피해자 수는 개인정보보호위원회가 정하게 된다.

# <toc>근본 원인</toc>

### <toc2>1. 비밀을 코드에 넣었다</toc2>

운영환경 접속키가 소스코드와 환경변수에 평문으로 들어가 있었다. 접속키 같은 비밀 정보는 <mark>소스코드와 분리해 전용 저장소에 보관</mark>해야 한다. 조사단은 적절한 키 관리가 있었다면 운영환경 침투를 막을 수 있었다고 보았고, 정부는 이런 관행이 ISMS 인증 기준에도 맞지 않는다고 지적했다.

### <toc2>2. 개발 키 하나로 전부 볼 수 있었다</toc2>

모든 개발자에게 전체 개발 프로젝트에 접근할 권한이 주어져 있었다. **최소 권한 원칙**이 지켜졌다면, 한 개발자의 키가 탈취되더라도 그 개발자가 맡은 프로젝트만 노출됐을 것이다.

개발환경과 운영환경의 경계도 사실상 무너져 있었다. <mark>개발환경에 들어간 것만으로 운영환경의 키를 얻을 수 있었기 때문이다.</mark>

### <toc2>3. 키를 "관리"하지 않았다</toc2>

키의 발급, 사용, 교체, 폐기가 체계적으로 관리되지 않았다. 일부 개발자는 사내 메신저로 키를 주고받았다. 키를 주기적으로 교체했다면, 탈취된 키나 코드 속 키가 공격 시점에 이미 쓸모없어졌을 수도 있다.

### <toc2>4. 알고도 고치지 않았다</toc2>

티빙은 2024년 모의해킹에서 이번에 악용된 것과 같은 접속키 하드코딩 취약점을 발견했지만 개선하지 않았다. <mark>**점검으로 문제를 찾는 것과 그 문제를 실제로 고치는 것은 다른 일이다.**</mark> 점검 결과를 추적하고 조치를 확인하는 절차가 없었다면 모의해킹은 보고서로만 남는다.

### <toc2>5. 볼 수 있는 것이 CPU뿐이었다</toc2>

티빙의 모니터링은 CPU 부하 같은 단순한 시스템 지표에 머물렀다. 네트워크 트래픽이나 대량 데이터 조회 같은 비정상 행위를 실시간으로 탐지하고 차단하는 체계가 없었다. 그래서 첫날 경보는 "장애"로 보였고, 둘째 날 공격자가 CPU 부하를 낮추자 아예 경보가 울리지 않았다.

### <toc2>6. 암호화 키를 데이터 옆에 두었다</toc2>

휴대전화번호와 이메일은 암호화되어 있었지만, 이를 풀 수 있는 키도 함께 유출됐다. 암호화의 효과는 <mark>키를 데이터와 분리해 보호할 때만</mark> 나온다.

### <toc2>7. 보안 조직이 성장을 따라가지 못했다</toc2>

티빙의 전체 임직원은 265명, 그중 개발 인력은 149명이었지만 정보보호 전담 인력은 외주를 빼고 4명 안팎이었다. 국정감사에서는 매출이 26배 성장하는 동안 보안 전담 인력은 4명에 그쳤다는 지적이 나왔다. 티빙 대표도 보안 투자가 충분한지 CEO로서 우선순위를 두고 챙기지 못했다고 인정했다.

# <toc>보완이 미흡했던 부분</toc>

### <toc2>1. 첫 번째 경보를 놓쳤다</toc2>

5월 30일 오후 6시 DB 서버 CPU가 100%가 됐을 때가 피해를 막을 수 있는 기회였다. 이때 대량 추출 시도를 공격으로 의심하고 접속키를 폐기했다면, 다음 날의 대량 유출은 막을 수 있었을 가능성이 크다.

그러나 이 상황은 장애로 처리됐고, <mark>정보보호 전담조직과 CISO에게 공유되기까지 약 14시간</mark>이 걸렸다. 그 사이 공격자는 다른 키로 다시 들어와 데이터를 가져갔다.

### <toc2>2. 신고가 늦었다</toc2>

정부가 판단한 공식 인지 시점은 5월 31일 오전 10시 10분이고, KISA 신고는 6월 1일 오후 3시 8분이었다. 법정 기한인 24시간을 약 5시간 넘겼다.

### <toc2>3. 로그가 없어서 원인을 못 찾았다</toc2>

VPN 접속 기록이 6일치만 보관되어 있어, 개발자 키가 언제 어떻게 탈취됐는지 추적할 수 없었다. <mark>최초 침입 경로를 모르면 같은 경로로 다시 공격받을 가능성을 막을 수 없다.</mark> 정부가 재발방지 대책에 로그 저장·관리 정책 마련을 넣은 이유다.

### <toc2>4. 필요 없는 데이터까지 가지고 있었다</toc2>

유출된 계정에는 탈퇴 계정 약 887만 개와 테스트 계정 약 11만 개가 포함됐다. 국정감사에서는 탈퇴 회원의 정보를 어떤 기준으로 얼마나 보관하고 있었는지가 쟁점이 됐다. 또한 가입 시 중복 여부를 확인하지 않아 한 사람이 여러 계정을 만들 수 있었고, 그 결과 같은 사람의 정보가 여러 번 저장되어 있었다.

<mark>**갖고 있지 않은 데이터는 유출될 수도 없다.**</mark>

### <toc2>5. 피해 규모 발표의 혼선</toc2>

초기 자체 집계(약 1,953만 명)와 정부 조사 결과(3,954만 계정)의 차이가 컸다. 활성 계정만이 아니라 휴면·탈퇴·테스트 계정까지 모두 유출됐다는 사실은 조사 결과 발표에서야 확인됐다. 이용자 입장에서는 자신이 피해 대상인지 판단하기 어려웠다.

### <toc2>6. 보상의 실효성 논란</toc2>

국정감사에서는 보상안이 1인당 2만 원 수준에 그쳐 실질적인 피해 구제가 되기 어렵다는 지적이 나왔다. 특히 CI는 주민등록번호처럼 한 사람에게 고정된 값이라 유출 후 바꾸기 어렵다. 보험이나 포인트로는 이런 구조적인 위험을 해소하기 어렵다.
