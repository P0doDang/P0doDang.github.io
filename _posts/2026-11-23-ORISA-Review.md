> **논문**: Recovering and Rehosting Mobile Local LLM Conversations and Contexts via Memory Forensics
> **저자**: Haichuan Xu, David Oygenblik, Runze Zhang, Mingxuan Yao, Muhammad Ibrahim, Brendan Saltaformaggio (Georgia Institute of Technology)
> **학회**: IEEE Symposium on Security and Privacy (IEEE S&P) 2026
> **분야**: 디지털 포렌식 / 메모리 포렌식

챗봇과 나눈 대화를 지우면 그 대화는 정말 사라질까? 클라우드 챗봇이라면 답은 "아니다"에 가깝다. 화면에서는 지워져도 서버 어딘가에는 로그가 남는다. 그렇다면 서버가 아예 없는 경우, 스마트폰 안에서만 돌아가는 로컬 LLM에서 대화를 지우면 어떨까.

이번에 읽은 ORISA는 이 질문에 "지워도 남고, 모델이 이미 잊어버린 것까지 남는다"고 답하는 논문이다. 남아 있는 것을 찾는 데서 끝나지 않고, 찾은 조각으로 **대화 세션 자체를 다시 살려서 수사관이 질문을 던질 수 있게** 만든다는 점이 이 논문의 핵심이다.

# <toc>읽기 전에 던진 세 가지 질문</toc>

논문을 본격적으로 읽기 전에 초록과 서론만 보고 아래 세 질문에 먼저 답을 적어 두었다. 다 읽은 뒤 이 답이 어떻게 바뀌었는지는 글 마지막에 다시 정리한다.

**이 논문이 다루는 문제는 무엇인가?**
스마트폰 안에서만 동작하는 로컬 LLM 앱에서 사용자가 대화를 삭제했을 때, 그 대화를 다시 찾아낼 수 있는가 하는 문제다.

**왜 이 문제가 중요한가?**
클라우드 챗봇은 서버에 기록이 남지만 로컬 LLM은 남지 않는다. 누군가 로컬 LLM으로 범죄를 계획하고 대화를 지우면 수사관이 볼 수 있는 증거가 없어진다. 반대로 사용자 입장에서는 "지웠다"고 믿은 대화가 남아 있다면 그 자체로 프라이버시 문제다.

**기존 방식들은 무엇이 부족했는가?**
디스크 포렌식은 디스크에 흔적이 없으면 할 수 있는 일이 없다. 기존 메모리 포렌식은 커널이나 앱의 자료구조를 찾아내는 데 집중했고, LLM처럼 여러 층으로 쌓인 소프트웨어의 내부 상태를 복구해서 다시 돌리는 것까지는 다루지 않았다.

# <toc>로컬 LLM이 만든 증거의 사각지대</toc>

요즘은 1~2B 파라미터 규모의 작은 모델을 스마트폰에서 직접 돌리는 앱이 꽤 많다. 문서 요약, 개인 비서, 학습 도우미 같은 기능을 인터넷 연결 없이 쓸 수 있고, 대화가 기기 밖으로 나가지 않으니 프라이버시 측면에서는 분명한 장점이다.

그런데 포렌식 관점에서 보면 이 장점이 그대로 약점이 된다. 클라우드 LLM은 요청과 응답, 텔레메트리가 서버에 남고, 수사기관은 영장 같은 법적 절차로 그 기록을 받아 볼 수 있다. 로컬 LLM에는 그런 서버가 없다. <mark>기기 자체가 유일한 증거 출처</mark>가 된다.

저자들은 이 문제가 실제로 어느 정도인지 확인하려고 Google Play에서 다운로드 1만 회가 넘는 **IRIS**라는 앱을 먼저 조사했다. IRIS는 "Privacy-Focused"를 내세우고 완전히 오프라인으로 동작하는 앱이다. 앱 저장소(내부·외부)를 덤프해 보니 대화 캐시나 로그가 디스크에 전혀 남지 않았다. 새 채팅 버튼을 누르면 기존 세션은 삭제되고, 앱 안에서는 지운 대화를 다시 열 방법이 없었다.

여기까지는 "증거가 없다"는 이야기다. 흥미로운 건 그다음이다. 저자들이 앱 프로세스의 메모리를 덤프해 보니, `llama_batch` 포인터가 가리키는 곳에서 입력한 프롬프트와 일치하는 토큰 ID가 나왔고, `llama_kv_cache`가 가리키는 영역에는 대화가 이어질수록 커지는 KV 캐시 텐서가 있었다. 5턴 동안 KV 캐시는 7.71MB에서 19.48MB까지 커졌다. 그리고 새 채팅 버튼으로 세션을 지운 뒤 다시 덤프했을 때, 포인터는 끊겼지만 **그 자리의 텐서 값은 그대로 남아 있었다.**

논문은 이 관찰을 바탕으로 다음과 같은 상황을 가정한다.

- 평범한 Android 사용자가 로컬 LLM 앱으로 범죄를 계획한다.
- 앱 UI에서 대화를 삭제한다. 디스크와 서버에는 흔적이 없다.
- 기기가 압수되는 시점에 **앱 프로세스는 아직 실행 중**이다.

수사관에게 주어지는 것은 앱 프로세스의 메모리 이미지와 앱 저장 디렉터리뿐이다. 앱을 직접 개조하거나 메모리 암호화 같은 안티 포렌식 기법을 쓰는 용의자는 범위에서 제외한다.

### <toc2>이해에 필요한 배경 개념</toc2>

논문을 따라가려면 LLM 추론 과정에서 메모리에 무엇이 올라가는지 알아야 한다.

- **모델 바이너리**: 학습된 가중치와 아키텍처 정보(어휘 크기, 임베딩 차원, 레이어 수 등)를 담은 파일이다. 모바일 앱은 주로 GGUF 형식을 쓰고, 세션을 시작하려면 디스크에서 이 파일을 읽어 와야 한다.
- **배치 토큰**: LLM은 문장을 정수 ID의 나열로 바꿔서 처리한다. 그래서 대화 내용은 메모리에 문자열이 아니라 **정수 배열**로 존재한다. 이 배열은 KV 캐시의 위치를 가리키는 기준 역할도 한다.
- **컨텍스트 윈도우**: 모델이 한 번에 볼 수 있는 토큰 수의 상한이다. 대화가 이보다 길어지면 오래된 토큰부터 밀려나고, 모델은 밀려난 내용을 "잊는다".
- **KV 캐시**: 트랜스포머는 새 토큰을 하나 만들 때마다 이전 토큰 전체에 대한 어텐션을 계산한다. 매번 처음부터 계산하면 느리니까 이전 토큰들의 Key/Value 텐서를 저장해 둔다. 이 캐시가 곧 **모델이 지금까지의 대화를 기억하고 있는 상태**다.
- **리호스팅(Rehosting)**: 복구한 상태를 분석 환경으로 옮겨 다시 실행하는 것이다.

정리하면 토큰은 "무슨 말을 했는지", KV 캐시는 "모델이 그 말을 어떻게 기억하고 있는지"에 해당한다. 대화를 이어가려면 둘 다 필요하다.

### <toc2>기존 기법으로는 왜 안 될까</toc2>

메모리 포렌식에는 이미 잘 알려진 방법들이 있다. 하지만 하나씩 대입해 보면 이 문제에는 그대로 쓸 수 없다.

| 기존 접근 | 통하지 않는 이유 |
|---|---|
| 디스크 포렌식 | UI에서 삭제하면 디스크에 남는 것이 없다 |
| 포인터 추적 | 삭제 시 KV 캐시로 가는 참조가 끊긴다. 따라갈 포인터가 없다 |
| 시그니처 스캔 | LLM 컨텍스트는 숫자 덩어리라 구조적 경계나 표식이 없다 |
| 값 집합 분석(VSA) | 모델 파일이나 토큰 정수는 찾을 수 있어도, 텐서를 살아 있는 엔진에 맞춰 넣지는 못한다 |
| 딥러닝 모델 리호스팅 연구 | 모델 가중치는 되살리지만 "대화 상태"는 대상이 아니었다 |

여기에 LLM 특유의 문제가 하나 더 있다. 추론 엔진은 생성이 진행되는 동안 텐서 버퍼를 계속 옮기고, 링 버퍼처럼 앞으로 되감아 쓰고, 오래된 영역의 참조를 놓아 버린다. 정적인 OS 프로파일이나 객체 포인터에 기대는 도구는 이런 구조를 따라가지 못한다.

결국 기존 연구는 <mark>무엇이 메모리에 있는지 찾는 것</mark>까지는 했지만, <mark>찾은 것을 다시 동작하게 만드는 것</mark>은 LLM에 대해 해 본 적이 없다. ORISA가 파고드는 지점이 바로 이 간극이다.

# <toc>삭제도 망각도, 메모리를 지우지는 않는다</toc>

ORISA는 두 가지 관찰에서 출발한다.

**첫째, 지워도 남는다.** UI에서 대화를 삭제해도 배치 토큰과 KV 캐시의 값은 프로세스 메모리에 그대로 있다. 삭제는 참조를 끊을 뿐 메모리를 0으로 덮지 않는다. C에서 `free()`를 호출해도 그 자리의 값이 곧바로 사라지지 않는 것과 같은 원리다.

**둘째, 잊은 것도 남는다.** 앱이 할당받은 버퍼는 모델의 컨텍스트 한도보다 크다. 그래서 윈도우 밖으로 밀려난 토큰과 KV 텐서도 OS가 회수하기 전까지 메모리에 남아 있다. 저자들은 컨텍스트 한도를 넘어선 영역에서 평균 30%가 넘는 토큰과 텐서를 발견했다.

나는 두 번째 관찰이 이 논문을 정말 흥미롭게 만든다고 생각한다. 삭제된 대화를 복구하는 것만으로도 의미가 있지만, 여기서 더 나아가 **원래 세션조차 더 이상 접근하지 못하는 내용**을 되살릴 수 있다는 뜻이기 때문이다. 복구한 세션이 원본보다 더 많이 기억할 수도 있다는 이야기다.

다만 관찰만으로 복구가 되지는 않는다. 실제로 세션을 되살리려면 넘어야 할 문제가 여럿 있다.

- 토큰 버퍼와 KV 텐서에는 라벨이 없다. 메모리 안에서 어디가 무엇인지 알 수 없다.
- 삭제 후에는 활성 영역을 가리키던 참조가 끊겨 있다.
- 엔진은 현재 윈도우 안의 텐서 위치만 관리한다. 밀려난 텐서에 대한 장부는 없다.
- 복구한 텐서가 올바른 토큰 위치와 시퀀스에 대응하는지 검증해야 한다.
- 밀려난 텐서는 물리적으로 존재해도 엔진이 "무효"로 취급한다. 다시 쓰게 하려면 활성 영역으로 넣어 줘야 한다.

### <toc2>다섯 단계 파이프라인</toc2>

ORISA는 크게 **아티팩트 추출**(1~2단계)과 **컨텍스트 재구성**(3~5단계)으로 나뉜다. 앞의 두 단계는 기존 포렌식 기법을 잘 조합한 부분이고, 이 논문의 새로운 기여는 뒤의 세 단계에 몰려 있다.

```text
[메모리 이미지 + 앱 저장 디렉터리]
        │
        ▼
 1. 모델 바이너리 추출 ──▶ 어떤 모델이었는지 특정
        │
        ▼
 2. 배치 토큰 복구·역토큰화 ──▶ 대화 "텍스트" 복구
        │
        ▼
 3. KV 캐시 복구 (활성 + 잊힌 영역) ──▶ 대화 "상태" 복구
        │
        ▼
 4. KV 확장·재정렬 ──▶ 잊힌 영역을 활성 영역으로 편입
        │
        ▼
 5. 세션 리호스팅 ──▶ 수사관이 질문할 수 있는 살아 있는 세션
```

**1단계 — 모델 바이너리 추출.** 토큰과 KV 캐시는 "어떤 모델이었는지"를 알아야 의미가 생긴다. 같은 계열 모델이라도 임베딩 차원이나 헤드 수가 조금만 달라지면 리호스팅이 깨진다. 기기에는 모델 파일이 여러 개 있을 수 있으니 정확히 어떤 파일이었는지 골라내야 한다. 다행히 실행 중인 앱의 메모리에는 모델의 지문이 남아 있다. 아키텍처 식별자, 양자화 방식, 레이어 수, 임베딩 차원, 헤드 수, 학습 컨텍스트 길이 같은 값이 llama.cpp의 `hparams`, `cparams`에 들어 있다. ORISA는 앱 디렉터리에서 GGUF 매직 바이트(`0x47475546`)로 모델 파일 후보를 카빙하고, 메타데이터가 메모리의 지문과 전부 일치하는 파일을 고른다. 이후 단계가 모두 "같은 모델"을 전제로 하기 때문에 가장 먼저 해야 하는 일이다.

**2단계 — 배치 토큰 복구와 역토큰화.** `llama_context` 안의 배치 포인터가 아직 유효하면 거기서부터 거슬러 올라가며 토큰을 읽는다. 포인터가 지워졌다면 "배치 크기 + 지금까지 처리한 토큰 수 × 토큰 크기"보다 큰 정렬된 연속 블록을 메모리에서 훑는다. 두 경우 모두 "토큰 ID가 어휘 범위 안에 있는가", "위치 버퍼와 시퀀스 ID 버퍼가 비어 있지 않은가"로 후보를 거른다. 찾은 토큰은 1단계에서 확보한 토크나이저로 텍스트로 되돌리고, 역할 구분자를 기준으로 시스템 프롬프트·사용자 입력·모델 응답으로 나눈다. 여기까지만 해도 수사관은 지워진 대화를 **읽을** 수 있다.

**3단계 — KV 캐시 복구.** 토큰 하나가 차지하는 KV 슬롯 크기는 모델 구조에서 계산할 수 있다.

```text
B_token = 헤드 수(H) × 헤드 차원(D_h) × 원소 크기(E) × 2   (K와 V)
```

ORISA는 `B_token × 컨텍스트 길이`보다 큰, 페이지 정렬된 블록을 힙에서 찾고, KV 캐시 헤더가 맞는지, `head` 값이 `[0, ctx)` 범위 안인지, `used` 값이 복구한 토큰 길이 이하인지 확인해서 진짜 캐시만 남긴다. KV 캐시는 링 버퍼처럼 동작하기 때문에 활성 영역이 버퍼 끝을 넘어 앞으로 감겨 돌아오는 경우도 계산에 넣는다.

그다음이 핵심이다. 각 KV 셀에 붙은 위치값과 시퀀스 ID를 2단계에서 복구한 토큰의 것과 하나씩 대조해 검증하고, 활성 영역의 시작점을 지나서도 계속 훑으며 **위치와 시퀀스 ID가 복구된 토큰과 맞는 "잊힌 셀"**을 모은다. 유효한 텐서가 더 이상 나오지 않거나 복구한 토큰 길이에 도달하면 멈춘다.

**4단계 — KV 확장과 재정렬.** 잊힌 셀을 찾아도 엔진은 그걸 쓰지 않는다. 엔진의 장부에는 여전히 "현재 윈도우"만 기록되어 있기 때문이다. 그래서 ORISA는 KV 캐시의 메타데이터를 직접 고친다. 링 버퍼의 시작점(`head`)을 0으로 되돌리고, `used`를 복구한 전체 셀 개수로, `size`를 새로 키운 컨텍스트 크기로 바꾼다. 각 셀은 `i_new = (i_old − h) mod ctx`로 새 인덱스를 받아 옮겨지고, 남는 칸은 비운다. 마지막으로 엔진이 "지금까지 처리한 토큰 수"로 쓰는 `n_past`를 복구한 개수로 맞춘다. 이렇게 하면 엔진은 밀려났던 내용을 원래부터 활성 컨텍스트였던 것처럼 취급한다.

**5단계 — 세션 리호스팅.** 난수 생성기 상태와 마지막 출력 로짓까지 메모리에서 복원해, 확장한 KV 캐시와 함께 llama.cpp가 읽을 수 있는 세션 바이너리로 만든다. 그리고 1단계의 모델로 새 세션을 열어 `llama_state_set_data()`로 이 상태를 주입한다. 이제 `decode()`를 호출하면 세션은 삭제 직전의 맥락에서 그대로 이어서 말한다. 수사관은 여기에 "아까 알려 준 내용을 다시 말해 줘" 같은 질문을 던질 수 있다.

### <toc2>이 설계에서 눈여겨본 점</toc2>

가장 마음에 들었던 건 **2단계와 3단계가 서로를 검증한다는 점**이다. 토큰만 찾으면 우연히 어휘 범위에 들어오는 정수 배열에 속을 수 있고, KV 텐서만 찾으면 아무 의미 없는 부동소수점 덩어리와 구분하기 어렵다. 그런데 KV 셀에는 위치와 시퀀스 ID가 붙어 있고, 그것이 복구한 토큰과 맞아야만 채택한다. 라벨이 없는 두 종류의 데이터를 서로의 라벨로 쓰는 셈이다.

또 하나는 4단계가 가진 성격이다. 지금까지 내가 알던 메모리 포렌식은 대부분 "읽는" 작업이었다. 메모리에서 자료구조를 찾고 해석해서 사람이 볼 수 있게 보여 주는 것이다. ORISA의 4단계는 반대로 **엔진의 상태를 "쓰는"** 작업이다. 엔진의 장부를 고쳐서, 엔진 스스로 버렸던 메모리를 다시 쓰게 만든다. 논문도 이 부분을 기존 메모리 포렌식과 구분되는 핵심 기여로 꼽는다.

### <toc2>얼마나 복구되는가</toc2>

각 세션에 키-값 쌍을 10개씩 계속 넣어서, 처리된 토큰이 1,024개를 넘을 때까지 대화를 채웠다. 실제로는 세션당 평균 1,056 토큰으로, 256·512 윈도우를 각각 약 4배, 2배 넘치게 채운 셈이다. 그다음 UI에서 대화를 지우고 메모리를 덤프했다.

| 구분 | 배치 토큰 | KV 텐서 |
|---|---|---|
| 활성 윈도우 안 | 100% 복구 | 100% 복구 (평균 약 21MB) |
| 윈도우 밖 (잊힌 영역) | 평균 233개, 약 38% | 평균 5,860K개, 약 33% (약 11MB) |

활성 윈도우 안은 60개 세션 전부에서 100% 복구했다. UI 삭제 후에도 활성 토큰과 KV 캐시가 메모리에 고스란히 남아 있다는 뜻이다. 이미 잊힌 영역에서도 3분의 1 이상을 건졌다.

몇 가지 경향도 보였다. Gemma 2는 KV 헤드 수와 헤드 차원이 커서 KV 캐시가 다른 두 모델보다 3배 정도 컸다(26.85MB 대 8.66MB, 7.56MB). 그리고 초기 윈도우가 클수록 잊힌 영역에서 더 많이 복구됐다. IRIS + Llama 3.2 조합에서 윈도우가 256일 때는 138개, 512일 때는 327개의 토큰을 추가로 찾았다. 윈도우가 크면 할당되는 버퍼 자체가 커지기 때문이다.

### <toc2>되살린 세션은 얼마나 기억하는가</toc2>

복구한 세션을 1,024 토큰 윈도우로 리호스팅한 뒤, "아까 말해 준 내부 프로젝트 메모를 전부 나열해 줘"라고 물었다.

평균 94쌍을 넣었을 때 원래 세션의 윈도우 안에는 27쌍만 남아 있었다. ORISA로 되살린 세션은 평균 46쌍을 답했다. 원래 세션 대비 약 **170%**다. 원래 세션이 이미 잊어버린 내용을 되살린 세션이 기억해 낸 것이다.

같은 수의 쌍을 넣어도 앱마다 윈도우에 남는 양이 달랐는데, 이유가 재미있다. ChatterUI는 앱이 넣는 시스템 프롬프트가 평균 120토큰 정도로 IRIS(약 42토큰)보다 길어서, 그만큼 사용자 대화가 들어갈 자리가 줄었다. 모델별로는 Llama와 Qwen이 Gemma보다 많이 복구됐는데, 키-값 한 쌍을 표현하는 데 Llama·Qwen은 약 9.5토큰, Gemma는 약 12.7토큰이 들기 때문이라고 한다.

ChatterUI 사례 연구도 같은 결과를 보여 준다. "Project Note Keeper"라는 캐릭터를 만들어 Llama 3.2 1B(윈도우 256)에 사실 100개를 넣고 대화를 지운 뒤 복구했다. 되살린 세션은 26개를 답했고, 원래 세션이 접근할 수 있던 것은 14개였다. 덤으로, 복구한 토큰을 역토큰화해 보니 ChatterUI가 사용자가 정의한 캐릭터 설명을 시스템 프롬프트에 넣고 윈도우에서 밀려나지 않는 고정 토큰(`n_keep`)으로 엔진에 넘긴다는 앱 내부 동작까지 드러났다. 포렌식 도구가 앱 분석 도구 역할도 하는 셈이다.

### <toc2>되살린 세션은 원래 세션처럼 답하는가</toc2>

포렌식 증거가 되려면 "되살린 세션의 답이 원래 세션이 했을 답과 같아야" 한다. 이를 확인하려고 30개 세션에 각각 키-값 20쌍을 넣고, 원래 세션과 되살린 세션에 똑같은 질문 15개를 던졌다. 10개는 실제로 넣은 키를 묻고, 5개는 넣은 적 없는 키를 묻는다. 그리고 "이전 메시지에 없는 내용이면 정확히 'Not in prior messages'라고만 답하라"는 규칙을 줬다.

총 450문항에서 두 세션의 결과는 **TP 291, FP 26, TN 124, FN 9로 완전히 같았다.** 넣은 적 없는 "client passphrase"를 물었더니 `DEBUG-ON-2025`라고 지어내는 오답(FP)도 원래 세션과 되살린 세션에서 똑같이 나왔다. 저자들은 이 오답이 리호스팅 때문이 아니라 모델 자체의 환각과 검색 한계 때문이며, 난수 생성기 상태까지 복원했기 때문에 행동이 그대로 재현된다고 설명한다.

### <toc2>llama.cpp 밖으로</toc2>

10개 앱이 모두 llama.cpp 기반이라는 점은 범용성에 대한 의문을 남긴다. 저자들은 GPU·NPU를 지원하는 다른 모바일 엔진인 **mllm**으로 ORISA를 확장해 보였다. `llama_batch` 대신 mllm의 `Tensor` 객체 헤더를 찾고, KV 캐시는 레이어별 `Tensor` 객체를 스캔하는 식으로 프런트엔드만 바꿨다. 여기서도 윈도우 밖 토큰 34%, 텐서 28%를 복구했고, 되살린 세션은 윈도우에 남아 있던 18쌍보다 많은 26쌍을 답했다.

저자들의 주장은 이렇다. 트랜스포머 엔진이라면 토큰 버퍼, KV 캐시, 런타임 상태 관리자라는 세 가지 구조는 반드시 있다. 따라서 엔진별로 이 구조를 해석하는 프런트엔드만 새로 쓰면 나머지 방법론은 그대로 적용된다.

# <toc>읽으면서 걸렸던 부분</toc>

결과만 보면 깔끔하지만, 읽으면서 몇 군데에서 멈칫했다. 먼저 저자들이 스스로 밝힌 한계는 다음과 같다.

- 메모리를 난독화하거나 암호화하는 엔진, 표준과 다른 레이아웃을 쓰는 엔진에는 그대로 통하지 않을 수 있다.
- 10개 앱 전체로 평가한 엔진은 llama.cpp뿐이다.
- 수사관이 되살린 세션에 계속 질문하면 세션의 답이 용의자의 기록보다 수사관의 질문을 반영하게 될 수 있다. 다만 복구한 상태는 메모리 이미지로 따로 있으니, 언제든 질문 전 상태로 되돌릴 수 있다고 한다.

여기에 내가 보기에 아쉬운 점을 더한다.

**1. "앱이 아직 실행 중"이라는 전제가 강하다.** 프로세스가 종료되거나 Android가 메모리 부족으로 앱을 정리하면 이 방법은 출발점부터 성립하지 않는다. 실험도 "삭제 직후 바로 덤프"한 경우만 다룬다. 삭제 후 시간이 지나거나, 같은 앱에서 새 대화를 시작했을 때 복구율이 어떻게 떨어지는지에 대한 정량 실험은 없다. 실제 압수 상황에서는 이 시간 축이 가장 중요한 변수일 텐데 말이다.

**2. 메모리 획득 방식이 실제 수사 환경과 다르다.** 논문은 루팅된 기기를 가정하지 않으며, 수사기관은 서드파티 포렌식 도구나 제로데이로 메모리를 확보한다고 설명한다. 하지만 실험에서는 Magisk로 루팅한 기기에서 Frida로 앱 프로세스에 직접 붙어 메모리를 떴다. 계측 도구를 붙이는 행위 자체가 메모리 상태를 바꿀 수 있고, 잠긴 기기에서 특정 앱 프로세스의 메모리만 깔끔하게 얻는 것은 또 다른 문제다. 획득 단계는 범위 밖으로 남겨 둔 셈이다.

**3. 일관성 실험이 핵심 기능을 시험하지 않는다.** 일관성 실험은 2,048 토큰 윈도우에서 20쌍만 넣고 진행했다. 세션이 넘치지 않으니, ORISA의 핵심인 "잊힌 KV를 확장·재정렬하는 경로"가 이 실험에서는 동작하지 않는다. 다시 말해 이 실험이 보여 주는 건 "상태를 손실 없이 옮길 수 있다"는 것이지, "잊힌 영역을 붙여 넣은 세션도 왜곡 없이 답한다"는 것이 아니다. 후자는 따로 검증이 필요하다.

**4. "집계가 같다"는 "응답이 같다"보다 약한 증거다.** 보고된 건 TP/FP/TN/FN 개수가 같다는 것뿐이다. 문항별로 같은 답을 했는지, 생성된 문장이 얼마나 비슷한지는 표에서 알 수 없다. 난수 상태까지 복원했다면 문항별 출력이 완전히 같아야 할 텐데, 그걸 직접 보여 줬다면 훨씬 강한 근거가 됐을 것이다.

**5. "170%"라는 숫자를 어떻게 읽을지.** 복구율은 "원래 윈도우에 남아 있던 쌍" 대비로 계산한다. 그래서 170%라는 큰 숫자가 나온다. 그런데 처음 넣은 94쌍을 기준으로 보면, 원래 세션은 약 29%(27쌍), 되살린 세션은 약 49%(46쌍)를 기억한 것이다. 분명 의미 있는 향상이지만, 대화의 절반 정도는 여전히 돌아오지 않는다는 점도 같이 봐야 한다. 그리고 표 2는 10개 앱 중 3개만 상세 수치를 보여 주고 나머지는 "Others"로 묶었다.

**6. 숫자 표기가 일치하지 않는다.** 초록과 5.1절 요약에서는 윈도우 밖 복구율을 "32.60%, 38.59%"라고 적었는데, 표 1의 전체 평균은 토큰 38.02%, KV 텐서 32.60%다. 38.59%는 PocketPal 앱 한 곳의 KV 평균이다. 큰 흐름에는 영향이 없지만 읽다가 헷갈렸다.

**7. 평가 범위가 좁다.** 1~2B 모델 3종, 기기 1대, 합성한 키-값 사실만 썼다. 실제 대화는 사실을 나열하지 않고, 256·512 토큰 윈도우는 실사용보다 훨씬 작다. 윈도우가 4K, 8K로 커지면 할당 버퍼와 잔존 양상도 달라질 것이다.

**8. 부분 복구된 컨텍스트를 증거로 볼 수 있는가.** 잊힌 셀은 복구된 토큰과 위치·시퀀스 ID가 맞아야 채택되고, 유효하지 않은 셀을 만나면 거기서 스캔을 멈춘다. 그러니 되살린 컨텍스트는 "원본의 앞부분 일부가 잘려 나간" 형태가 된다. 이런 컨텍스트 위에서 모델이 내놓는 답을 증거로 볼 수 있는지, 모델이 빈 곳을 그럴듯하게 메우지는 않는지에 대한 논의가 부족하다. 무엇보다 모델의 답은 **"기록"이 아니라 "생성"**이라는 점에서 기존 포렌식 증거와 성격이 다르다. 토큰을 역토큰화한 텍스트는 기록이지만, 되살린 세션이 내놓는 답은 그 기록을 바탕으로 한 추론이다.

**9. 모델 파일이 디스크에 있어야 한다.** 1단계는 "로컬 LLM이니 모델 파일은 반드시 디스크에 있다"고 가정한다. 용의자가 대화뿐 아니라 모델 파일까지 지웠다면 어떻게 될까. 같은 연구실의 AI Psychiatry처럼 메모리에서 모델 가중치를 복구하는 기법과 합치면 풀 수 있을 것 같은데, 논문에서는 다루지 않았다.

# <toc>다 읽고 나서</toc>

### <toc2>사전 질문의 답은 어떻게 달라졌나</toc2>

읽기 전에는 이 논문을 "지운 대화를 복구하는 연구"로만 이해했다. 다 읽고 나서는 핵심이 두 가지로 바뀌었다.

먼저, 복구 대상은 텍스트가 아니라 **상태**다. 토큰만 찾으면 대화를 읽을 수는 있다. 하지만 KV 캐시까지 찾아서 엔진에 다시 넣어야 세션이 살아나고, 수사관이 질문을 던질 수 있다.

다음으로, 삭제된 것뿐 아니라 **모델이 이미 잊은 것**까지 복구한다. "삭제"와 "망각"은 모두 장부를 고치는 논리적인 동작일 뿐 메모리를 지우지 않는다. ORISA는 이 틈을 정확히 파고든다.

"기존 방식은 무엇이 부족했나"에 대한 답도 바뀌었다. 기존 기법이 LLM의 흔적을 **못 찾아서** 부족했던 게 아니다. 값 집합 분석으로도 토큰 정수나 모델 파일은 찾을 수 있다. 부족했던 건 찾은 것을 **엔진이 다시 쓸 수 있게 맞춰 넣는 단계**였다. 잊힌 텐서를 활성 영역으로 재정렬하는 4단계가 그 빈자리를 채운다.

### <toc2>느낀 점</toc2>

메모리 포렌식의 오래된 원칙이 새로운 대상에도 그대로 통한다는 점이 가장 인상 깊었다. "해제된 메모리는 덮어쓰이기 전까지 남는다"는 건 수십 년 된 이야기다. 그런데 그 위에 KV 캐시라는 새 자료구조가 올라오자 완전히 새로운 종류의 증거가 생겼다. 새로운 소프트웨어가 나올 때마다 "이건 메모리에 무엇을 남기는가"를 묻는 것만으로 연구 주제가 될 수 있다는 걸 다시 느꼈다.

또 하나는 포렌식과 프라이버시가 같은 현상의 양면이라는 점이다. 수사관에게 유용한 잔존 데이터는 사용자에게는 지워지지 않은 개인정보다. IRIS는 "Privacy-Focused"를 내세우는 앱이지만, 사용자가 대화를 지워도 메모리에는 그대로 남아 있었다. 이 논문은 포렌식 기법인 동시에 로컬 LLM 앱의 프라이버시 결함 보고서로도 읽힌다.

마지막으로, 증거의 성격이 달라지고 있다는 생각이 들었다. 지금까지 디지털 증거는 대부분 "남아 있는 기록"이었다. ORISA가 만든 세션은 질문에 따라 답이 달라지는, 말하자면 **심문할 수 있는 증거**다. 이런 증거를 법정에서 어떻게 다뤄야 할지는 기술만으로 답할 수 없는 문제지만, 기술 쪽에서도 "어디까지가 기록이고 어디부터가 생성인지"를 구분해 보여 주는 장치는 필요하다고 본다.

### <toc2>이 논문이 더 나아갈 수 있는 방향</toc2>

앞에서 짚은 아쉬운 점에서 출발해 개선 아이디어를 정리해 봤다.

- **시간에 따른 복구율 감쇠 곡선.** 삭제 후 경과 시간, 이후 새 대화의 길이, 다른 앱 사용량에 따라 복구율이 어떻게 떨어지는지 측정한다. "삭제 후 몇 분 안에 압수해야 몇 %를 건질 수 있다" 같은 실무 기준을 줄 수 있다.
- **프로세스 종료 이후의 흔적.** 앱이 종료된 뒤 해제된 페이지가 물리 메모리나 스왑(zram)에 얼마나 남는지 조사한다. 전제 조건을 "실행 중"에서 "최근에 실행됨"으로 넓히는 방향이다.
- **잊힌 영역을 편입한 세션의 충실도 검증.** 윈도우가 넘친 세션을 대상으로, 처음부터 큰 윈도우로 돌린 기준 세션과 ORISA가 확장한 세션의 응답을 문항 단위로 비교한다. 위의 3번, 4번 아쉬움을 직접 메우는 실험이다.
- **복구 결과의 신뢰 등급화.** 토큰으로 직접 복구한 텍스트(기록), 활성 KV로 뒷받침되는 응답, 부분 복구된 KV에 의존하는 응답(생성)을 구분해서 표시한다. 증거 능력을 따질 때 필요한 장치다.
- **방어 쪽 연구.** 삭제할 때 토큰 버퍼와 KV 캐시를 0으로 덮는 "안전한 삭제"를 엔진에 넣고 그 성능 비용을 측정한다. ORISA를 공격 모델로 삼는 프라이버시 연구가 된다.

# <toc>앞으로 할 것</toc>

### <toc2>이 논문을 바탕으로 더 읽어볼 논문</toc2>

- **AI Psychiatry: Forensic Investigation of Deep Learning Networks in Memory Images (USENIX Security 2024)** — 같은 연구실의 선행 연구로, 메모리 이미지에서 딥러닝 모델을 복구해 리호스팅한다. ORISA가 대상을 "모델"에서 "대화 상태"로 넓힌 것임을 이해할 수 있고, 위의 9번 아쉬움(모델 파일이 지워진 경우)과도 연결된다.
- **DSCRETE (USENIX Security 2014)** — 앱 자신의 로직을 재사용해 메모리 속 자료구조를 해석한다. "엔진을 다시 써서 복원한다"는 ORISA 발상의 뿌리로 보인다.
- **GUITAR (CCS 2015), Screen after Previous Screens (USENIX Security 2016), VCR (CCS 2015)** — Android 앱의 화면과 사진 증거를 메모리 이미지에서 복구하는 연구들이다. 모바일 메모리 포렌식이 어떤 흐름으로 발전해 왔는지 잡는 데 좋다.
- **Tipped Off by Your Memory Allocator (NDSS 2018)** — Android 메모리 할당기의 흔적으로 기기 전반의 사용자 활동 순서를 재구성한다. 위의 "시간 축" 문제를 고민할 때 참고가 될 것 같다.
- **DEEPVSA (USENIX Security 2019)** — 값 집합 분석 계열 연구. ORISA가 왜 이 방식만으로는 부족하다고 했는지 직접 확인하고 싶다.
- **Back to the Whiteboard (USENIX Security 2019)** — 메모리 포렌식 기법을 원칙적으로 평가하는 틀을 제안한 논문. 위에서 짚은 한계를 더 체계적인 언어로 정리하는 데 도움이 될 것이다.
- **I Know What You Asked: Prompt Leakage via KV-Cache Sharing in Multi-Tenant LLM Serving (NDSS 2025)** — KV 캐시가 포렌식 대상이 아니라 공격 표면이 되는 사례다.

### <toc2>비슷한 문제를 다른 분야에 적용할 가능성</toc2>

- **데스크톱·서버의 로컬 LLM 실행기.** Ollama, LM Studio처럼 리눅스·윈도우·맥에서 돌아가는 llama.cpp 기반 실행기에도 같은 구조가 있다. 프로세스 덤프를 얻기가 모바일보다 훨씬 쉬워서 오히려 적용하기 좋다.
- **온디바이스 AI 전반.** 음성 비서, 키보드 자동완성, 이미지 생성 모델도 추론 중간 상태를 메모리에 둔다. 각각 무엇이 얼마나 남는지 조사해 볼 가치가 있다.
- **AI 에이전트 포렌식.** 에이전트가 도구를 호출한 기록과 중간 추론이 모두 컨텍스트에 들어 있다. 침해 사고가 났을 때 "에이전트가 무엇을 보고 무엇을 했는가"를 재구성하는 데 쓸 수 있다.
- **다중 사용자 추론 서버.** 여러 사용자의 KV 캐시가 한 프로세스에 있다면, 덤프 한 번으로 여러 사람의 대화가 드러난다. 포렌식보다는 보안 위험 평가에 가까운 주제다.

### <toc2>직접 구현·재현·비교해 보고 싶은 포인트</toc2>

- 리눅스에서 llama.cpp를 직접 돌리고 프로세스 덤프를 떠서, **토큰 버퍼가 정말 정수 배열로 보이는지** 눈으로 확인하기. 2단계의 축소판이다.
- 대화를 초기화한 직후와, 새 대화를 얼마간 진행한 후의 덤프를 비교해서 이전 토큰이 얼마나 덮어쓰였는지 세어 보기. 위의 "시간에 따른 감쇠 곡선"을 작게 해 보는 실험이다.
- llama.cpp의 세션 저장·복원 API(`llama_state_get_data` / `llama_state_set_data`)로 KV 캐시를 저장했다가 다시 로드해 보기. 5단계가 어떤 정보를 필요로 하는지 감을 잡을 수 있다.
- 같은 세션을 원래 상태로 복원했을 때 문항별 출력이 정말 바이트 단위로 같은지 확인하기. 위의 4번 아쉬움을 직접 확인해 보는 것이다.
- 논문은 채택 후 ORISA를 공개하겠다고 했다. 코드가 공개되면 다른 양자화 수준이나 더 큰 윈도우(4K, 8K)에서도 같은 복구율이 나오는지 비교해 보고 싶다.

### <toc2>내가 연구/프로젝트로 발전시킨다면</toc2>

두 방향을 생각했다.

**방향 A — LLM 런타임 잔존 데이터 측정 연구.** 여러 로컬 LLM 실행기를 대상으로 대화 삭제, 세션 종료, 앱 종료 각 시점에 메모리에 무엇이 얼마나 남는지 체계적으로 측정한다. ORISA가 "복구할 수 있다"를 보였다면, 이 연구는 "**언제까지, 어떤 조건에서** 복구할 수 있는가"에 답한다. 새로운 복구 기법을 만들지 않아도 되는 측정 연구라 시작하기에 현실적이다.

**방향 B — 안전한 삭제 패치와 그 비용.** llama.cpp에 삭제 시 토큰 버퍼와 KV 캐시를 지우는 옵션을 넣고, 잔존 데이터가 실제로 사라지는지와 성능 저하가 얼마나 되는지 측정한다. ORISA의 반대편에 서는 연구이고, 결과물이 오픈소스 기여로 이어질 수 있다.

둘 중에서는 **방향 A를 먼저** 해 보려고 한다. 무엇이 남는지 알아야 무엇을 지워야 할지도 정할 수 있기 때문이다. 우선은 데스크톱 llama.cpp로 작게 시작해서, 위의 재현 포인트 중 첫 번째와 두 번째부터 직접 손으로 확인해 볼 생각이다.
