> **논문**: Recovering and Rehosting Mobile Local LLM Conversations and Contexts via Memory Forensics
> **저자**: Haichuan Xu, David Oygenblik, Runze Zhang, Mingxuan Yao, Muhammad Ibrahim, Brendan Saltaformaggio (Georgia Institute of Technology)
> **학회**: IEEE Symposium on Security and Privacy (IEEE S&P) 2026
> **분야**: 디지털 포렌식 / 메모리 포렌식

챗봇과 나눈 대화를 지우면 그 대화는 정말 사라질까? 클라우드 챗봇이라면 답은 "아니다"에 가깝다. 화면에서는 지워져도 서버 어딘가에는 로그가 남는다. 그렇다면 서버가 아예 없는 경우, 스마트폰 안에서만 돌아가는 로컬 LLM에서 대화를 지우면 어떨까.

이번에 읽은 ORISA는 이 질문에 "지워도 남고, 모델이 이미 잊어버린 것까지 남는다"고 답하는 논문이다. 남아 있는 것을 찾는 데서 끝나지 않고, 찾은 조각으로 **대화 세션 자체를 다시 살려서 수사관이 질문을 던질 수 있게** 만든다는 점이 핵심이다.

# <toc>주요 용어 정리</toc>

본문을 읽기 전에 자주 나오는 용어를 먼저 정리한다. 논문은 llama.cpp를 기준으로 설명하기 때문에 llama.cpp의 변수 이름도 함께 적었다.

가장 중요한 두 가지만 먼저 기억하면 된다. **토큰**은 "무슨 말을 했는지"를, **KV 캐시**는 "모델이 그 말을 어떻게 기억하고 있는지"를 담는다. 대화를 읽으려면 토큰이 있으면 되지만, 대화를 이어가려면 둘 다 있어야 한다.

### <toc2>로컬 LLM과 추론 엔진</toc2>

| 용어 | 설명 |
|---|---|
| **로컬 LLM (온디바이스 LLM)** | 서버를 거치지 않고 사용자 기기 안에서 직접 실행되는 언어 모델. 이 논문에서는 스마트폰에서 도는 1~2B 파라미터 규모의 모델을 다룬다. |
| **추론 엔진** | 모델 파일을 읽어 실제로 다음 토큰을 계산하는 런타임. 이 논문의 앱 10개는 모두 **llama.cpp**를 쓰고, 확장 실험에서는 **mllm**을 다룬다. |
| **모델 바이너리 / GGUF** | 학습된 가중치와 모델 구조 정보(어휘 크기, 레이어 수 등)를 담은 파일. llama.cpp는 GGUF 형식을 쓰며, 파일 맨 앞에 `GGUF`(`0x47475546`)라는 매직 바이트가 있다. ORISA 1단계에서 찾는 대상이다. |
| **양자화 (Quantization)** | 가중치를 4비트, 6비트처럼 낮은 정밀도로 줄여 저장하는 기법. 모바일에서 큰 모델을 돌리려고 쓴다. 같은 모델이라도 양자화 방식이 다르면 다른 파일이므로, 모델을 특정하는 지문 중 하나가 된다. |
| **하이퍼파라미터** | 레이어 수, 임베딩 차원, 어텐션 헤드 수, 헤드 차원처럼 모델 구조를 정하는 값. llama.cpp에서는 `hparams`, 컨텍스트 설정은 `cparams`에 들어 있다. ORISA는 이 값으로 모델 파일을 특정하고 KV 슬롯 크기를 계산한다. |
| **컨텍스트 관리자** | 세션의 상태(처리한 토큰 수, KV 캐시 위치 등)를 관리하는 엔진 내부 구조. llama.cpp에서는 `llama_context`다. |

### <toc2>토큰과 컨텍스트</toc2>

| 용어 | 설명 |
|---|---|
| **토큰 / 토크나이저** | LLM은 문장을 그대로 처리하지 않고, 토크나이저로 잘게 나눈 뒤 각 조각을 정수 ID로 바꿔 처리한다. 이 정수 하나하나가 토큰이다. |
| **어휘 (Vocabulary)** | 모델이 아는 토큰 전체 목록. 토큰 ID는 반드시 `0 ~ 어휘 크기-1` 범위 안에 있으므로, ORISA는 이 범위를 진짜 토큰 배열인지 거르는 조건으로 쓴다. |
| **배치 토큰 (`llama_batch`)** | 엔진에 입력으로 넘겨진 토큰 배열. 대화 내용이 메모리에 문자열이 아니라 **정수 배열**로 남는 이유다. ORISA 2단계에서 복구한다. |
| **역토큰화 (Detokenization)** | 토큰 ID 배열을 다시 사람이 읽을 수 있는 텍스트로 되돌리는 것. 원래 모델의 토크나이저가 있어야 정확히 할 수 있다. |
| **위치(pos) / 시퀀스 ID(seq_id)** | 각 토큰에 붙는 메타데이터. pos는 대화 안에서 몇 번째 토큰인지, seq_id는 어느 대화(시퀀스)에 속하는지를 뜻한다. ORISA가 토큰과 KV 셀을 짝지을 때 쓰는 열쇠다. |
| **시스템 프롬프트 / 역할 구분자** | 시스템 프롬프트는 앱이 사용자 몰래 대화 앞에 넣는 지시문이고, 역할 구분자는 Llama 3의 `start_header_id` 같은 특수 토큰으로 시스템·사용자·모델 발화의 경계를 표시한다. ORISA는 이 구분자로 복구한 대화를 발화별로 나눈다. |
| **컨텍스트 윈도우** | 모델이 한 번에 볼 수 있는 토큰 수의 상한. 실험에서는 256, 512 토큰을 썼다. |
| **컨텍스트 축출 / 망각** | 대화가 윈도우보다 길어지면 오래된 토큰부터 밀려나는 것. 엔진의 장부에서만 빠질 뿐 메모리 값은 바로 지워지지 않는다. 이 논문이 말하는 "잊힌 컨텍스트(forgotten context)"가 이것이다. |
| **`n_past`** | 엔진이 "지금까지 처리한 토큰 수"로 기억하는 값. ORISA 4단계에서 복구한 전체 개수로 고쳐 쓴다. |
| **`n_keep`** | 윈도우가 넘쳐도 밀려나지 않게 고정해 두는 앞부분 토큰 수. ChatterUI 사례에서 캐릭터 설명이 이렇게 고정돼 있었다. |

### <toc2>KV 캐시</toc2>

| 용어 | 설명 |
|---|---|
| **어텐션 / 어텐션 헤드** | 트랜스포머가 새 토큰을 만들 때 이전 토큰들 중 어디에 주목할지 계산하는 과정. 여러 개의 헤드가 병렬로 계산한다. |
| **KV 캐시** | 이전 토큰들에 대한 Key·Value 텐서를 저장해 두는 캐시. 매번 처음부터 계산하지 않으려고 쓴다. **모델이 지금까지의 대화를 기억하고 있는 상태** 그 자체이며, ORISA 3단계에서 복구한다. |
| **텐서** | 숫자를 담은 다차원 배열. KV 캐시는 수백만 개의 부동소수점 값으로 된 텐서 덩어리라 겉보기에는 아무 구조도 없다. |
| **KV 셀(슬롯)** | KV 캐시 안에서 토큰 하나에 해당하는 칸. 크기는 `헤드 수 × 헤드 차원 × 원소 크기 × 2`로 계산되고, 각 셀에는 pos와 seq_id가 붙어 있다. |
| **링 버퍼** | 끝에 도달하면 처음으로 돌아가 다시 쓰는 원형 버퍼. llama.cpp의 KV 캐시는 이렇게 동작하며, `head`(다음에 쓸 위치), `used`(사용 중인 셀 수), `size`(전체 크기)로 관리된다. ORISA 4단계는 이 세 값을 고쳐서 잊힌 영역을 다시 활성 영역으로 만든다. |
| **활성 영역 / 잊힌 영역** | 활성 영역은 엔진이 현재 윈도우로 인정하는 KV 셀들이고, 잊힌 영역은 윈도우 밖으로 밀려났지만 아직 메모리에 남아 있는 셀들이다. |
| **로짓 (Logits)** | 다음 토큰 후보 각각에 대한 점수. 이 점수로 다음 토큰을 고른다. |
| **난수 생성기(RNG) 상태** | 로짓에서 다음 토큰을 확률적으로 뽑을 때 쓰는 난수의 현재 상태. ORISA는 로짓과 RNG 상태까지 복원해, 되살린 세션이 원래 세션과 같은 답을 내도록 한다. |
| **환각 (Hallucination)** | 모델이 없는 사실을 그럴듯하게 지어내는 것. 실험 3의 FP 대부분이 이것이다. |

### <toc2>포렌식</toc2>

| 용어 | 설명 |
|---|---|
| **디스크 포렌식 / 메모리 포렌식** | 디스크 포렌식은 저장장치에 남은 파일·로그를, 메모리 포렌식은 실행 중인 시스템의 RAM에 남은 데이터를 분석한다. 이 논문은 디스크에 흔적이 없는 상황이라 메모리 포렌식을 택했다. |
| **메모리 이미지 (덤프)** | 특정 시점의 메모리 내용을 그대로 떠 낸 파일. ORISA의 입력이다. |
| **논리적 삭제 / 물리적 삭제** | 논리적 삭제는 참조나 장부만 지우는 것이고, 물리적 삭제는 실제 값을 덮어쓰는 것이다. 앱의 "대화 삭제"와 엔진의 "망각"은 둘 다 논리적 삭제라서 값이 남는다. |
| **역참조 해제 (Dereference)** | 논문에서는 "어떤 영역을 가리키던 포인터가 끊긴 상태"를 뜻하는 말로 쓴다. 대화를 지우면 KV 캐시를 가리키던 포인터가 끊기지만 그 영역의 값은 그대로다. |
| **파일 카빙 / 매직 바이트** | 파일 시스템 정보 없이 파일 고유의 시작 바이트(매직 바이트)를 단서로 파일을 찾아내는 기법. ORISA 1단계에서 GGUF 모델 파일을 찾을 때 쓴다. |
| **포인터 추적** | 알려진 구조체에서 출발해 포인터를 따라가며 자료구조를 찾는 기존 메모리 포렌식 기법. 삭제 후 포인터가 끊기면 쓸 수 없다. |
| **시그니처 스캔** | 자료구조 고유의 바이트 패턴(시그니처)으로 메모리를 훑는 기법. KV 캐시처럼 구조적 표식이 없는 데이터에는 약하다. |
| **값 집합 분석 (VSA)** | 메모리 값이 가질 수 있는 범위를 분석해 자료구조를 추론하는 기법. 정적인 값은 찾지만 LLM의 어텐션 구조는 이해하지 못한다. |
| **리호스팅 (Rehosting)** | 복구한 상태를 분석 환경으로 옮겨 다시 실행하는 것. ORISA 5단계에서 llama.cpp 세션으로 되살린다. |
| **위협 모델** | 연구가 어떤 공격자(여기서는 용의자)를 가정하는지 정한 범위. 이 논문은 앱을 개조하지 않는 평범한 사용자를 가정한다. |
| **안티 포렌식** | 메모리 암호화, 난독화처럼 포렌식 분석을 방해하는 기법. 이 논문의 범위 밖이다. |
| **Frida / 루팅(Magisk)** | Frida는 실행 중인 앱에 붙어 메모리를 읽고 동작을 조작하는 동적 계측 도구이고, Magisk는 Android 기기에 루트 권한을 주는 도구다. 실험에서 메모리 덤프를 뜨는 데 썼다. |

### <toc2>평가 지표</toc2>

| 용어 | 설명 |
|---|---|

# <toc>1. 기존의 문제 정의 — 연구 목적과 배경</toc>

### <toc2>이 논문이 다루는 문제</toc2>

스마트폰 안에서만 동작하는 로컬 LLM 앱에서 사용자가 대화를 삭제했을 때, **그 대화를 다시 찾아내고, 나아가 그 대화가 이어지던 상태 그대로 세션을 되살릴 수 있는가**가 이 논문의 문제다.

요즘은 1~2B 파라미터 규모의 작은 모델을 스마트폰에서 직접 돌리는 앱이 꽤 많다. 문서 요약, 개인 비서, 학습 도우미 같은 기능을 인터넷 연결 없이 쓸 수 있고, 대화가 기기 밖으로 나가지 않으니 프라이버시 측면에서는 분명한 장점이다.

### <toc2>왜 이 문제가 중요한가</toc2>

포렌식 관점에서 보면 로컬 LLM의 장점이 그대로 약점이 된다. 클라우드 LLM은 요청과 응답, 텔레메트리가 서버에 남고, 수사기관은 영장 같은 법적 절차로 그 기록을 받아 볼 수 있다. 로컬 LLM에는 그런 서버가 없다. <mark>기기 자체가 유일한 증거 출처</mark>가 된다. 누군가 로컬 LLM으로 범죄를 계획하고 대화를 지우면 수사관이 볼 수 있는 것이 사라진다.

반대 방향에서 봐도 중요한 문제다. 사용자가 "지웠다"고 믿은 대화가 어딘가에 남아 있다면, 그 자체로 프라이버시 결함이다.

저자들은 이 문제가 실제로 어느 정도인지 확인하려고 Google Play에서 다운로드 1만 회가 넘는 **IRIS**라는 앱을 먼저 조사했다. IRIS는 "Privacy-Focused"를 내세우고 완전히 오프라인으로 동작한다. 앱 저장소(내부·외부)를 덤프해 보니 대화 캐시나 로그가 디스크에 전혀 남지 않았다. 새 채팅 버튼을 누르면 기존 세션은 삭제되고, 앱 안에서는 지운 대화를 다시 열 방법이 없었다.

그런데 앱 프로세스의 메모리를 덤프해 보니 이야기가 달라졌다. `llama_batch` 포인터가 가리키는 곳에서 입력한 프롬프트와 일치하는 토큰 ID가 나왔고, `llama_kv_cache`가 가리키는 영역에는 대화가 이어질수록 커지는 KV 캐시 텐서가 있었다. 5턴 동안 KV 캐시는 7.71MB에서 19.48MB까지 커졌다. 새 채팅 버튼으로 세션을 지운 뒤 다시 덤프했을 때, 포인터는 끊겼지만 **그 자리의 텐서 값은 그대로 남아 있었다.**

논문이 가정하는 상황은 다음과 같다.

- 평범한 Android 사용자가 로컬 LLM 앱으로 범죄를 계획한다.
- 앱 UI에서 대화를 삭제한다. 디스크와 서버에는 흔적이 없다.
- 기기가 압수되는 시점에 **앱 프로세스는 아직 실행 중**이다.

수사관에게 주어지는 것은 앱 프로세스의 메모리 이미지와 앱 저장 디렉터리뿐이다. 앱을 직접 개조하거나 메모리 암호화 같은 안티 포렌식 기법을 쓰는 용의자는 범위에서 제외한다.

### <toc2>기존 방식들은 무엇이 부족했는가</toc2>

메모리 포렌식에는 이미 잘 알려진 방법들이 있다. 하지만 하나씩 대입해 보면 이 문제에는 그대로 쓸 수 없다.

| 기존 접근 | 통하지 않는 이유 |
|---|---|
| 디스크 포렌식 | UI에서 삭제하면 디스크에 남는 것이 없다 |
| 포인터 추적 | 삭제 시 KV 캐시로 가는 참조가 끊긴다. 따라갈 포인터가 없다 |
| 시그니처 스캔 | LLM 컨텍스트는 숫자 덩어리라 구조적 경계나 표식이 없다 |
| 값 집합 분석(VSA) | 모델 파일이나 토큰 정수는 찾을 수 있어도, 텐서를 살아 있는 엔진에 맞춰 넣지는 못한다 |
| 딥러닝 모델 리호스팅 연구 | 모델 가중치는 되살리지만 "대화 상태"는 대상이 아니었다 |

여기에 LLM 특유의 문제가 하나 더 있다. 추론 엔진은 생성이 진행되는 동안 텐서 버퍼를 계속 옮기고, 링 버퍼처럼 앞으로 되감아 쓰고, 오래된 영역의 참조를 놓아 버린다. 정적인 OS 프로파일이나 객체 포인터에 기대는 도구는 이런 구조를 따라가지 못한다.

결국 기존 연구는 <mark>무엇이 메모리에 있는지 찾는 것</mark>까지는 했지만, <mark>찾은 것을 다시 동작하게 만드는 것</mark>은 LLM에 대해 해 본 적이 없다. ORISA의 연구 목적은 이 간극을 메우는 것이다.

# <toc>2. 문제 해결을 위한 제안 — ORISA</toc>

### <toc2>출발점이 된 두 가지 관찰</toc2>

**첫째, 지워도 남는다.** UI에서 대화를 삭제해도 배치 토큰과 KV 캐시의 값은 프로세스 메모리에 그대로 있다. 삭제는 참조를 끊을 뿐 메모리를 0으로 덮지 않는다. C에서 `free()`를 호출해도 그 자리의 값이 곧바로 사라지지 않는 것과 같은 원리다.

**둘째, 잊은 것도 남는다.** 앱이 할당받은 버퍼는 모델의 컨텍스트 한도보다 크다. 그래서 윈도우 밖으로 밀려난 토큰과 KV 텐서도 OS가 회수하기 전까지 메모리에 남아 있다. 저자들은 컨텍스트 한도를 넘어선 영역에서 평균 30%가 넘는 토큰과 텐서를 발견했다.

두 번째 관찰이 이 논문을 흥미롭게 만든다. 삭제된 대화를 복구하는 데서 그치지 않고, **원래 세션조차 더 이상 접근하지 못하는 내용**을 되살릴 수 있다는 뜻이기 때문이다. 복구한 세션이 원본보다 더 많이 기억할 수도 있다.

### <toc2>넘어야 할 문제</toc2>

관찰만으로 복구가 되지는 않는다. 실제로 세션을 되살리려면 다음 문제를 풀어야 한다.

- 토큰 버퍼와 KV 텐서에는 라벨이 없다. 메모리 안에서 어디가 무엇인지 알 수 없다.
- 삭제 후에는 활성 영역을 가리키던 참조가 끊겨 있다.
- 엔진은 현재 윈도우 안의 텐서 위치만 관리한다. 밀려난 텐서에 대한 장부는 없다.
- 복구한 텐서가 올바른 토큰 위치와 시퀀스에 대응하는지 검증해야 한다.
- 밀려난 텐서는 물리적으로 존재해도 엔진이 "무효"로 취급한다. 다시 쓰게 하려면 활성 영역으로 넣어 줘야 한다.

### <toc2>다섯 단계 파이프라인</toc2>

ORISA는 크게 **아티팩트 추출**(1~2단계)과 **컨텍스트 재구성**(3~5단계)으로 나뉜다. 앞의 두 단계는 기존 포렌식 기법을 잘 조합한 부분이고, 이 논문의 새로운 기여는 뒤의 세 단계에 몰려 있다.

```text
[메모리 이미지 + 앱 저장 디렉터리]
        │
        ▼
 1. 모델 바이너리 추출 ──▶ 어떤 모델이었는지 특정
        │
        ▼
 2. 배치 토큰 복구·역토큰화 ──▶ 대화 "텍스트" 복구
        │
        ▼
 3. KV 캐시 복구 (활성 + 잊힌 영역) ──▶ 대화 "상태" 복구
        │
        ▼
 4. KV 확장·재정렬 ──▶ 잊힌 영역을 활성 영역으로 편입
        │
        ▼
 5. 세션 리호스팅 ──▶ 수사관이 질문할 수 있는 살아 있는 세션
```

**1단계 — 모델 바이너리 추출.** 토큰과 KV 캐시는 "어떤 모델이었는지"를 알아야 의미가 생긴다. 같은 계열 모델이라도 임베딩 차원이나 헤드 수가 조금만 달라지면 리호스팅이 깨진다. 기기에는 모델 파일이 여러 개 있을 수 있으니 정확히 어떤 파일이었는지 골라내야 한다. 다행히 실행 중인 앱의 메모리에는 모델의 지문이 남아 있다. 아키텍처 식별자, 양자화 방식, 레이어 수, 임베딩 차원, 헤드 수, 학습 컨텍스트 길이 같은 값이 llama.cpp의 `hparams`, `cparams`에 들어 있다. ORISA는 앱 디렉터리에서 GGUF 매직 바이트(`0x47475546`)로 모델 파일 후보를 카빙하고, 메타데이터가 메모리의 지문과 전부 일치하는 파일을 고른다.

**2단계 — 배치 토큰 복구와 역토큰화.** `llama_context` 안의 배치 포인터가 아직 유효하면 거기서부터 거슬러 올라가며 토큰을 읽는다. 포인터가 지워졌다면 "배치 크기 + 지금까지 처리한 토큰 수 × 토큰 크기"보다 큰 정렬된 연속 블록을 메모리에서 훑는다. 두 경우 모두 "토큰 ID가 어휘 범위 안에 있는가", "위치 버퍼와 시퀀스 ID 버퍼가 비어 있지 않은가"로 후보를 거른다. 찾은 토큰은 1단계에서 확보한 토크나이저로 텍스트로 되돌리고, 역할 구분자를 기준으로 시스템 프롬프트·사용자 입력·모델 응답으로 나눈다. 여기까지만 해도 수사관은 지워진 대화를 **읽을** 수 있다.

**3단계 — KV 캐시 복구.** 토큰 하나가 차지하는 KV 슬롯 크기는 모델 구조에서 계산할 수 있다.

```text
B_token = 헤드 수(H) × 헤드 차원(D_h) × 원소 크기(E) × 2   (K와 V)
```

ORISA는 `B_token × 컨텍스트 길이`보다 큰, 페이지 정렬된 블록을 힙에서 찾고, KV 캐시 헤더가 맞는지, `head` 값이 `[0, ctx)` 범위 안인지, `used` 값이 복구한 토큰 길이 이하인지 확인해서 진짜 캐시만 남긴다. KV 캐시는 링 버퍼처럼 동작하기 때문에 활성 영역이 버퍼 끝을 넘어 앞으로 감겨 돌아오는 경우도 계산에 넣는다.

그다음이 핵심이다. 각 KV 셀에 붙은 위치값과 시퀀스 ID를 2단계에서 복구한 토큰의 것과 하나씩 대조해 검증하고, 활성 영역의 시작점을 지나서도 계속 훑으며 **위치와 시퀀스 ID가 복구된 토큰과 맞는 "잊힌 셀"**을 모은다. 유효한 텐서가 더 이상 나오지 않거나 복구한 토큰 길이에 도달하면 멈춘다.

**4단계 — KV 확장과 재정렬.** 잊힌 셀을 찾아도 엔진은 그걸 쓰지 않는다. 엔진의 장부에는 여전히 "현재 윈도우"만 기록되어 있기 때문이다. 그래서 ORISA는 KV 캐시의 메타데이터를 직접 고친다. 링 버퍼의 시작점(`head`)을 0으로 되돌리고, `used`를 복구한 전체 셀 개수로, `size`를 새로 키운 컨텍스트 크기로 바꾼다. 각 셀은 `i_new = (i_old − h) mod ctx`로 새 인덱스를 받아 옮겨지고, 남는 칸은 비운다. 마지막으로 엔진이 "지금까지 처리한 토큰 수"로 쓰는 `n_past`를 복구한 개수로 맞춘다. 이렇게 하면 엔진은 밀려났던 내용을 원래부터 활성 컨텍스트였던 것처럼 취급한다.

**5단계 — 세션 리호스팅.** 난수 생성기 상태와 마지막 출력 로짓까지 메모리에서 복원해, 확장한 KV 캐시와 함께 llama.cpp가 읽을 수 있는 세션 바이너리로 만든다. 그리고 1단계의 모델로 새 세션을 열어 `llama_state_set_data()`로 이 상태를 주입한다. 이제 `decode()`를 호출하면 세션은 삭제 직전의 맥락에서 그대로 이어서 말한다. 수사관은 여기에 "아까 알려 준 내용을 다시 말해 줘" 같은 질문을 던질 수 있다.

### <toc2>이 설계에서 눈여겨본 점</toc2>

가장 마음에 들었던 건 **2단계와 3단계가 서로를 검증한다는 점**이다. 토큰만 찾으면 우연히 어휘 범위에 들어오는 정수 배열에 속을 수 있고, KV 텐서만 찾으면 아무 의미 없는 부동소수점 덩어리와 구분하기 어렵다. 그런데 KV 셀에는 위치와 시퀀스 ID가 붙어 있고, 그것이 복구한 토큰과 맞아야만 채택한다. 라벨이 없는 두 종류의 데이터를 서로의 라벨로 쓰는 셈이다.

또 하나는 4단계의 성격이다. 지금까지 내가 알던 메모리 포렌식은 대부분 "읽는" 작업이었다. 메모리에서 자료구조를 찾고 해석해서 사람이 볼 수 있게 보여 주는 것이다. ORISA의 4단계는 반대로 **엔진의 상태를 "쓰는"** 작업이다. 엔진의 장부를 고쳐서, 엔진 스스로 버렸던 메모리를 다시 쓰게 만든다. 논문도 이 부분을 기존 메모리 포렌식과 구분되는 핵심 기여로 꼽는다.

# <toc>3. 실험 과정</toc>

### <toc2>실험 환경</toc2>

- **앱**: Google Play와 GitHub에서 인기 있는 Android 로컬 LLM 앱 10개 (IRIS, ChatterUI, Layla, Solia, Maid, LLMHub, PocketPal, Local AI, AnythingLLM, LM Playground). 모두 llama.cpp 기반이다.
- **모델**: Llama 3.2 1B, Qwen 2.5 1.5B, Gemma 2 2B
- **컨텍스트 윈도우**: 256, 512 토큰
- **구성 수**: 10 × 3 × 2 = 60개 세션
- **기기**: 루팅된 Google Pixel 6 (Android 15). 메모리 덤프는 Frida(Objection)로 확보했고, 루트 권한은 Magisk로 얻었다. 리호스팅은 Ubuntu 24.04의 llama.cpp에서 진행했다.

평가는 세 가지 질문으로 나뉜다.

1. 얼마나 복구되는가 (토큰·KV 캐시 복구율)
2. 되살린 세션이 얼마나 기억하는가 (컨텍스트 보존)
3. 되살린 세션이 원래 세션과 같게 답하는가 (의미적 일관성)

### <toc2>실험 데이터 설계</toc2>

실험 설계에서 재미있었던 건 "모델이 정말 대화에서 배운 것을 말하는지"를 확인하는 방법이다. 모델이 학습 데이터로 이미 알고 있을 법한 내용을 넣으면 복구 덕분인지 원래 알던 것인지 구분할 수 없다. 그래서 저자들은 `Project codename = FERN-9e2f1b5d`, `On-call PIN = 5421-ALTO`처럼 무작위로 만든 가상의 프로젝트 메모를 키-값 쌍으로 넣었다. 모델이 이 값을 말한다면 그건 대화에서 온 것이 확실하다.

### <toc2>실험 1 — 토큰·KV 캐시 복구</toc2>

각 세션에 키-값 쌍을 10개씩 계속 넣어서, 처리된 토큰(프롬프트 + 응답)이 1,024개를 넘을 때까지 대화를 채웠다. 이렇게 하면 256·512 윈도우를 확실히 넘치게 되고, 적어도 512토큰은 윈도우 밖으로 밀려난다. 그다음 앱 UI에서 대화를 지우고 프로세스 메모리를 덤프해 ORISA로 토큰과 KV 캐시를 복구했다. 윈도우 안과 밖을 나눠서 복구율을 측정했다.

### <toc2>실험 2 — 되살린 세션의 기억</toc2>

실험 1에서 복구한 상태로 세션 바이너리를 만들고, **1,024 토큰 윈도우**를 가진 새 llama.cpp 세션으로 리호스팅했다. 리호스팅 직후 "List out all the internal project notes I told you earlier."라는 문장으로 질문하고, 응답에서 정확히 기억해 낸 키-값 쌍의 수를 셌다. 비교 기준은 삭제 직전 원래 세션의 윈도우 안에 남아 있던 쌍의 수다.

### <toc2>실험 3 — 응답 일관성</toc2>

10개 앱 × 3개 모델 = 30개 세션에 각각 키-값 20쌍을 넣었다. 이번에는 윈도우를 **2,048 토큰**으로 크게 잡아서 원래 세션이 내용을 잃지 않게 했다. 그다음 메모리를 덤프해 같은 2,048 윈도우로 리호스팅하고, 원래 세션과 되살린 세션에 똑같은 질문 15개를 던졌다.

- 실제로 넣은 키를 묻는 질문 10개 (예: "What is the project codename?")
- 넣은 적 없는 키를 묻는 질문 5개 (예: "What is the client passphrase?")
- 규칙: "이전 메시지에 없는 내용이면 정확히 'Not in prior messages'라고만 답하라"

답은 TP(넣은 값을 맞게 답함), FP(없는 값을 있는 것처럼 지어냄), TN(없다고 맞게 답함), FN(넣은 값을 못 찾거나 틀림)으로 분류해 두 세션을 비교했다.

### <toc2>사례 연구와 다른 엔진으로의 확장</toc2>

- **ChatterUI 사례 연구**: "Project Note Keeper"라는 캐릭터를 만들고 Llama 3.2 1B(윈도우 256)에 사실 100개를 넣어 1,024 토큰을 넘겼다. 대화를 지운 뒤 복구·리호스팅해서 같은 질문을 던졌다.
- **mllm 확장**: GPU·NPU를 지원하는 다른 모바일 엔진인 mllm에 맞춰 프런트엔드를 새로 썼다. `llama_batch` 대신 mllm의 `Tensor` 객체 헤더를 찾고, KV 캐시는 레이어별 `Tensor` 객체를 스캔한다. Llama 3.2(윈도우 256)로 실험 1·2와 같은 절차를 반복했다.

# <toc>4. 실험 결과 및 한계점</toc>

### <toc2>결과 1 — 활성 영역은 전부, 잊힌 영역도 3분의 1 이상</toc2>

세션은 평균 1,056 토큰 길이로, 256·512 윈도우를 각각 약 4배, 2배 넘치게 채웠다.

| 구분 | 배치 토큰 | KV 텐서 |
|---|---|---|
| 활성 윈도우 안 | 100% 복구 | 100% 복구 (평균 약 21MB) |
| 윈도우 밖 (잊힌 영역) | 평균 233개, 약 38% | 평균 5,860K개, 약 33% (약 11MB) |

활성 윈도우 안은 60개 세션 전부에서 100% 복구했다. UI 삭제 후에도 활성 토큰과 KV 캐시가 메모리에 고스란히 남아 있다는 뜻이다. 이미 잊힌 영역에서도 3분의 1 이상을 건졌다.

몇 가지 경향도 보였다. Gemma 2는 KV 헤드 수와 헤드 차원이 커서 KV 캐시가 다른 두 모델보다 3배 정도 컸다(26.85MB 대 8.66MB, 7.56MB). 그리고 초기 윈도우가 클수록 잊힌 영역에서 더 많이 복구됐다. IRIS + Llama 3.2 조합에서 윈도우가 256일 때는 138개, 512일 때는 327개의 토큰을 추가로 찾았다. 윈도우가 크면 할당되는 버퍼 자체가 커지기 때문이다.

### <toc2>결과 2 — 되살린 세션이 원본보다 더 많이 기억한다</toc2>

평균 94쌍을 넣었을 때 원래 세션의 윈도우 안에는 27쌍만 남아 있었다. ORISA로 되살린 세션은 평균 46쌍을 답했다. 원래 세션 대비 약 **170%**다. 원래 세션이 이미 잊어버린 내용을 되살린 세션이 기억해 낸 것이다.

같은 수의 쌍을 넣어도 앱마다 윈도우에 남는 양이 달랐는데, 이유가 재미있다. ChatterUI는 앱이 넣는 시스템 프롬프트가 평균 120토큰 정도로 IRIS(약 42토큰)보다 길어서, 그만큼 사용자 대화가 들어갈 자리가 줄었다. 모델별로는 Llama와 Qwen이 Gemma보다 많이 복구됐는데, 키-값 한 쌍을 표현하는 데 Llama·Qwen은 약 9.5토큰, Gemma는 약 12.7토큰이 들기 때문이라고 한다.

### <toc2>결과 3 — 원래 세션과 똑같이 답한다</toc2>

총 450문항에서 두 세션의 결과는 **TP 291, FP 26, TN 124, FN 9로 완전히 같았다.** 넣은 적 없는 "client passphrase"를 물었더니 `DEBUG-ON-2025`라고 지어내는 오답(FP)도 원래 세션과 되살린 세션에서 똑같이 나왔다. 저자들은 이 오답이 리호스팅 때문이 아니라 모델 자체의 환각과 검색 한계 때문이며, 난수 생성기 상태까지 복원했기 때문에 행동이 그대로 재현된다고 설명한다. 그래서 되살린 세션의 답을 "원래 세션이 계속됐다면 했을 답"으로 믿을 수 있다는 것이 저자들의 결론이다.

### <toc2>사례 연구와 mllm 결과</toc2>

ChatterUI 사례에서는 윈도우 밖에서 토큰 22%, 텐서 18%를 더 복구했다. 되살린 세션은 26개를 답했고, 원래 세션이 접근할 수 있던 것은 14개였다(약 186%). 덤으로, 복구한 토큰을 역토큰화해 보니 ChatterUI가 사용자가 정의한 캐릭터 설명을 시스템 프롬프트에 넣고 윈도우에서 밀려나지 않는 고정 토큰(`n_keep`)으로 엔진에 넘긴다는 앱 내부 동작까지 드러났다. 포렌식 도구가 앱 분석 도구 역할도 하는 셈이다.

mllm에서도 윈도우 밖 토큰 34%, 텐서 28%를 복구했고, 되살린 세션은 윈도우에 남아 있던 18쌍보다 많은 26쌍을 답했다(약 144%). 저자들은 트랜스포머 엔진이라면 토큰 버퍼, KV 캐시, 런타임 상태 관리자라는 세 가지 구조가 반드시 있으므로, 엔진별 프런트엔드만 새로 쓰면 나머지 방법론은 그대로 적용된다고 주장한다.

### <toc2>저자들이 밝힌 한계</toc2>

- 메모리를 난독화하거나 암호화하는 엔진, 표준과 다른 레이아웃을 쓰는 엔진에는 그대로 통하지 않을 수 있다.
- 10개 앱 전체로 평가한 엔진은 llama.cpp뿐이다.
- 수사관이 되살린 세션에 계속 질문하면 세션의 답이 용의자의 기록보다 수사관의 질문을 반영하게 될 수 있다. 다만 복구한 상태는 메모리 이미지로 따로 있으니, 언제든 질문 전 상태로 되돌릴 수 있다고 한다.

### <toc2>읽으면서 보인 한계</toc2>

결과만 보면 깔끔하지만, 읽으면서 몇 군데에서 멈칫했다.

**① "앱이 아직 실행 중"이라는 전제가 강하다.** 프로세스가 종료되거나 Android가 메모리 부족으로 앱을 정리하면 이 방법은 출발점부터 성립하지 않는다. 실험도 "삭제 직후 바로 덤프"한 경우만 다룬다. 삭제 후 시간이 지나거나, 같은 앱에서 새 대화를 시작했을 때 복구율이 어떻게 떨어지는지는 측정하지 않았다.

**② 메모리 획득 방식이 실제 수사 환경과 다르다.** 논문은 루팅된 기기를 가정하지 않으며, 수사기관은 서드파티 포렌식 도구나 제로데이로 메모리를 확보한다고 설명한다. 하지만 실험에서는 루팅한 기기에서 Frida로 앱 프로세스에 직접 붙어 메모리를 떴다. 계측 도구를 붙이는 행위 자체가 메모리 상태를 바꿀 수 있고, 잠긴 기기에서 특정 앱 프로세스의 메모리만 깔끔하게 얻는 것은 또 다른 문제다.

**③ 일관성 실험이 핵심 기능을 시험하지 않는다.** 실험 3은 2,048 윈도우에 20쌍만 넣어서 세션이 넘치지 않는다. 그러면 ORISA의 핵심인 "잊힌 KV를 확장·재정렬하는 경로(4단계)"가 이 실험에서는 동작하지 않는다. 이 실험이 보여 주는 건 "상태를 손실 없이 옮길 수 있다"는 것이지, "잊힌 영역을 붙여 넣은 세션도 왜곡 없이 답한다"는 것이 아니다.

**④ "집계가 같다"는 "응답이 같다"보다 약한 증거다.** 보고된 건 TP/FP/TN/FN 개수가 같다는 것뿐이다. 문항별로 같은 답을 했는지, 생성된 문장이 얼마나 비슷한지는 표에서 알 수 없다. 난수 상태까지 복원했다면 문항별 출력이 완전히 같아야 할 텐데, 그걸 직접 보여 줬다면 훨씬 강한 근거가 됐을 것이다.

**⑤ "170%"라는 숫자를 어떻게 읽을지.** 복구율은 "원래 윈도우에 남아 있던 쌍" 대비로 계산한다. 처음 넣은 94쌍을 기준으로 보면 원래 세션은 약 29%(27쌍), 되살린 세션은 약 49%(46쌍)를 기억한 것이다. 분명 의미 있는 향상이지만, 대화의 절반 정도는 여전히 돌아오지 않는다. 그리고 표 2는 10개 앱 중 3개만 상세 수치를 보여 주고 나머지는 "Others"로 묶었다.

**⑥ 숫자 표기가 일치하지 않는다.** 초록과 5.1절 요약에서는 윈도우 밖 복구율을 "32.60%, 38.59%"라고 적었는데, 표 1의 전체 평균은 토큰 38.02%, KV 텐서 32.60%다. 38.59%는 PocketPal 앱 한 곳의 KV 평균이다. 큰 흐름에는 영향이 없지만 읽다가 헷갈렸다.

**⑦ 평가 범위가 좁다.** 1~2B 모델 3종, 기기 1대, 합성한 키-값 사실만 썼다. 실제 대화는 사실을 나열하지 않고, 256·512 토큰 윈도우는 실사용보다 훨씬 작다.

**⑧ 부분 복구된 컨텍스트를 증거로 볼 수 있는가.** 잊힌 셀은 복구된 토큰과 위치·시퀀스 ID가 맞아야 채택되고, 유효하지 않은 셀을 만나면 스캔을 멈춘다. 그러니 되살린 컨텍스트는 "원본의 앞부분 일부가 잘려 나간" 형태가 된다. 이런 컨텍스트 위에서 모델이 빈 곳을 그럴듯하게 메우지는 않는지에 대한 논의가 부족하다. 무엇보다 모델의 답은 **"기록"이 아니라 "생성"**이다. 토큰을 역토큰화한 텍스트는 기록이지만, 되살린 세션이 내놓는 답은 그 기록을 바탕으로 한 추론이다.

**⑨ 모델 파일이 디스크에 있어야 한다.** 1단계는 "로컬 LLM이니 모델 파일은 반드시 디스크에 있다"고 가정한다. 용의자가 대화뿐 아니라 모델 파일까지 지웠다면 1단계부터 막힌다.

# <toc>5. 추가로 진행하거나 수정해서 실험했으면 하는 부분</toc>

앞에서 짚은 한계를 바탕으로, 내가 이 연구를 이어받는다면 해 보고 싶은 실험을 정리했다.

### <toc2>추가했으면 하는 실험</toc2>

**시간에 따른 복구율 감쇠 곡선 (← 한계 ①)**
삭제 직후만이 아니라 1분, 10분, 1시간 뒤에 덤프를 떠서 복구율을 비교한다. 삭제 후 같은 앱에서 새 대화를 얼마나 진행했는지, 다른 앱을 얼마나 썼는지도 변수로 둔다. 결과가 나오면 "삭제 후 몇 분 안에 확보해야 몇 %를 건질 수 있다" 같은 실무 기준을 줄 수 있다. 실제 압수 상황에서는 이 시간 축이 가장 중요한 변수라고 생각한다.

**프로세스 종료 이후의 흔적 (← 한계 ①)**
앱을 강제 종료하거나 Android가 메모리 부족으로 정리한 뒤, 해제된 페이지가 물리 메모리나 스왑(zram)에 얼마나 남는지 조사한다. 전제 조건을 "실행 중"에서 "최근에 실행됨"으로 넓히는 실험이다.

**메모리 획득 방식별 비교 (← 한계 ②)**
같은 세션을 Frida 기반 프로세스 덤프와 물리 메모리 전체 획득 두 방식으로 떠서 복구율 차이를 본다. 계측 도구를 붙이는 것 자체가 결과에 영향을 주는지 확인할 수 있다.

**모델 파일이 지워진 시나리오 (← 한계 ⑨)**
대화와 함께 모델 파일까지 삭제한 경우를 실험에 넣는다. 메모리에 매핑된 가중치에서 모델을 복구하는 AI Psychiatry 계열 기법과 결합하면 1단계를 대체할 수 있을지 확인해 보고 싶다.

### <toc2>수정해서 다시 했으면 하는 실험</toc2>

**윈도우가 넘친 세션으로 일관성 실험 다시 하기 (← 한계 ③)**
실험 3을 윈도우가 넘친 세션으로 다시 한다. 비교 기준은 "처음부터 큰 윈도우로 돌려 아무것도 잊지 않은 세션"이다. 이 기준 세션과 ORISA가 잊힌 영역을 붙여 확장한 세션에 같은 질문을 던지면, 4단계가 답을 왜곡하지 않는지 직접 확인할 수 있다.

**문항 단위 비교 (← 한계 ④)**
TP/FP 개수 대신 문항마다 두 세션의 출력이 같은지, 다르다면 얼마나 비슷한지(완전 일치율, 편집 거리 등)를 보고한다. 난수 상태까지 복원했다면 바이트 단위로 같아야 하므로 검증이 어렵지 않다.

**지표를 두 가지로 보고하기 (← 한계 ⑤)**
"원래 윈도우 대비 복구율"과 함께 "처음 넣은 전체 대비 복구율"을 나란히 보고한다. 앱 10개의 상세 수치도 전부 공개하면 앱별 차이를 더 잘 볼 수 있다.

**현실에 가까운 조건 (← 한계 ⑦)**
윈도우를 2K, 4K, 8K로 키우고, 키-값 나열 대신 실제 대화에 가까운 데이터(긴 질의응답, 여러 주제가 섞인 대화)로 실험한다. 양자화 수준(Q4, Q6, Q8)도 바꿔 본다. 윈도우와 버퍼 크기가 커질 때 잔존 양상이 어떻게 달라지는지가 궁금하다.

**결과에 신뢰 등급 붙이기 (← 한계 ⑧)**
되살린 세션의 답을 세 단계로 나눠 표시한다. 토큰으로 직접 복구한 텍스트(기록), 활성 KV로 뒷받침되는 응답, 부분 복구된 잊힌 KV에 의존하는 응답(생성). 그리고 각 등급에서 환각 비율이 어떻게 다른지 측정한다. 증거 능력을 따질 때 꼭 필요한 장치라고 본다.

### <toc2>직접 재현해 보고 싶은 것</toc2>

논문은 채택 후 ORISA를 공개하겠다고 했다. 코드가 나오기 전에도 작게 해 볼 수 있는 것들이 있다.

- 리눅스에서 llama.cpp를 직접 돌리고 프로세스 덤프를 떠서, **토큰 버퍼가 정말 정수 배열로 보이는지** 눈으로 확인하기. 2단계의 축소판이다.
- 대화를 초기화한 직후와, 새 대화를 얼마간 진행한 후의 덤프를 비교해서 이전 토큰이 얼마나 덮어쓰였는지 세어 보기. 위의 감쇠 곡선 실험을 작게 해 보는 것이다.
- llama.cpp의 세션 저장·복원 API(`llama_state_get_data` / `llama_state_set_data`)로 KV 캐시를 저장했다가 다시 로드해 보기. 5단계가 어떤 정보를 필요로 하는지 감을 잡을 수 있다.
- 같은 상태에서 복원한 두 세션의 문항별 출력이 정말 같은지 확인하기.

### <toc2>연구나 프로젝트로 발전시킨다면</toc2>

**방향 A — LLM 런타임 잔존 데이터 측정 연구.** 여러 로컬 LLM 실행기를 대상으로 대화 삭제, 세션 종료, 앱 종료 각 시점에 메모리에 무엇이 얼마나 남는지 체계적으로 측정한다. ORISA가 "복구할 수 있다"를 보였다면, 이 연구는 "**언제까지, 어떤 조건에서** 복구할 수 있는가"에 답한다. 새로운 복구 기법을 만들지 않아도 되는 측정 연구라 시작하기에 현실적이다.

**방향 B — 안전한 삭제 패치와 그 비용.** llama.cpp에 삭제 시 토큰 버퍼와 KV 캐시를 0으로 덮는 옵션을 넣고, 잔존 데이터가 실제로 사라지는지와 성능 저하가 얼마나 되는지 측정한다. ORISA를 공격 모델로 삼는 프라이버시 연구이고, 결과물이 오픈소스 기여로 이어질 수 있다.

둘 중에서는 **방향 A를 먼저** 해 보려고 한다. 무엇이 남는지 알아야 무엇을 지워야 할지도 정할 수 있기 때문이다.

# <toc>6. 논문을 읽고 난 후기</toc>

### <toc2>읽기 전과 후, 달라진 이해</toc2>

처음 초록만 읽었을 때는 이 논문을 "지운 대화를 복구하는 연구"로만 이해했다. 다 읽고 나서는 핵심이 두 가지로 바뀌었다.

먼저, 복구 대상은 텍스트가 아니라 **상태**다. 토큰만 찾으면 대화를 읽을 수는 있다. 하지만 KV 캐시까지 찾아서 엔진에 다시 넣어야 세션이 살아나고, 수사관이 질문을 던질 수 있다.

다음으로, 삭제된 것뿐 아니라 **모델이 이미 잊은 것**까지 복구한다. "삭제"와 "망각"은 모두 장부를 고치는 논리적인 동작일 뿐 메모리를 지우지 않는다. ORISA는 이 틈을 정확히 파고든다.

"기존 방식은 무엇이 부족했나"에 대한 답도 바뀌었다. 기존 기법이 LLM의 흔적을 **못 찾아서** 부족했던 게 아니다. 값 집합 분석으로도 토큰 정수나 모델 파일은 찾을 수 있다. 부족했던 건 찾은 것을 **엔진이 다시 쓸 수 있게 맞춰 넣는 단계**였다.

### <toc2>느낀 점</toc2>

메모리 포렌식의 오래된 원칙이 새로운 대상에도 그대로 통한다는 점이 가장 인상 깊었다. "해제된 메모리는 덮어쓰이기 전까지 남는다"는 건 수십 년 된 이야기다. 그런데 그 위에 KV 캐시라는 새 자료구조가 올라오자 완전히 새로운 종류의 증거가 생겼다. 새로운 소프트웨어가 나올 때마다 "이건 메모리에 무엇을 남기는가"를 묻는 것만으로 연구 주제가 될 수 있다는 걸 다시 느꼈다.

포렌식과 프라이버시가 같은 현상의 양면이라는 점도 와닿았다. 수사관에게 유용한 잔존 데이터는 사용자에게는 지워지지 않은 개인정보다. IRIS는 "Privacy-Focused"를 내세우는 앱이지만, 사용자가 대화를 지워도 메모리에는 그대로 남아 있었다. 이 논문은 포렌식 기법인 동시에 로컬 LLM 앱의 프라이버시 결함 보고서로도 읽힌다.

마지막으로, 증거의 성격이 달라지고 있다는 생각이 들었다. 지금까지 디지털 증거는 대부분 "남아 있는 기록"이었다. ORISA가 만든 세션은 질문에 따라 답이 달라지는, 말하자면 **심문할 수 있는 증거**다. 이런 증거를 법정에서 어떻게 다뤄야 할지는 기술만으로 답할 수 없는 문제지만, 기술 쪽에서도 "어디까지가 기록이고 어디부터가 생성인지"를 구분해 보여 주는 장치는 필요하다고 본다.

### <toc2>배운 점</toc2>

- **KV 캐시의 실체.** 개념으로만 알던 KV 캐시가 메모리에서 어떤 크기(`H × D_h × E × 2` × 토큰 수)로, 어떤 구조(링 버퍼, `head`/`used`/`size` 메타데이터)로 존재하는지 구체적으로 알게 됐다.
- **라벨 없는 데이터를 검증하는 법.** 각자는 해석할 수 없는 두 데이터(토큰, KV 셀)를 서로의 위치·시퀀스 ID로 맞춰 보는 교차 검증 방식은 다른 포렌식 문제에도 쓸 수 있는 발상이다.
- **포렌식이 "쓰기"가 될 수 있다.** 엔진의 장부를 고쳐 버려진 메모리를 다시 쓰게 만드는 4단계는, 포렌식이 꼭 읽기 전용 분석일 필요는 없다는 걸 보여 줬다.
- **실험 설계의 디테일.** 모델이 원래 알 수 없는 무작위 키-값을 써서 "대화에서 온 지식"만 측정한 방식은, LLM이 끼는 실험을 설계할 때 참고할 만하다.

### <toc2>다른 분야로 넓혀 본다면</toc2>

- **데스크톱·서버의 로컬 LLM 실행기.** Ollama, LM Studio처럼 리눅스·윈도우·맥에서 돌아가는 llama.cpp 기반 실행기에도 같은 구조가 있다. 프로세스 덤프를 얻기가 모바일보다 훨씬 쉬워서 오히려 적용하기 좋다.
- **온디바이스 AI 전반.** 음성 비서, 키보드 자동완성, 이미지 생성 모델도 추론 중간 상태를 메모리에 둔다.
- **AI 에이전트 포렌식.** 에이전트가 도구를 호출한 기록과 중간 추론이 모두 컨텍스트에 들어 있다. 침해 사고가 났을 때 "에이전트가 무엇을 보고 무엇을 했는가"를 재구성하는 데 쓸 수 있다.
- **다중 사용자 추론 서버.** 여러 사용자의 KV 캐시가 한 프로세스에 있다면, 덤프 한 번으로 여러 사람의 대화가 드러난다. 포렌식보다는 보안 위험 평가에 가까운 주제다.

### <toc2>이어서 읽어볼 논문</toc2>

- **AI Psychiatry (USENIX Security 2024)** — 같은 연구실의 선행 연구로, 메모리 이미지에서 딥러닝 모델을 복구해 리호스팅한다. 한계 ⑨와도 연결된다.
- **DSCRETE (USENIX Security 2014)** — 앱 자신의 로직을 재사용해 메모리 속 자료구조를 해석한다. "엔진을 다시 써서 복원한다"는 발상의 뿌리로 보인다.
- **GUITAR (CCS 2015), Screen after Previous Screens (USENIX Security 2016), VCR (CCS 2015)** — Android 앱의 화면과 사진 증거를 메모리에서 복구하는 연구들. 모바일 메모리 포렌식의 흐름을 잡는 데 좋다.
- **Tipped Off by Your Memory Allocator (NDSS 2018)** — 메모리 할당기의 흔적으로 사용자 활동 순서를 재구성한다. 감쇠 곡선 실험을 고민할 때 참고가 될 것 같다.
- **I Know What You Asked (NDSS 2025)** — 다중 사용자 LLM 서빙에서 KV 캐시 공유로 프롬프트가 유출되는 공격. KV 캐시가 공격 표면이 되는 사례다.

### <toc2>앞으로 할 것</toc2>

우선은 데스크톱 llama.cpp로 작게 시작해서, 5장의 재현 항목 중 "토큰 버퍼 눈으로 확인하기"와 "새 대화 후 덮어쓰기 비율 세어 보기"부터 직접 해 볼 생각이다. 그 결과를 바탕으로 방향 A의 측정 연구를 어떤 변수로 설계할지 정리해 보려고 한다.
